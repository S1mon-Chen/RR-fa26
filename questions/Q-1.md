## 问题 1　负载均衡的收益与代价

### 1.1 收益：多花的钱逐条买到了什么（对应 L-02 的七类 NFR）

| NFR 类别 | 买到的东西（可度量） | 依据 |
| --- | --- | --- |
| **性能** | 2400 QPS 高峰下，查询 p95 从 4.8 s 降到 170 ms（最少连接），错误率从 9% 降到 0，满足"开放后 10 分钟内 p95 ≤ 2 s、不宕机"的要求 | Act 2 对照压测 |
| **可扩展性** | 处理能力从 1 个"旧机器单位"变为 1 + 3×2 = **7 个单位**（估算）。旧机器在 800 QPS 时 p95 = 150 ms，按此口径集群舒适容量约 7 × 800 ≈ 5600 QPS，去年高峰 2400 QPS 只占约 43%；再增长可继续加机器（加机器的上限见问题 5）。另外，Act 2 显示即使把去年的旧机器**换成一台新机器**（垂直扩容），2400 QPS 下仍是 p95 4.8 s、错误率 9%，所以"换一台好机器"不能替代这笔预算 | Act 0 单机压测 + Act 2 重载单机 + 新旧机器能力比 |
| **可靠性 / 可用性** | 单台应用服务器故障从"全站不可用 20～40 分钟"变为"健康检查 3 秒内摘除、用户无感"；应用层 4 台并联的可用性理论值 1 − 0.01⁴ = 99.999999%（计算与成立前提见问题 4） | Act 4 统计 |
| **可维护性** | 发布从"贴公告停机 10 分钟"变为"逐台摘除→更新→挂回"，学生无感；排障时 Nginx 访问日志可直接给出出错请求落在哪台机器 | Act 3 |
| **安全性** | 全站 HTTPS、单 IP 限流只需在唯一入口配置一次；后端 Tomcat 可只在内网暴露，不直接面对公网 | Act 3 |
| **易用性** | 不直接改善。学生"不再转圈"是性能改善带来的体验结果；反而若 Session 处理不当，会出现"反复要求登录"的易用性倒退（见下） | 事件 1 |
| **可移植性** | 基本无关。唯一的间接收益是客户端只认识 Nginx 的地址，后端迁到其他主机或容器时客户端不用改 | — |

结论：花的钱主要买到了**容量（性能 + 可扩展性）**和**冗余（可用性 + 可维护性）**，入口统一顺带买到了**安全与可观测**的集中管理点；易用性和可移植性不能算作这笔钱的收益。

### 1.2 代价：按 L-04"瓶颈 → 方案 → 新问题"来读

```text
瓶颈：单台 Tomcat（去年的旧机器）在约 1200 QPS 处到达拐点（p95 1.8 s，开始超时）；即使换成新机器，2400 QPS 时仍 p95 4.8 s、错误率 9%（Act 2）
方案：Nginx 七层负载均衡 + 4 台 Tomcat（L-04 第三阶段）
新问题：原来"只有一台"而天然成立的假设全部失效 —— 状态、缓存、日志都从 1 份变成了 4 份
```

#### 事件 1："明明登录了，点两下又让我重新登录"

- **成因**：登录状态保存在 Tomcat 进程内的 `HttpSession` 中，只有处理登录请求的那台机器有。轮询下，下一次请求落到同一台机器的概率只有 1/4，即点两下大概率换了机器；新机器上没有这个 Session，于是判定为未登录。单机时代"所有请求都到同一台"的隐含前提消失了。
- **常规解法**（按推荐程度排序）：
  1. **Session 集中存储**：Spring Session + Redis，所有 Tomcat 读同一份 Session，应用实例变成无状态（L-04 第三阶段给出的方向）。代价是多一个需要高可用的 Redis，每次请求多一次内网访问（亚毫秒级）。
  2. **无状态令牌**：登录后签发 JWT，服务端只验签不存状态。代价是令牌难以中途吊销、体积较大。
  3. **会话粘滞**（`ip_hash` 或 sticky cookie）：只能作为临时止血。校园网大量学生可能共用少数出口 IP，`ip_hash` 会导致负载严重不均；被粘住的机器宕机或下线发布时，其上的会话照样丢失。

#### 事件 2：学生总数没变，课程列表查询的数据库 QPS 变成原来的 4 倍

- **成因**：Caffeine 是**进程内本地缓存**，4 台 Tomcat 各有一份、各自过期、各自回源。对任一热点 key，只要每台机器 5 秒内至少被请求一次，回源频率就是"每台每 5 秒 1 次"：

  ```text
  数据库回源 QPS ≈ 实例数 N × 热点 key 数 K / TTL
  单机：1 × K / 5        4 台：4 × K / 5      → 恰好 4 倍，与学生人数无关
  ```

  示例：若 K = 1000 个课程 key，回源从 200 QPS 变为 800 QPS。另有两个副作用：缓存内存占用 ×4；4 份副本过期时刻不同，同一学生连续刷新可能看到余量"忽多忽少"。若各实例在 9:00 同时冷启动，还会每 5 秒集中失效一次，形成 L-04 所说的缓存击穿或雪崩。
- **常规解法**：
  1. **两级缓存**：本地 Caffeine 前置 + 共享 Redis（L-04 第二阶段），回源到 MySQL 的只有 Redis 未命中的那一次，回源量回到 K / TTL 量级。
  2. 本地缓存改用 `refreshAfterWrite` 异步刷新，并给 TTL 加随机抖动，避免集中失效；开放前预热。
  3. 若按课程 ID 访问，可在 Nginx 上用 `hash $arg_courseId consistent` 让同一门课固定落到同一台机器，每个 key 只在一台机器上缓存。代价是负载可能因热门课程而不均。

#### 事件 3：偶发 500，日志分散在 4 台，值班 40 分钟才找到出错的那台

- **成因**：单机时代只有一份日志；现在一次请求只在 4 台中的一台留下记录，排查者不知道是哪台，只能逐台登录 grep。请求在两层（Nginx → Tomcat）之间也没有可关联的 ID。
- **常规解法**：
  1. **在入口生成请求 ID**：Nginx 使用 `$request_id`，通过 `proxy_set_header X-Request-ID $request_id` 传给 Tomcat，Tomcat 用 MDC 把它写进每行应用日志。
  2. **Nginx 访问日志记录上游信息**：`$upstream_addr $upstream_status $upstream_response_time $request_id`。出现 500 时，在**一份** Nginx 日志里 grep `status=500` 就能直接得到出错机器和请求 ID。
  3. **集中日志**：Filebeat/Fluent Bit 采集到 ELK 或 Loki，按 request_id 一次检索全链路。
  4. 可度量目标（SMART）：从告警到定位出错实例 ≤ 2 分钟。

#### 其他代价（运维多操心的事）

| 新问题 | 说明 |
| --- | --- |
| Nginx 成为所有流量的必经点 | 它坏了全站不可用，必须做主备（问题 4） |
| 多一跳的延迟 | 轻载时每个请求多 1～5 ms（问题 2a） |
| 异构节点 | 旧机器只有一半能力，轮询策略会让它成为尾延迟源头（问题 2c） |
| 重试语义 | 必须确认 Nginx 不会把超时的**选课提交（POST）**重试到另一台，否则可能重复扣减。Nginx 1.9.13 起默认不重试非幂等请求，不能随手打开 `proxy_next_upstream ... non_idempotent` |
| 机器数 ×5 | 打补丁、配置一致性、证书、监控、发布脚本都要覆盖 5 台；健康检查参数本身也会成为故障源（问题 4 的 3 分钟 502） |

## 问题 2　吞吐量提升了，响应时间呢？

先指出同事那句话的两处不准确：

1. **"吞吐翻了几倍"**：重载场景两种架构的**输入负载都是 2400 QPS**。单机的有效吞吐（goodput）约为 2400 × (1 − 9%) ≈ 2184 QPS，其余超时；4 台时为 2400 QPS 且错误率为 0。这组实验证明的是**容量余量**变大了，而不是测出的吞吐翻倍；要说"翻几倍"，得做逐级加压找最大吞吐的实验。
2. **"响应时间全面变快"**：轻载时 4 台 + Nginx 反而**更慢**（p50 +1 ms，p95 +2 ms，p99 +5 ms）。变快只发生在重载下，而且变快多少取决于均衡策略。

### (a) 轻载时为什么 4 台反而比单机慢 1～5 ms

这两行**都是新机器**，硬件相同，所以差异只能来自架构本身。用 L-03 的分解：**响应时间 ≈ 建连 + 传输 + 后端处理**。轻载（200 QPS）时两种架构都几乎没有排队，所以差别全部来自"多了一层"：

| 分解项 | 多出来的开销 |
| --- | --- |
| 建连 | 浏览器先与 Nginx 建连（含 TLS），Nginx 再与 Tomcat 建连。Nginx 默认用 HTTP/1.0 连上游、**不复用连接**，每个请求多一次内网 TCP 握手 |
| 传输 | 请求和响应都要在 Nginx 处多收发一次、经过缓冲区复制，多一个内网往返（RTT 约 0.1～0.5 ms） |
| 后端处理 | Nginx 解析 HTTP、选上游、写访问日志。另外，200 QPS 被分成每台 50 QPS 后，每台本地缓存中冷门 key 在 5 秒内被访问的概率下降，**命中率降低**，偶发回源数据库的那部分请求会拉长尾部。这能解释为什么 p99 多出 5 ms，而 p50 只多 1 ms |

缓解办法：`upstream { keepalive 32; }` + `proxy_http_version 1.1` + `proxy_set_header Connection ""` 复用上游连接；共享 Redis 缓存。但"多一跳"的固定开销无法消除。所以**负载均衡在轻载时不会让单个请求更快**。

### (b) 重载时 p95 为什么从 4.8 s 掉到几百毫秒：排队

把"后端处理"再拆一层：

```text
后端处理时间 W = 服务时间 S（真正干活）+ 排队时间 Wq（等着轮到自己）
```

- 轻载时 p50 ≈ 18 ms，可视为单个查询的**服务时间 S**。负载均衡不会改变它，同一段代码、同一次缓存或数据库访问，在哪台机器上执行都差不多。
- **单机重载**（一台新机器）：p50 = 2.1 s，其中服务时间约 18 ms，即 **约 99% 的时间在排队**。由 Little's Law `L = λ × W`，取 λ ≈ 2184 QPS（有效吞吐）、W ≈ 2.1 s，系统内同时滞留约 **4600 个请求**，远超 Tomcat 默认 200 个工作线程（maxThreads）+ 100 的等待队列（acceptCount），多出的请求滞留在内核连接队列或超时失败。按新机器约为旧机器 2 倍折算，2400 QPS 压在一台新机器上，相当于让旧机器承受约 1200 QPS；Act 0 中旧机器在 1200～1500 QPS 区间正是开始超时、错误率从 0.5% 升到 9% 的区间，与这一行 p95 4.8 s、错误率 9% 的表现一致。输入负载已越过拐点，队列只会越积越长，直到超时把请求丢弃，这就是 9% 错误率的来源。
- **4 台重载**：每台只分到约 600 QPS，回到拐点以下：新机器的 600 QPS 只相当于旧机器的 300 QPS，远低于 Act 0 中 p95 仅 150 ms 的 800 QPS。p50 = 25～26 ms ≈ 18 ms 服务时间 + 约 7～8 ms 排队。由 Little's Law，全系统同时在处理的请求约 2400 × 0.026 ≈ **62 个**，每台约 16 个，线程池远未占满。
- Act 0 的曲线说明排队时间是**非线性**的：同一台机器从 800 到 1200 QPS（负载 +50%），p95 从 150 ms 涨到 1.8 s（×12）。排队论的直觉是 `Wq ∝ ρ / (1 − ρ)`，利用率 ρ 越接近 1，排队时间越陡。负载均衡把每台的 ρ 从"大于 1"拉回到"拐点以下"，这才是 p95 下降 28 倍的原因。

所以负载均衡**直接提升的是容量**，响应时间的下降是"**消除排队**"的副产品：它减掉的是 Wq，S、建连、传输一样不少（还略多）。

### (c) 同样 4 台机器，轮询的 p99 为什么是最少连接的 4 倍

- **轮询**不感知机器快慢，每台固定 25%（各 600 QPS）。旧机器只有新机器一半的能力，**同样 600 QPS 在它身上的利用率是新机器的 2 倍**。用 Act 0（正是这台旧机器）的曲线对照：600 QPS 已是它舒适点 800 QPS 的 75%，离 1200 QPS 的拐点只差一倍；而新机器上的 600 QPS 只相当于旧机器的 300 QPS。由 (b) 的非线性，利用率翻倍带来的排队时间远不止翻倍；选课高峰的流量又是突发的（9:00 集中涌入、缓存每 5 秒集中失效），旧机器在突发时会短暂越过拐点，积压的队列又因为它余量小而消化得慢。
- **p99 为什么只看旧机器**：轮询下 25% 的请求落在旧机器上，全系统最慢的 1% 请求几乎全部来自它；系统 p99 约等于旧机器自己的 p96。而 p50 几乎不受影响（26 ms 对 25 ms），因为 75% 的请求在新机器上。**策略差异几乎全部体现在尾部**。
- **最少连接**每次选当前活跃连接数最少的机器。由 Little's Law `L_i = λ_i × W_i`，把各机器的在途请求数 `L_i` 拉平，等价于 `λ_i ∝ 1 / W_i`：旧机器处理一个请求要 2 倍时间，就自然只分到一半流量。能力比 2 : 2 : 2 : 1 → 份额 2/7 : 2/7 : 2/7 : 1/7 = **28.6% / 28.6% / 28.6% / 14.3%**，与题中观测的 29/29/29/14% 吻合。此时 4 台利用率相同：新机器各约 686 QPS，旧机器约 343 QPS（只有其 800 QPS 舒适点的 43%）；按新机器折算，四台都约为 686 QPS，没有哪台单独成为尾巴。
- 用加权轮询（旧机器 `weight=1`、新机器 `weight=2`）也能得到同样的静态比例，但最少连接还能自动适应**瞬时**变慢（GC 停顿、缓存集中回源），更适合突发流量。

### 小结：改善的是平均响应时间还是尾延迟？

| 条件 | 平均 / p50 | 尾延迟 p95 / p99 |
| --- | --- | --- |
| 轻载（远低于单机拐点） | 不改善，略变差 1 ms | 不改善，略变差 2～5 ms |
| 重载、单机已过拐点 | 大幅改善（2.1 s → 25 ms），由**机器数量 / 总容量**决定 | 大幅改善，但改善多少由**均衡策略和节点同质性**决定（1.6 s 对 400 ms） |

结论：负载均衡本质上提升吞吐（容量），只有当**原系统的响应时间主要由排队构成**时，响应时间才随之改善。其中平均值的改善主要靠"总容量够不够"，**尾延迟的改善额外要求每一台都远离拐点**。这需要满足：① 均衡策略感知负载或按能力加权；② 瓶颈在应用层，下游数据库有余量（否则加机器只会把队列推到数据库，见问题 5）；③ 尾延迟的来源是排队，而不是 GC、锁等待这类单请求内部的慢。对后一类原因，负载均衡无能为力，需要 "The Tail at Scale" 中的对冲请求（hedged request）等手段。

## 问题 3　负载均衡带来的仅仅是性能提升吗？

不是。所有流量都经过同一个入口，许多能力"在一处做一次就全站生效"。但要区分哪些是开箱即用，哪些还得另外建设：

| 方面 | 具体机制 | 顺带 / 额外建设 |
| --- | --- | --- |
| **可用性** | 故障摘除：开源 Nginx 自带**被动**健康检查（`max_fails` / `fail_timeout`，真实请求失败若干次后暂时摘除），以及对幂等 GET 失败后自动换一台重试（`proxy_next_upstream`） | 被动摘除与重试是**顺带**的。题中"3 秒主动健康检查"在开源 Nginx 中**需要额外建设**（`health_check` 是 NGINX Plus 功能，开源版需 `nginx_upstream_check_module` / OpenResty 等第三方模块），健康检查接口也要应用自己实现 |
| **可维护性（发布与变更）** | 滚动发布：在 upstream 中把一台标记为 `down` 并 `nginx -s reload`（平滑重载，不断开已有连接）→ 等在途请求处理完 → 更新 → 健康检查通过后挂回；还可用 `weight` / `split_clients` 先给新版本 10% 流量做金丝雀 | "可以把流量从某台挪走"是**顺带**的；但让它真正"学生无感"需要**额外建设**：Tomcat 优雅停机、Session 外置（否则摘机器 = 踢人下线）、新旧版本能共存（接口与数据库结构向后兼容）、发布脚本自动化。还要注意摘一台就少 25% 容量，高峰期不要做 |
| **安全性** | TLS 终结（一张证书、一处升级 TLS 1.3）、`limit_req_zone $binary_remote_addr` 单 IP 限流、后端只在内网暴露 | 配置能力是**顺带**的。**额外**要处理：后端看到的客户端 IP 都是 Nginx，需配置 `X-Forwarded-For` 并让 Tomcat 信任它（RemoteIpValve）；校园网 NAT 下多名学生共用一个出口 IP，按 IP 限流可能误伤，应在应用层按学号再限一次；Nginx→Tomcat 是明文，需确认内网可信或重新加密；WAF 也要另外部署 |
| **可观测性** | 访问日志中 `$upstream_addr`、`$upstream_response_time`、`$request_time` 直接定位慢机器；`$request_time − $upstream_response_time` 可区分"慢在后端"还是"慢在网络或客户端"；`stub_status` 给出活跃连接数 | 入口处的全局视角是**顺带**的，这是唯一能看到全部请求的位置。日志格式需要自己配置；集中日志、指标看板（Prometheus + Grafana）、请求 ID 贯穿链路、告警都要**额外建设** |
| **成本 / 弹性** | 后端可以随时增减，客户端无感，平时缩容、高峰扩容 | "增减机器不影响客户端"是**顺带**的；何时缩、谁来扩、怎么预热，以及 upstream 列表的动态更新，都要**额外建设** |

### 回答主任："平时只用 3%，能不能关掉两台，选课前再开？"

**可以，但要满足以下前提**，并且要先算清楚是否真的省钱：

1. **容量前提**：平时几十 QPS，旧机器一台在 800 QPS 时 p95 也只有 150 ms，两台新机器绰绰有余（估算每台 CPU 利用率仅约 5%）。保留**两台而非一台**，是为了平时也保有冗余：两台并联可用性 1 − 0.01² = 99.99%，一台只有 99%（见问题 4）。应优先关掉旧机器。
2. **无状态前提**：Session 已外置到 Redis，否则关机等于踢掉这台上的所有登录用户。关机前先在 Nginx 上摘除并等待在途请求排空。
3. **配置前提**：upstream 列表要同步修改（或采用可动态更新的服务发现）。否则 Nginx 会持续尝试已关机的机器，产生失败请求和告警噪音。
4. **重新上线前提**：选课前**提前至少一天**开机，打齐补丁、发布到与其他机器一致的版本，做 JVM 预热和**缓存预热**，再做一次压测验证。不能在 8:55 才开机：4 台冷缓存在 9:00 同时回源，正好触发问题 1 的数据库 4 倍回源和缓存雪崩。整个过程要脚本化（基础设施即代码），按校历定时执行，因为选课高峰可以提前预测。
5. **风险前提**：长期关机的物理机可能开不起来（磁盘、电源），还会错过安全补丁、产生配置漂移，所以"选课前再开"必须留出排错时间。
6. **是否真的省钱**：如果是**云主机按小时计费**，关两台基本能省下约一半的应用服务器费用，值得做。如果是**学校自购的物理机**，机器本身是沉没成本，省下的只是电费（示例：单台空载约 150 W，两台关一学期约 2 × 0.15 kW × 24 h × 120 天 ≈ 860 kWh），收益很小。更好的用法是把这两台用作预发布环境或压测环境。

## 问题 4　系统变复杂了，为什么可靠性没有恶化？

### 4.1 串联与并联的可用性

- **串联**（任一环节坏，整体坏）：`A = A₁ × A₂ × … × Aₙ`，部件越多越差。
- **并联**（全部坏才坏，故障独立）：`A = 1 − (1 − A₁)(1 − A₂)…(1 − Aₙ)`，部件越多越好。

**4 台应用服务器各 99%，只要 1 台存活即可服务：**

```text
A_app = 1 − (1 − 0.99)⁴ = 1 − 0.01⁴ = 1 − 10⁻⁸ = 99.999999%
```

对照年不可用时长：单台 99% ≈ 87.6 小时/年；4 台并联 ≈ 0.3 秒/年。

整体是串联：`A_total = A_Nginx层 × A_app × A_MySQL`。若 Nginx 主备两台各 99%，`A_Nginx层 = 1 − 0.01² = 99.99%`。此时整体可用性的瓶颈已不在应用层，而在**仍是单点的 MySQL 和 Nginx 层**。示例：若 MySQL 单机为 99.9%，整体约 99.99% × 99.999999% × 99.9% ≈ 99.89%，由 MySQL 决定。这也是题图所说"Nginx 自己必须足够可靠"的原因。

**成立前提**：① 故障相互独立（同机柜断电、同一份错误配置、同一个软件 bug 会同时打倒所有机器，见 4.4）；② 剩余机器容量足够（见进阶题）。

### 4.2 主备为什么适合 Nginx，却不是应用服务器的首选

- **Nginx 几乎无状态**：它保存的只有静态配置，以及少量可丢弃的运行时状态（在途连接、限流计数器）。备机配置相同，keepalived 通过 VRRP 把虚拟 IP 漂移过去，2 秒后就能完整接管，丢失的只是那 2 秒内的在途连接，客户端重试即可。同时，单台 Nginx 的能力（数万 QPS，L-04 数量级表）远大于 2400 QPS，**容量上不需要多台同时工作**，主备就够了。
- **应用服务器"有状态"且"缺容量"**：
  1. **容量**：Act 2 显示单台新机器在 2400 QPS 下 p95 4.8 s、错误率 9%；按新机器舒适容量约 2 × 800 = 1600 QPS 估算，2400 QPS 需要至少 2 台、留余量需要 3 台同时工作，主备模式下只有一台在干活，根本扛不住高峰，等于花 2 倍的钱买 1 台的容量。
  2. **状态**：应用服务器上有 Session 和本地缓存。主备切换时，若状态没有同步，所有学生被踢下线，备机冷缓存瞬间回源数据库；若要同步状态，就得先把状态外置或复制。可一旦状态外置、应用变成无状态，**多活（4 台同时工作 + 负载均衡）就严格优于主备**：所有容量都被使用；坏一台只损失 1/4 容量而不是全部；不需要"由谁判定主机已死、何时切换"的决策，也就没有脑裂风险。
  3. 主备的备机平时闲置，它自己的隐性故障要等到切换时才暴露；多活下每台机器随时承接真实流量，坏了会立刻被发现。
- 反过来，Nginx 主备也有代价：keepalived 可能脑裂（两台同时持有 VIP），两台配置可能漂移，需要定期演练切换。

### 4.3 "故障次数"为什么变多，"服务可用性"为什么变好

- **故障次数 ∝ 机器数 × 单机故障率**。机器从 1～2 台变成 7 台（4 Tomcat + 2 Nginx + 1 MySQL），出故障的机会自然更多：5 次对 3 次。
- **可用性取决于"故障转化为用户不可用的比例"和 MTTR**：`A = MTTF / (MTTF + MTTR)`，这里的 MTTR 指**用户感知到的**恢复时间。
  - 单机时代：每次故障 = 全站不可用，用户感知的 MTTR = 人工恢复 20～40 分钟，3 次共约 90 分钟。
  - 本学期：机器故障被健康检查在 3 秒内屏蔽，用户感知的 MTTR ≈ 3 秒，且只影响落在故障机上的那部分在途请求。**修机器的 20～40 分钟从关键路径上移走了**，可以白天慢慢修，不计入不可用时间。
  - 估算：本学期约 140 天 = 201,600 分钟，不可用 3 分钟 → 99.9985%；单机时代两年约 1,051,200 分钟，不可用 90 分钟 → 99.991%。按一学期的时长折算，单机时代约 17 分钟/学期，本学期 3 分钟，**而且这 3 分钟与机器故障无关**。
- 一句话：冗余没有让机器更少坏，而是让"坏"不再等于"停"。

### 4.4 全站 502 那 3 分钟：负载均衡引入的新故障模式

那 3 分钟的本质是**共模故障（common-mode failure）**：4 台后端由**同一个** Nginx、按**同一套**健康检查规则判定生死。一次网络抖动同时影响 Nginx 到 4 台机器的探测，过于激进的阈值（间隔短、失败一次就摘除、超时小于正常 p99）把 4 台同时判死。这正好违反了 4.1 中"故障独立"的前提。**本来用于屏蔽故障的机制，把一个非故障放大成了全站故障。**

解法：
- 阈值合理：失败次数 ≥ 3、超时大于正常 p99，并区分"连续失败"和"偶发失败"。
- **恐慌阈值（fail open）**：当健康机器比例低于某个值（如 Envoy 默认 50%）时，判定"更可能是检查本身出了问题"，忽略健康检查，继续向所有机器转发。
- 把 Nginx 配置当代码管理：进 Git、评审、`nginx -t` 校验，先改一台再推全量，并保留一键回滚。

**同类风险**（都是"集中化的入口或机制同时影响全部节点"）：

| 风险 | 后果 |
| --- | --- |
| Nginx 配置变更错误（upstream 写错、reload 失败） | 一次改动影响全站，爆炸半径 = 100% |
| 级联故障：高峰时摘掉一台 → 剩余 3 台负载 +33% → 越过拐点变慢 → 被判不健康再摘掉 → 雪崩 | 健康检查与容量不足叠加，结果比不摘除更糟 |
| 重试风暴：后端变慢时 `proxy_next_upstream` 重试放大流量；对非幂等 POST 重试造成重复选课 | 放大故障、破坏正确性 |
| 健康检查接口与真实健康不符：`/health` 只返回 200，数据库连接池已耗尽仍被视为健康（黑洞）；或检查过深，数据库抖一下 4 台全被摘 | 误留或误摘 |
| keepalived 脑裂或 VIP 漂移后 ARP 缓存未更新 | 入口不可达 |
| Nginx 上的 TLS 证书过期 | 全站 HTTPS 失败 |
| 共享依赖单点：MySQL 只有一台 | 应用层再多冗余也无用 |
| 冷启动机器挂回后缓存为空，集中回源 | 数据库瞬时过载 |

### 进阶（不计分）：至少 3 台存活的可用性

```text
P(≥3 台存活) = p⁴ + C(4,3)·p³·(1−p)
             = 0.99⁴ + 4 × 0.99³ × 0.01
             = 0.96059601 + 0.03881196
             = 0.99940797 ≈ 99.94%
```

对比：1/4 存活为 99.999999%，3/4 存活只有 99.94%，年不可用约 5.2 小时，**比 1/4 时差了约 6 万倍**。若 4 台中有一台是只有一半能力的旧机器，而"3 台"指 3 台新机器的等效容量，那么任何一台新机器坏了都不够，可用性只剩 0.99³ ≈ 97.03%，**比单台新机器还差**。

对容量规划的意义：
1. 冗余只来自"超过需求的那部分机器"。需要 3 台时配 4 台，实际只有 N+1 冗余；高峰期的"8 个 9"是幻觉。
2. 高峰要按 **N+2** 规划：5 台中至少 3 台存活 = Σ_{k=0}^{2} C(5,k)·0.01ᵏ·0.99⁵⁻ᵏ ≈ **99.999%**，多一台机器换来约两个数量级的提升。
3. 容量要按同质化的"等效单位"计算，异构的旧机器不能按 1 台算。
4. 选课高峰只有 10 分钟，在这 10 分钟内恰好坏机器的概率远小于 1%。更现实的风险是共模故障（配置、发布、网络）。所以高峰前应**冻结变更**，这比多买机器更有效。

## 问题 5　负载均衡有没有上限？

### 5.1 第一层：负载均衡器自身的上限

**为什么 Nginx 在约 2.5 万 QPS 到顶**：L-04 数量级表中，Nginx 七层反向代理单机为"数万～十万级 QPS"，2.5 万处在下沿，因为这里是 **HTTPS**。七层负载均衡必须对每个请求完整地做：TCP 终结 → TLS 解密（新连接还要做 ECDHE 等非对称运算的握手）→ 解析 HTTP 头 → 选上游、再建或复用一个上游连接 → 双向复制数据 → TLS 加密响应 → 写访问日志。这些都是**按请求计**的 CPU 工作，学生每秒刷一次余量，握手和加解密的量直接随 QPS 线性增长。对比四层 LVS：它只在内核里按 IP 和端口转发数据包，DR 模式下响应甚至不经过 LVS，所以能到数十万～百万级。

**需求 3 万 QPS > 单台 2.5 万 QPS**，单台 Nginx 无论如何扛不住。扩展路径：

1. **先压降每请求的成本**（最小改动）：TLS 会话复用（session ticket）、客户端 keep-alive / HTTP/2 减少握手次数、ECDSA 证书、`worker_processes auto` 用满所有核、上游 keepalive。
2. **再压降请求数**：余量查询在 Nginx 上做 1 秒的微缓存（`proxy_cache_valid 200 1s`），命中时连 Tomcat 都不经过；或改为 SSE 推送余量，取代每秒轮询（L-03 Pull 与 Push）。
3. **仍不够则横向扩展入口，即 L-04 第六阶段**：LVS（DR 模式）或 F5 主备 + VIP，后面挂多台 Nginx。台数估算：按 CPU 不超过 70% 留余量，3 万 / (2.5 万 × 70%) ≈ 1.7 → 2 台，再加 N+1 冗余 → **3 台 Nginx**。
4. **第七阶段**：若两个校区各有机房，或要求机房级容灾，再用 DNS 轮询 / GSLB 让同一域名解析到两个机房的 VIP。代价是跨机房数据同步，以及 DNS 缓存导致切换变慢。对一所学校而言，当前容量需求还不需要第七阶段（YAGNI）。

**边界**：上面每一层都只是把"单点上限"往上推一个数量级，每一层自身仍有上限，只是更高。

### 5.2 第二层：横向扩展的上限（Amdahl 定律）

以 1 台时的 300 TPS 为基准，加速比 `S(N) = TPS(N) / 300`。由 `S(N) = 1 / [s + (1 − s) / N]` 解出：

```text
s = (N / S(N) − 1) / (N − 1)
```

| N | 提交 TPS | 加速比 S(N) | 反解 s | 用 s = 0.25 回代的预测 TPS |
| --- | --- | --- | --- | --- |
| 1 | 300 | 1.00 | — | 300 |
| 4 | 690 | 2.30 | (4/2.30 − 1)/3 = **0.246** | 686 |
| 8 | 870 | 2.90 | (8/2.90 − 1)/7 = **0.251** | 873 |
| 16 | 1010 | 3.37 | (16/3.37 − 1)/15 = **0.250** | 1010 |
| 32 | — | — | — | 1097 |
| ∞ | — | — | — | **1200** |

三个数据点独立反解都得到 **s ≈ 0.25**，回代误差小于 1%。

**理论上限**：`S(∞) = 1 / s = 4`，即**无论加多少台应用服务器，提交 TPS 都不会超过 300 × 4 = 1200 TPS**。从 16 台加到 32 台，16 台机器只换来约 87 TPS；从 8 台到 16 台每台只增加 17.5 TPS，而第 1 台贡献了 300 TPS。

**s 来自哪里：唯一的那台 MySQL 及其上的热点行锁。**
1. **行锁串行化**：抢课提交都执行"对课程余量行减 1"，InnoDB 对同一行加排他锁直到事务提交，同一门热门课的所有事务只能一个接一个执行。热门课那几行"行锁等待占提交耗时的 70%"直接证明了这一点。无论请求来自哪台 Tomcat，到这里都排成一队。
2. **数据库是共享资源**：数据库 CPU 从 25%（300 TPS）涨到 95%（1010 TPS）。按每 TPS 约 0.083% CPU 外推，CPU 达到 100% 时约为 300 × 100/25 = **1200 TPS**，与 Amdahl 拟合的上限恰好一致。这说明那 25% 的"串行比例"就是每笔提交在单台数据库上花掉的、无法被应用服务器分摊的那部分工作（含行锁持有、redo/binlog 刷盘与组提交）。
3. **还会更糟**：同一行上排队的事务越多，InnoDB 死锁检测的开销越大（等待者两两检查），这正是数据库 CPU 被吃满的原因之一。真实系统在越过某点后吞吐可能**下降**而不只是持平（通用可扩展性定律 USL 中的"一致性开销"项）。Amdahl 只给出了**乐观**上限。

### 5.3 第三层："均衡"本身的上限：数据级热点

题图那句话概括得很准确："负载均衡把请求分开了，数据却没有分开。"

**请求级负载均衡能做的：**
- 把 2000 个提交均匀分给 16 台 Tomcat，保证应用层不是瓶颈。但应用层本来就不是瓶颈。
- 在入口**限流**（`limit_req` / `limit_conn`），把进入写路径的并发压到数据库能承受的范围内，保护数据库不被压垮。
- 按课程 ID 做一致性哈希（`hash $arg_courseId consistent`），让同一门热门课的所有提交落到同一台 Tomcat，为应用层做"进程内排队 / 合并扣减"创造条件。负载均衡层能做的只是**为下一层的方案提供亲和性**。

**做不到的：**
- 不能把一行数据拆开。2000 个请求无论分到几台机器，最终都要拿 `CS101` 那一行的同一把锁。
- 加机器反而有害：同时打到数据库的并发事务更多，锁等待和死锁检测开销更大。
- 不理解业务语义：它不知道 60 个名额已经抢完，剩下 1940 个请求注定失败，仍会把它们全部送进数据库。

**解决办法应放在数据层和业务层（入口层辅助）：**

| 层 | 办法 | 代价 |
| --- | --- | --- |
| 入口层 | 名额售罄后在缓存中置"已满"标记，Nginx/应用直接返回"名额已满"，不再进数据库；入口限流 | 标记有秒级延迟；必须保证最终校验仍在数据库 |
| 数据层 | **缩短持锁时间**：单条条件更新 `UPDATE course SET remain = remain − 1 WHERE id = ? AND remain > 0`，配合选课表 `(student_id, course_id)` 唯一约束防重复，扣减放在事务最后、立即提交 | 仍是串行，只是每次更快 |
| 数据层 | **拆热点行**：60 个名额拆成 6 个子行各 10 个，请求随机选子行扣减，锁竞争降为约 1/6 | 子行耗尽时要再找其他子行；统计余量要求和 |
| 数据层 | **Redis 预扣**：Lua 脚本原子地"查重 + 扣减"（Redis 十万级 QPS），成功者再经消息队列异步落库（L-03 的 Outbox 保证可靠） | 前端需区分"已受理"与"选课成功"；要与数据库对账 |
| 应用层 | **按课程排队**：每门热门课一个队列、单消费者串行处理，批量提交，没有锁竞争 | 增加等待；需要处理积压、重复和结果查询 |
| 业务层 | **改规则**：热门课改为"报名 + 抽签"，或按年级错峰开放 | 需教务处决策，但能从根本上消除"秒杀"峰值 |

**结论**：请求级负载均衡解决的是"**计算**能否分摊"；"2000 人抢 60 个名额"是"**数据**能否分摊"的问题。这个问题的串行性来自业务本身（同一份名额只能被逐个分配），只能在**数据层**（缩短或拆分临界区）和**业务层**（改变争抢方式）解决，入口层的限流和售罄拦截只起保护作用。L-04 的核心原则"识别当前瓶颈 + 最小改动"在这里意味着：瓶颈已经从应用服务器转移到数据库的一行数据上，再加应用服务器不是最小改动，而是无效改动。
