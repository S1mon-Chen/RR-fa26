## 1. 本讲主线：从结构到时间轴（pp.3、5–6）

[Lecture 4](/Users/xlchen/RR-fa26/notes/lecture-04.md) 讨论系统由哪些组件构成、如何连接，以及瓶颈出现后如何演进。本讲换一个视角：**一行代码从写下到退役，经过哪些状态？每个状态产出什么，能不能退回去？**

| 视角 | 主要问题 | 示例 |
| --- | --- | --- |
| 结构图 | 由什么组成，组件怎么连接 | Nginx → 多台 Tomcat → MySQL / Redis |
| 时间轴 | 当前是什么状态，如何进入下一状态，能否撤销 | v1.0 → v1.1 → v1.2；每版经历构建、部署、运行、替换 |

DevOps 要求同时关注这两种视角。系统不仅要能运行，还要能持续交付、替换、恢复与退役。

### 1.1 两条生命周期

```text
制品轴：源码 → 构建 → 测试 → 版本 → 配置与环境 → 部署 → 运行 → 变更/回滚 → 下线
                                                   │
                                                   └─ 把一个制品变成若干运行实例

实例轴：启动 → 就绪 → 服务 → 停止 → 退出/替换
         ↑                              │
         └──────── 新实例重新开始 ────────┘
```

| 维度 | 制品的生命周期 | 实例的生命周期 |
| --- | --- | --- |
| 关注对象 | 版本及其制品 | 一次运行中的进程 / 实例 |
| 时间范围（课件） | 跨天到跨年 | 跨分钟到跨周 |
| 核心问题 | 是哪个版本，在哪些环境，能否退回上一版 | 能否接流量，怎样安全地停止 |
| 两者关系 | 同一制品可以部署多次、产生多个实例 | 一个版本运行期间，实例可能被多次替换 |

**部署是两条轴的交点。** 制品轴上的一次部署，在实例轴上通常表现为启动一批新实例、停止一批旧实例。

本讲是“重新认识软件”模块的第一部分：L-05 看生命周期，L-06 看运行中的进程，L-07 看资源消费，L-08 看度量指标。

### 1.2 贯穿案例

选课平台 9:00 开放选课，8:55 发现刚上线的新规则有 bug。此时能否快速恢复，取决于之前是否保留旧制品、设计兼容的数据变更、准备功能开关和回退路径。

## 2. DORA 指标：生命周期的健康状况（p.7）

| 指标 | 衡量什么 | 课件中的“精英团队”示例 |
| --- | --- | --- |
| 部署频率 | 多久部署一次到生产 | 按需，一天多次 |
| 变更前置时间 | 从提交到进入生产需要多久 | 小于一天 |
| 变更失败率 | 部署后需要修复或回滚的比例 | 约 5% |
| 失败部署恢复时间 | 失败部署后多久恢复 | 小于一小时 |

前两个指标关注**速度**，后两个关注**稳定性**。课件强调，交付快与运行稳定并不必然矛盾，优秀团队可以同时做好两者。

这些数字用于建立数量级直觉；课件注明以相应年度 DORA 报告为准，本笔记未将其当作最新报告结论。复习重点是四个指标分别反映生命周期的哪个方面。

## 3. 制品生命周期总览与源码提交（pp.9–10）

### 3.1 九个节点及产出物

| 节点 | 课件中的产出物 / 结果 | 复习时要追问 |
| --- | --- | --- |
| 源码 | 一次提交 | 能否追溯到这次变更？ |
| 构建 | JAR、二进制、容器镜像等制品 | 制品能否被准确识别、重复部署？ |
| 测试 | 质量门禁的结论 | 哪些检查支持进入下一阶段？ |
| 版本 | 带版本号的制品 | 版本、构建与源码能否互查？ |
| 配置 + 环境 | 可运行的组合 | 环境差异与配置变更是否受控？ |
| 部署 | 环境中的实例 | 如何替换实例、保留回退能力？ |
| 运行 | 对外提供的服务 | 当前版本是否正常，新旧能否共存？ |
| 变更 / 回滚 | 进入新状态，或恢复到先前状态 | 数据与外部副作用是否允许撤销？ |
| 下线 | 服务或功能退出使用 | 依赖、数据与资源是否处理完毕？ |

每个节点都按三个问题理解：**产出物是什么？常见问题是什么？能不能回到上一个状态？** 产出物与记录使变更可追溯、过程可复现；不可逆的步骤应放在最后，留出更长观察时间。

### 3.2 提交是追溯起点

一次提交是本讲使用的最小变更单位。后续的制品、版本和部署都应能追溯到源码提交。

- **人工门禁：**代码评审。
- **自动门禁：**CI 执行构建和测试，通过后才能合入主干。
- **协作原则：**短命分支、小步提交、主干随时可发布。

分支模型和分支保护的具体做法见实验 1 指导书。本讲关注的是：**“线上跑的是哪次提交”必须有明确答案。**

## 4. 构建、测试与版本（pp.11–13）

### 4.1 不可变制品：一次构建，多处部署

制品（artifact）是构建产出，例如 JAR、可执行文件或容器镜像。课件要求 **build once, deploy many**：同一个制品经过不同环境的验证后被部署，环境差异通过配置表达。

| 问题 | 课件分析的原因 | 对策 |
| --- | --- | --- |
| “在我机器上能跑” | 依赖、系统库、JDK、环境变量等不一致 | 同一制品跨环境部署，配置与制品分离 |
| 同一源码两次构建不同 | 依赖版本未固定，基础镜像使用 `latest` | 锁定依赖；镜像用 digest 引用；固定构建环境 |
| 找不到线上制品，制品库无序增长 | 缺少源码关联与保留策略 | 记录 git SHA、构建号；课件示例为保留最近 N 个及所有已上线制品 |

课件举例包括 `package-lock`、`go.mod` 与 `go.sum`、Maven 固定版本，并要求按 digest 引用镜像、以镜像固定构建环境。理解重点是同时管理依赖版本、校验信息与构建环境，不能仅凭存在某个文件就认定整个构建已经可复现。

**补充理解：**不可变指某个制品一经生成便不原地修改；修复问题应生成新制品。它与“相同输入能否重建出相同输出”是相关但不同的要求。镜像封装程序及其运行依赖，也不意味着数据库、配置和宿主机差异全部消失。

### 4.2 测试贯穿状态变更

| 位置 | 课件列举的检查 | 时间 / 数量直觉 |
| --- | --- | --- |
| 构建时 | 单元测试 | 秒级，数量最多 |
| test 环境 | 集成测试 | 分钟级 |
| staging 环境 | 端到端测试、性能测试 | 小时级 |
| 线上 | 合成监控、金丝雀验证 | 课件图中数量最少 |

**测试左移（前移）：成本越低的检查越早执行。** 将门禁分成构建、合并、发布等层次，可以缩短发现问题到修复的反馈环。

“测试环境正常，生产仍然出错”可能来自环境漂移。课件给出的方向是：各环境使用同一制品，环境用代码定义。

**要点：测试在总览中有一个节点，但质量检查并不限于那个节点。** 表中的耗时是教学示例，不是每类测试的固定时长。

### 4.3 版本号、构建号与 git SHA

SemVer 用 `MAJOR.MINOR.PATCH` 表达兼容性承诺，例如 `1.4.2`：

| 部分 | 课件含义 |
| --- | --- |
| MAJOR：主版本 | 不兼容的改动 |
| MINOR：次版本 | 向后兼容的新功能 |
| PATCH：修订号 | 向后兼容的修复 |

| 标识 | 面向谁 | 回答的问题 |
| --- | --- | --- |
| 版本号 `1.4.2` | 用户、依赖方 | 这次变化作出什么兼容性承诺？ |
| 构建号 `#1873` | 流水线 | 这是哪一次构建？ |
| git SHA `a1b2c3d` | 开发者 | 对应哪份源码？ |

**三者要能互查。** 版本号的意义在于兼容性约定，构建号和源码提交则支持定位与追溯。课件用 Tomcat 的 `javax` → `jakarta` 迁移说明不兼容变更。

## 5. 发布、部署、放量与配置（pp.14–15）

### 5.1 三个动词改变三层状态

| 动作 | 改变哪一层 | 本讲示例 | 撤销方式 |
| --- | --- | --- | --- |
| 发布 release | 制品层 | 打 `v1.4.2` tag，制品获得版本号并进入制品库 | 撤回版本，较少采用 |
| 部署 deploy | 环境层 | `v1.4.2` 在生产的 4 台机器上运行 | 部署回上一版 |
| 放量 rollout | 流量 / 功能暴露层 | 1% 用户使用新版本，或打开功能开关 | 切回流量、关闭开关 |

英文 release 在不同上下文中也可能指“对用户开放”；本笔记遵循课件的上述区分。

**部署与放量可以分开。** 新代码先进入生产，功能暂不对用户开放，课件称为 dark launch。出问题时，如果可以切流量或关闭开关，往往比替换所有实例更快。

联系 Lecture 2：Continuous Delivery 强调随时具备发布条件，Continuous Deployment 强调通过流水线自动部署。不能只依据是否打了 tag 判断是否已经持续交付。

### 5.2 同一制品，不同配置

| 环境 | 本讲定位 |
| --- | --- |
| dev | 开发者环境 |
| test | 自动化测试环境 |
| staging | 尽量接近生产，用于预演 |
| prod | 生产环境 |

课件给出三条原则：

1. **配置与代码分离：**数据库地址等由环境变量或配置中心注入；密钥单独管理，不进入代码仓库。
2. **配置也有生命周期：**版本化、评审、先灰度后全量，并保留回退能力。
3. **环境用代码定义：**通过 IaC（Infrastructure as Code，基础设施即代码）定义环境，以重建而非手工修补维护环境，减少环境漂移。

课件用“可变的只有制品版本和配置版本”强调交付控制：始终能回答当前和上一版是什么。

**补充理解：**这句话不表示业务数据不变化；代码与配置的版本管理，不能替代对数据库、消息和其他运行状态的管理。配置切换也不一定热生效，可能需要重启实例。

## 6. 部署策略与版本共存（pp.16–17）

### 6.1 五种手段的取舍

| 手段 | 做法 | 收益 | 主要成本 / 前提 | 课件回退量级 |
| --- | --- | --- | --- | --- |
| 重建 / 停机 | 停旧实例，再起新实例 | 实现简单 | 存在停机窗口 | 分钟，重新部署 |
| 滚动 | 一次替换一台或一批 | 可保持服务持续提供 | 新旧版本必须兼容；课件模型下替换期间容量下降 | 分钟，反向滚动 |
| 蓝绿 | 两套环境，切换流量 | 切换和回退快 | 切换窗口内增加资源；共享数据库的 schema 仍需兼容 | 秒，切回旧环境 |
| 金丝雀 | 先给 1%～10% 流量，观察后扩大 | 用真实流量验证，限制影响范围 | 需要流量控制和指标对比；新旧版本共存更久 | 秒，切回流量 |
| 功能开关 | 代码已部署，由配置决定是否启用 | 分离部署与功能开放 | 增加代码分支；开关需治理、清理；快速关闭要求热生效 | 秒，关闭开关 |

不存在脱离约束的最优策略。选择取决于回退时间要求、资源预算、兼容性与运维能力；实际可以组合滚动、金丝雀和功能开关。

**补充理解：**滚动期间是否减容取决于能否先加新实例、再停旧实例；蓝绿的额外资源成本也取决于哪些层复制。课件的时间和资源数字是案例模型，切流量还需考虑传播与已有连接。

### 6.2 新旧版本共存时会发生什么

滚动更新中，同一用户的连续请求可能分别落到 v1.4 和 v1.5。兼容性不仅涉及 API，也涉及消息、Session、缓存和数据库。

| 风险 | 课件对策 |
| --- | --- |
| 新版产生的数据，旧版无法解析 | 优先增加字段，避免直接删除或改变语义；旧字段先废弃再删除；消费者容忍未知字段 |
| 新生产者写入的消息，旧消费者读不懂 | 消息带版本号；先升级能兼容新旧格式的消费者，再升级生产者 |
| 新版更改 Session / 缓存格式，旧版读取失败 | 使用新 key 前缀，或提供兼容读取 |

**补充理解：**“增加字段”也要求消费者确实容忍未知字段；给消息加版本号只是识别格式，还需要对应的处理逻辑。缓存换前缀能隔离格式，但不能自动完成已有状态的迁移。

## 7. 回滚边界与数据库变更（pp.18–19）

### 7.1 回滚代码，不等于恢复整个系统

```text
系统状态 = 代码 + 配置 + 数据
```

| 对象 | 课件中的恢复方式或边界 |
| --- | --- |
| 制品 | 重新部署上一版 |
| 配置 | 切回上一版配置 |
| 流量 / 功能开放 | 切回旧版本或关闭开关 |
| 数据库 schema | 删除的列不会随代码回滚恢复；新增约束可能使旧代码无法写入 |
| 已写入数据 | 旧代码可能不认识新逻辑写入的记录 |
| 消息、外部调用 | 已发短信、已发生扣款等副作用不会自动撤销 |
| 缓存 | 新格式内容仍可能存在，旧代码读取时继续报错 |

两种恢复方向：

- **回滚（roll back）：**退回先前的代码、配置或流量安排。
- **向前修复（fix forward）：**通过后续变更修复当前状态；已经改变的数据与副作用往往需要这种方式处理。

课件用“代码与配置可以按版本回退，数据只能向前演进”提醒回滚的边界。为回滚而设计，意味着将代码变更与数据变更拆分发布，并在写入数据前检查旧代码能否读取。

**补充理解：**这不是说任何数据都不能恢复，而是说数据不会随部署自动倒退。备份恢复、反向迁移、业务补偿都有各自条件和代价，也可能影响故障后合法产生的数据。回退前必须检查旧代码能否处理当前的数据与 schema。

### 7.2 expand–contract：扩展、迁移、切读、收缩

场景：选课记录表 `enrollment` 需要增加 `section_id`，让冲突检测从“按课程”改为“按教学班”。

| 步骤 | 做什么 | 读写状态 | 回退能力 |
| --- | --- | --- | --- |
| ① 扩展 expand | 增加可空的 `section_id`，暂不改代码 | 旧代码继续使用旧列 | 新列可以保留，无须为了退回旧代码而删掉它 |
| ② 双写与迁移 migrate | 新代码写新旧两列，后台回填历史数据 | 仍读旧列 | 可退回旧代码；新列暂时保留 |
| ③ 切读 | 确认新数据齐备后，改读 `section_id` | 读新列，继续双写新旧列 | 可退回读旧列的上一版，旧列仍有完整数据 |
| ④ 收缩 contract | 确认旧列不再使用，再删除旧列或增加 `NOT NULL` | 移除旧路径或施加新约束 | 可能破坏旧代码运行条件，应放最后、等最久 |

**核心是把一次大变更拆成多个兼容步骤，每步独立发布和验证。** 代价是迁移周期变长、双写与回填增加一致性管理成本。

课件明确指出，切读后旧列**仍在双写**；回退依赖的不只是旧列仍然存在，还包括它持续得到正确维护。收缩是关闭旧路径的最后一步，不应套用前几步的回退承诺。

**补充理解：**

- 第二步若退回不认识新列的旧代码，回退期间产生的新记录可能缺少 `section_id`；再次切读前需重新检查和补齐。
- 收缩前要确认旧实例、旧消费者、后台任务等都不再依赖旧结构；增加非空约束前还要确认数据和所有写入路径满足要求。

课件警示把 schema 与代码一次性一起改会损害回退能力。理解重点是**避免在同一次变更中破坏旧版本的运行条件**，而不是把所有同时涉及代码与 schema 的发布都视为绝对不可回滚。

## 8. 下线与退役（p.20）

软件长时间运行，就会经历依赖、接口和功能各自的生命周期。EOL（End of Life）意味着某个版本或产品到达其支持生命周期的终点，需要提前规划迁移。

| 问题 | 课件对策 |
| --- | --- |
| 依赖的运行时 / 库不再提供安全补丁 | 盘点 EOL，将升级纳入路线图 |
| 老接口没人敢删，不清楚调用方 | 标记废弃 → 监控调用量 → 通知调用方 → 设定下线日期 → 下线 → 删除代码 |
| 功能已删，队列、定时任务和数据仍残留 | 用下线清单覆盖代码、配置、数据、基础设施、监控告警、文档 |

课件列举 Tomcat 连接器移除与 CentOS 7 的 EOL，说明长期维护还要处理上游依赖变化。具体版本状态与迁移步骤应查看对应公告。

数据按需求归档或删除，并考虑适用的保存要求。**下线不是只删代码，而是有计划地解除依赖和收尾资源。**

## 9. 实例的生命周期与健康检查（pp.22–23）

### 9.1 一次运行的状态机

```text
启动中 → 已就绪 → 服务中 → 停止中 → 已退出
                                    ↓
                              新实例重新启动
```

| 状态 | 主要活动 | 判断重点 |
| --- | --- | --- |
| 启动中 | 读配置、建立数据库 / Redis 连接池、加载缓存或模型、JIT 预热 | 进程活着，不代表能服务 |
| 已就绪 | 需要的依赖可用、预热完成 | 可以加入负载均衡、接收流量 |
| 服务中 | 正常处理请求 | 可能因线程池饱和、依赖故障而变得不就绪 |
| 停止中 | 停止接新请求、处理在途请求、关闭连接 | 是否在期限内完成退出 |
| 已退出 | 当前实例结束 | 替代实例从启动阶段重新开始 |

课件给出的启动时间示例为 10 秒～2 分钟，停止窗口示例为不超过 30 秒；它们不是所有应用的统一时限。

**补充理解：**状态图是一条正常路径。就绪状态在运行中可以反复变化；实例暂时不能接流量，不代表它已经退出。

### 9.2 存活与就绪是两个问题

| 检查 | 核心问题 | 失败后的动作 | 课件对应名称 |
| --- | --- | --- | --- |
| 存活检查 | 实例是否仍能正常执行，是否需要重启？ | 达到失败条件后重启 | `livenessProbe` |
| 就绪检查 | 实例现在能否接流量？ | 暂时摘除流量，本身不要求重启 | `readinessProbe` |

课件另提及 `startupProbe`；具体机制留到后续 Kubernetes 模块展开。

三个典型错误：

1. **进程一启动就切流量：**初始化尚未完成，最初请求大量失败。应等待就绪检查通过。
2. **只检查进程是否存在：**进程可能已经死锁或失去处理能力，仍不断接到请求。存活检查需反映应用自身是否还能工作。
3. **把数据库短暂故障判为所有实例死亡：**实例集体重启，进一步放大故障。课件要求外部依赖故障影响就绪，避免直接使存活检查失败。

**补充理解：**检查内容应与实际服务能力匹配。若某个依赖故障仍允许降级服务，需要判断是否应摘除整个实例；健康检查也不能重到反过来拖垮应用或下游。

## 10. 优雅停止、启动时间与无状态（pp.24–25）

### 10.1 优雅停止的五步

1. 收到 **`SIGTERM`**，执行程序准备好的终止处理逻辑。
2. 从负载均衡摘除，或将就绪状态置为失败，停止接收新请求。
3. 等待在途请求完成，但设置等待上限，例如课件中的 30 秒。
4. 关闭连接池、刷出日志并退出。
5. 超时仍未结束则强制终止，未完成的在途请求可能丢失。

`SIGKILL` 不能替代上述优雅处理过程。WebSocket、SSE 等长连接还需要安排断开与客户端重连，排空连接（drain）可能需要更长时间。

**补充理解：**从负载均衡摘除到流量真正停止之间可能有延迟，停止流程要为此留出余量。即使客户端超时，也不能直接认定服务端没有完成写入，重试需要考虑重复操作。

### 10.2 启动时间是发布与恢复的硬约束

课件给出简化估算：

```text
发布时间 ≈ 实例数 ×（停止时间 + 启动时间 + 就绪时间）÷ 并行度
```

适用前提是各批次耗时近似、以固定并行度替换；它没有完整计入流量传播、验证和异常处理时间。

启动时间直接影响：

- **扩容速度：**流量上升后，新实例要多久才能提供容量。
- **部署与回滚速度：**每批实例替换要等待多久。
- **冷启动体验：**按需启动实例时，用户请求需要等多久。

课件将这一点联系到 Lecture 3 的 Quarkus / GraalVM，下一讲再展开。这里应记住：**能快速启动、安全停止，实例才适合被频繁替换。**

### 10.3 实例短命为什么要求无状态

```text
实例可能因部署、扩缩容或故障被替换
  → 实例内存和本地文件不能成为唯一的持久状态
  → 需要保留的状态放到 Redis / 数据库 / 对象存储等系统
  → 新实例可以接替旧实例
  → 支持滚动、扩缩容与自动恢复
```

Lecture 4 中的 Session 共享问题，在这里有了生命周期解释：应用实例不再唯一，也不能假定它长期存活。

**补充理解：**无状态指应用实例不独占必须保留的业务或会话状态，不表示程序不能使用内存、本地缓存或临时文件；可丢失、可重建的内容仍可本地存放。数据库和队列等有状态系统在替换时需要额外保证数据持久性与一致性，不能直接套用应用实例的替换假设。

## 11. 职责归属：DevOps 与流水线（pp.27–28）

### 11.1 生命周期的所有权

| 阶段 | 课件描述的传统分工 | DevOps 下的分工 |
| --- | --- | --- |
| 源码 / 构建 / 测试 | 开发 | 开发 |
| 版本 / 发布 | 发布工程 / 测试 | 开发，通过自动化完成 |
| 环境 / 配置 / 部署 | 运维 | 开发 + 平台，提供自助能力 |
| 运行 / 监控 / 值班 | 运维 | 开发 + SRE |
| 下线 | 容易无人负责 | 产品 + 开发 |

课件用 **you build it, you run it** 强调开发对运行结果承担责任，平台团队提供自助工具。DevOps 关注全生命周期的协作和所有权，不只是增加一个岗位名称。

**补充理解：**这不意味着每位开发者都要独自承担所有基础设施工作；关键是阶段之间有明确负责人，发布后和退役时也有人持续负责。

### 11.2 流水线是生命周期的自动化

每个箭头可以对应一次自动化状态变更，每道门禁可以对应一次检查。Lecture 2 讨论流水线如何搭建，本讲解释它实际管理什么。

实验 1 的课件预告：

```text
代码仓库 + 分支保护
        ↓
push → GitHub Actions 构建 → 测试 → 打包制品/镜像 → 打版本与发布
```

预期产出是一个**能追溯到源码提交的制品**。实验时间、分支模型和提交要求以指导书为准，本讲没有给出完整实验规范。

### 12.2 讨论一：冻结什么，冻结多久？

**课件讲评：**

- 代码冻结 2～3 天，给 staging 预演与观察留时间。
- 配置变更可以进行，但需要双人评审。
- 基础设施冻结。
- 紧急 hotfix 按例外流程处理：最小改动、两人批准、回滚预案。

冻结会推迟新功能或调整，但能减少高峰前的不确定性。它提高变更门槛，并不等于完全禁止改动。

**补充理解：**冻结策略与下节的迁移安排要一起看：分阶段发布应提前列入计划或按例外流程管理；课件的“2～3 天”是案例建议，不是所有项目的固定规则。

### 12.3 讨论二：schema 如何分步发布？

| 日期 | 课件讲评安排 | 保留的恢复能力 |
| --- | --- | --- |
| 10/6 | 发布①：只加可空列 `section_id` | 旧代码继续运行 |
| 10/7 | 发布②：双写 + 回填；新规则置于开关后，默认关闭 | 可关闭新规则或退回旧代码，新列保留 |
| 10/8 | 在 staging 预演打开开关 | 验证新规则和操作流程 |
| 10/9 之后 | 再安排切读与收缩 | 先确认迁移和兼容性，再移除旧路径 |

**理解边界：**staging 的演练不等于生产已经放量；课件未给出完整的生产开关开启计划。上表强调将不可逆的收缩推迟，实际启用新规则还要满足其数据读取和回退条件。

### 12.4 讨论三：8:55 发现 bug，哪种办法赶得上？

**课件讲评的回退时间估算：**

| 方案 | 时间估算 | 前提与代价 |
| --- | --- | --- |
| 关闭可热生效的功能开关 | 秒级 | 已提前实现开关；旧路径仍可用；有人有权限并知道如何操作 |
| 蓝绿切回 | 秒级 | 旧环境仍保留且可承接当前数据和流量；承担额外 4 台机器的费用 |
| 单台一批滚动回滚 | `4 × (0.5 + 1) = 6` 分钟 | 8:55 开始，约 9:01 完成，超过开放时间 |
| 两台一批滚动回滚 | `(4 ÷ 2) × (0.5 + 1) = 3` 分钟 | 约 8:58 完成，但题设下替换期间容量减半，缓冲时间很少 |
| 关闭需重启生效的开关 | 接近滚动重启耗时 | 不具备热开关的秒级恢复能力 |

这里的 1 分钟已经包括“启动 + 预热”，计算时不能再重复加一遍预热时间。3 分钟和 6 分钟也没有额外计入确认故障、下发操作、检查恢复结果等耗时。

**参考判断：**如果故障仅在新规则、关闭开关后旧路径仍正确且配置可热生效，可以优先关闭开关；如果不满足这些前提，就要评估蓝绿或制品回退。不能在事故发生后才临时假设系统有开关、有可用旧环境。

**课件结论：回退速度是在发布前准备出来的。8:55 能做什么，取决于 10/6～10/8 做了什么。**

### 12.5 讨论四：8:50～8:55 的请求如何处理？

题目另给出这一时间段已有受影响请求，需要区分两种结果：

| 情况 | 课件讲评 | 为什么回滚代码不够 |
| --- | --- | --- |
| 误拒合法选课 | 题设假定未写入选课记录，学生重试；需要公告说明 | 恢复服务不会自动替用户重新提交 |
| 误收冲突选课 | 找出按错误规则写入的记录，逐条补偿：取消、通知、归还名额 | 错误记录已经入库，旧代码不会自动删除它们 |

因此，写入记录时应保留版本 / 规则标记，结合时间范围定位受影响记录。只知道故障发生的时间，不一定能准确区分哪些记录由新逻辑产生。

联系 [Lecture 3](/Users/xlchen/RR-fa26/notes/lecture-03.md) 的 Saga：补偿是明确的业务动作，不能把切回旧代码当作已经撤销所有业务结果。

**补充理解：**应先识别并核验受影响记录，再执行补偿；补偿要处理重试，避免同一条选课记录被重复取消或名额重复归还。这里的补偿流程是课程案例，不是无条件批量删除某个时间段全部选课数据。

## 13. 本讲要点与易混淆概念（p.33）

| 容易混淆的概念 | 区别 |
| --- | --- |
| 制品 vs 实例 | 制品是可识别、可部署的构建产物；实例是其一次运行 |
| 不可变制品 vs 软件不更新 | 更新通过产生并部署新制品完成 |
| 发布 vs 部署 vs 放量 | 分别管理制品版本、环境中的运行、用户流量或功能开放 |
| 存活 vs 就绪 | 前者决定是否需要重启，后者决定现在是否接流量 |
| 回滚 vs 补偿 | 回滚切回代码 / 配置等版本；补偿处理已经产生的业务结果 |
| 无状态 vs 没有数据 | 无状态应用实例仍可访问持久化数据，不独占关键状态 |
| 测试节点 vs 质量门禁 | 测试有专门产出，但检查贯穿多次状态变更 |
| 功能开关 vs 数据迁移 | 开关控制后续执行路径，不能自动撤销 schema 和已有数据 |

复习时，将本讲的两个判断标准与前几讲结合：

```text
这个方案解决了什么问题，增加了什么成本？
这个阶段产出什么，能不能回到上一个状态？
```

## 15. 复习自测

1. **两条生命周期轴的交点是什么？**  
   部署：把一个制品变成环境中的若干实例。

2. **为什么不能在 test、staging、prod 分别重新构建后，就认定部署的是同一制品？**  
   构建依赖或环境可能变化，应将验证过的同一不可变制品推进到后续环境。

3. **版本号、构建号和 git SHA 各有什么用？**  
   分别表达兼容性承诺、标识一次构建、定位源码，并且应能互查。

4. **代码进入生产后，是否必须立即对所有用户开放？**  
   不必。部署可以与放量分离，通过流量控制或功能开关逐步开放。

5. **滚动发布为什么要求兼容？**  
   新旧实例会共存，并可能共享 API 数据、消息、缓存、Session 和数据库。

6. **expand–contract 最后一步为什么要等最久？**  
   删除旧字段或施加新约束可能破坏旧版本的运行条件，缩小甚至关闭回退空间。

7. **数据库短暂故障时，为什么不宜让所有应用存活检查一起失败？**  
   重启不能直接修复共享依赖，反而可能因集体重连和预热放大故障。

8. **优雅停止为什么要先摘流量，再等待请求结束？**  
   若持续接受新请求，在途请求可能一直无法排空；等待本身还需要超时上限。

9. **题设 4 台实例单台滚动回退为什么约需 6 分钟？**  
   每台按停止 0.5 分钟、启动与预热 1 分钟估算，串行合计 `4 × 1.5 = 6` 分钟。

10. **功能开关为什么不一定比部署回滚快很多？**  
    如果配置只有重启后才生效，关闭开关仍需等待实例逐批重启。

11. **误收冲突选课后，代码回滚完成是否代表故障处理结束？**  
    不代表。还需定位错误记录、完成业务补偿、归还名额并通知受影响用户。

12. **流水线在本讲中的本质是什么？**  
    将生命周期中的状态变更和质量门禁自动化，同时保留可追溯的产出。
