## 2. 操作系统视角：进程、线程与 CPU（pp.5–6）

### 2.1 一个服务在机器上是什么

本讲先用“一个实例对应一个主要服务进程”的模型分析。进程有自己的地址空间，包含线程、内存映射和文件描述符表。

```text
服务进程
├─ 线程 × N：被调度到 CPU 上运行，各有线程栈
├─ 内存：堆、线程栈、元数据、JIT 代码、direct buffer、共享库等
└─ fd 表
   ├─ 客户端 socket：浏览器 / Nginx → Tomcat
   ├─ 下游 socket：Tomcat → MySQL / Redis
   └─ 文件、管道：日志、配置、JAR 等
```

| 资源 | 消耗在哪里 | 关键问题 |
| --- | --- | --- |
| 线程 | CPU 时间、栈内存、调度开销 | 在运行、等 CPU，还是等锁 / I/O？ |
| 内存 | 堆、堆外、共享映射，以及服务依赖的内核缓存 | 堆以外还用了多少？实际限制是什么？ |
| fd | 打开的 socket、文件、管道等 | 还可以接多少连接、打开多少文件？ |

**补充理解：**真实服务也可能由多个 worker 进程组成，容器也可以包含多个进程；“服务 = 一个进程”是本讲的分析起点。

### 2.2 利用率与饱和不是一回事

- **利用率：**CPU 有多少时间在忙。
- **饱和：**已经有可运行任务因 CPU 不够而等待。

线程是操作系统的调度单位。可运行线程多于可用核数时，需要轮流运行；切换还会带来调度与缓存失效成本。

| 现象 | 可能的解释 | 应继续观察 |
| --- | --- | --- |
| CPU 平均只有 60%，响应却越来越慢 | 单个核或短时峰值已饱和；也可能在等锁、连接或 I/O | 每核利用率、运行队列、线程状态 |
| 线程从 200 增到 2000，吞吐反降 | 上下文切换、缓存失效，或下游竞争加重 | 切换次数、`user` / `sys`、下游等待 |
| 进程 `%CPU` 超过 100% | 多个线程同时使用多个核 | 工具是否按“单核 = 100%”计数 |
| load average 高，CPU 却不高 | Linux load 也包含不可中断睡眠任务 | 阻塞任务、存储等待等 |

在单核为 100% 的口径下，4 核进程可接近 400%。`user` 是用户态耗时，`sys` 是内核代进程完成工作的耗时。

**不要按在线用户数设置线程数。** 线程配置要结合核数、阻塞比例和下游容量；并发用户、连接、请求、线程是不同的数量。

## 3. 内存：堆不等于进程总占用（p.7）

### 3.1 四个需要区分的口径

| 概念 | 含义 | 易错点 |
| --- | --- | --- |
| 虚拟内存 | 进程地址空间中的保留与映射 | 预留地址空间不等于已占用同等物理内存 |
| 堆 | JVM 等运行时管理对象的主要区域 | `-Xmx` 只限制最大堆大小 |
| RSS | 进程当前驻留在物理内存中的页 | 包含共享页，不等于进程独占内存 |
| 页缓存 | 内核缓存文件数据使用的内存 | 可回收部分不能简单视为“泄漏” |

JVM 除了堆，还要为线程栈、元空间、JIT 代码缓存、直接缓冲区及本地库等付出内存成本。

```text
服务内存预算 ≈ 堆的实际需求 + 堆外需求 + 相关缓存与内核开销 + 余量
```

课件用“堆设 2 GB，进程却占 3 GB”说明：**不能直接把容器内存限制设成 `-Xmx`。**

### 3.2 三种常见误判

1. **`free` 很低，就认为内存耗尽。**  
   Linux 会用空闲内存做缓存；判断还能承受多少新负载时，优先看 `available`，并结合回收与换页情况。

2. **线程栈预留 1 MB，就认为每个线程立即占 1 MB RSS。**  
   课件的 1 MB 是预留量示例，物理页按需提交；实际默认值也与平台和配置有关。

3. **退出码 137，就断定一定发生 OOM。**  
   常见约定下 `137 = 128 + 9`，表示进程被 `SIGKILL` 终止。OOM 是一种原因，也可能是其他强制终止；应结合 `OOMKilled`、内核日志和 cgroup 事件确认。

**补充理解：**课件将页缓存画在 RSS 之外，用于提醒服务还有进程之外的内存需求。精确统计时，映射进进程的文件页可以进入 RSS；cgroup 内存统计也可能包括文件缓存、socket 缓冲区和内核内存，不能把 RSS 与全部缓存机械相加。容器预算应核对实际计费口径。[Linux cgroup v2 文档](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)

## 4. 连接与 fd：CPU 空闲也会拒绝服务（p.8）

### 4.1 连接数不等于请求数

文件描述符（file descriptor，fd）用于引用进程打开的文件、socket 等资源。客户端连接与数据库连接在 Tomcat 进程里分别占用 fd。

keep-alive 连接即使暂时不发送请求，也会占 socket、fd 和缓冲资源。

```text
客户端连接数 ≈ 在线人数 × 每人保持的连接数
2000 人 × 4 条连接 ≈ 8000 条连接
```

这个数字不能直接解释成 8000 QPS，也不能解释成需要 8000 个业务线程。

### 4.2 三种 Tomcat 参数与一个系统限制

| 配置 / 限制 | 管什么 | 本讲使用的值 |
| --- | --- | --- |
| `maxThreads` | 请求处理线程的最大数量 | 200 |
| `maxConnections` | 连接器接收、处理的连接数量 | 8192 |
| `acceptCount` | 连接达到限制后，操作系统连接等待队列的长度配置 | 100 |
| `ulimit -n` / `RLIMIT_NOFILE` | 进程可用的 fd 限额 | 讨论中假设仍为 1024 |

**补充理解：**`acceptCount` 不是“200 个工作线程以外，只允许再排 100 个 HTTP 请求”。它控制连接 backlog，实际大小还受操作系统影响。已接收连接、请求执行队列、数据库等待队列也不能混算；使用外部 executor 时，线程限制要看 executor 配置。[Tomcat 10.1 HTTP Connector](https://tomcat.apache.org/tomcat-10.1-doc/config/http.html)

### 4.3 典型故障

| 现象 | 可能瓶颈 | 思路 |
| --- | --- | --- |
| `Too many open files`，CPU 很闲 | fd 已耗尽 | 核对进程实际限额与 fd 用途；调整限额、连接超时 |
| 新连接失败，已有连接仍可工作 | 连接额度或 backlog 已满 | 观察连接数、监听队列与连接建立失败 |
| 短连接频繁建立、关闭 | 握手开销、`TIME_WAIT` 与临时端口压力 | 合理复用连接，检查是哪一端主动关闭 |

**补充理解：**`TIME_WAIT` 是连接关闭后由内核维护的 TCP 状态，不等于原进程仍持有一个打开的 fd；出现在哪一端也不能一概而论。

Nginx 可以替后端维持大量客户端连接，并通过上游连接复用降低后端建连与空闲连接压力。但效果依赖协议、配置、并发活跃请求和长连接比例；上游 keepalive 缓存大小本身也不是总连接数上限。[Nginx upstream keepalive](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#keepalive)

## 5. 怎么观察：工具速查与课堂演示（pp.9–10）

以下是 **Linux 服务端**命令；`<pid>`、`<host>` 要替换为实际值，macOS 上不能直接照搬 `/proc` 等接口。

| 想看什么 | 命令 | 重点 |
| --- | --- | --- |
| 进程 CPU、RSS、线程数 | `top`；`ps -p <pid> -o pid,nlwp,rss,%cpu` | `%CPU`、RSS、`nlwp`；注意单位与统计时间窗 |
| CPU 排队与阻塞 | `uptime`；`vmstat 1` | load average、`r` 可运行任务、`b` 阻塞任务 |
| 可用内存 | `free -m` | `available`，而非只看 `free` |
| 进程 fd 数 | `ls /proc/<pid>/fd`，再统计条目数 | socket 与文件各占多少 |
| 连接及监听队列 | `ss -s`；`ss -tanp`；`ss -ltn` | 连接状态、数量、监听队列 |
| 哪些线程忙 | `top -H -p <pid>` | 各线程 CPU、R / S 等状态 |
| 线程 / goroutine 在做什么 | Java 用 `jstack`；Go 用相应 `pprof` profile | 计算、等锁、等 I/O、goroutine 堆积 |

课堂演示先观察空载 Tomcat，再进行 10 秒负载：

```bash
top -H -p <pid>
grep -E "VmRSS|Threads" /proc/<pid>/status
free -m
ls /proc/<pid>/fd | wc -l
ss -s

# 在测试环境使用，替换目标地址
wrk -t4 -c200 -d10s http://<host>:8080/
```

这里 `-t4` 是压测客户端的 4 个线程，`-c200` 是它保持的 200 条连接，不能直接当作服务端线程数。

课件希望比较：线程状态、RSS、fd 与 TCP 状态在压测前后的变化。**补充理解：**线程数是否增加取决于线程池是否已建立、是否按需扩张；RSS 也受分配和 GC 影响。课件中的“线程数不变”“压完有大量 TIME_WAIT”是演示预期，不是所有环境的固定结果。本笔记没有把这些预期写成实测数据。

## 6. 语言运行时：选择资源画像（pp.12–14）

### 6.1 JVM：堆、GC、JIT 与线程

| 机制 | 收益 | 代价 / 观察重点 |
| --- | --- | --- |
| 堆与 GC | 自动管理对象内存 | GC 消耗 CPU，部分阶段会 Stop-The-World（STW）；停顿取决于回收器与负载 |
| JIT：即时编译 | 热点代码优化后可有较高吞吐 | 启动与预热期间性能不同，刚上线不一定已到稳态 |
| 平台线程 | 传统阻塞编程方式直接 | 通常与 OS 线程 1:1 对应，有栈和调度成本 |
| 虚拟线程 | 保留阻塞式写法，以较低成本承载大量等待任务 | 仍受 CPU、内存、数据库连接和锁约束 |

“堆越大越好”不成立：它影响内存预算、回收行为和实例密度。JIT 则解释了上一讲为什么把启动时间、预热与就绪检查联系在一起。

课件以 JDK 10+ 的容器感知说明 JVM 可以读取容器资源限制；实际支持还取决于具体 JDK、cgroup 版本和参数，不能以此替代内存预算。

**虚拟线程的核心：降低等待时占用 OS 线程的成本。** JDK 21 将其正式引入；它通过运行时调度映射到平台线程。适用的阻塞操作可以挂起虚拟线程、释放承载线程，但不能将所有阻塞情形都视为零成本。它不会让一段 CPU 计算自动更快。[JEP 444：Virtual Threads](https://openjdk.org/jeps/444)

### 6.2 Go、Node.js、Python

| 运行时 | 主要并发单位 | 本讲强调的优势 | 需要注意 |
| --- | --- | --- | --- |
| Go | goroutine，M:N 调度到 OS 线程 | 初始栈 KB 级，适合大量并发任务；启动与内存基线较轻 | goroutine 泄漏、GC CPU 成本；并发不等于无限容量 |
| Node.js | 主事件循环，配合异步 I/O、线程池等 | 适合大量 I/O 等待 | 在主循环里执行长时间 CPU 计算会阻塞其他回调；可用 worker threads 或多进程分担 |
| Python | 进程、线程；异步程序还使用协程 / 任务 | `asyncio` 组织 I/O 并发，多个 worker 分担请求 | 传统启用 GIL 的 CPython 中，普通 Python 字节码线程不能自由多核并行；CPU 密集任务常用多进程 |

**补充理解：**课件提到 Python 3.13 起的无 GIL 构建，用于提醒运行时会演进，不能把 GIL 当成所有 Python 实现与构建的永久属性。Node 的网络 I/O 也不能全部理解为“扔给 libuv 线程池”；本节重点是避免阻塞事件循环。

### 6.3 怎样读课件的对比表

| 运行时 | 课件内存基线 | 课件启动量级 | 多核使用方式 | 课件吞吐印象 |
| --- | --- | --- | --- | --- |
| JVM（JIT） | 较高，百 MB 起 | 秒级，并需预热 | 多线程 | 预热后高 |
| GraalVM Native Image | 较低 | 毫秒级 | 多线程 | 示例中略低于 JIT |
| Go | 较低，十 MB 级 | 毫秒级 | 运行时调度 | 高 |
| Node.js | 中 | 亚秒级 | 多进程，也可用 worker threads | I/O 场景有优势 |
| Python | 中 | 亚秒级 | 常见多 worker 部署 | 本讲示例较低 |

这些是**教学数量级，不是相同条件下的性能排名**。实际结果取决于框架、库、工作负载、优化与运行时配置；原生镜像也不是所有场景都必然比 JIT 吞吐低。

课件用“同一台机器 JVM 放 2 个实例、Go 放 10 个”说明实例密度的影响，不是可以直接套用的比例。选择运行时，要同时评估启动时间、稳态吞吐、内存、构建成本与团队能力。

## 7. 并发模型与吞吐：先说明公式的边界（pp.16–19）

### 7.1 Little's Law：平均在途数 = 吞吐 × 平均停留时间

```text
L = λ × W

L：选定系统边界内的平均在途请求数
λ：通过该边界的平均吞吐，单位 requests/s
W：请求在该边界内的平均停留时间，单位 s
```

使用时必须满足两个要求：

1. **边界一致。** 若 L 数整个服务内的请求，W 就包含该服务内的处理与等待；若只数占用工作线程的请求，W 就是平均线程占用时长。
2. **使用平均值与适当的稳定观察窗口。** p50、p95、p99 不能直接代替平均 W；在持续过载、队列不断增长时，不能随意把输入速率当作稳定吞吐。

在“一请求占一个工作线程”的阻塞模型下，线程池有 T 个线程：

```text
线程容量估算：λ_thread ≈ T / W_thread
```

| 参数 | 估算 | 含义 |
| --- | --- | --- |
| T = 200，平均占线程 50 ms | `200 / 0.050 = 4000 rps` | 仅考虑线程这一项的理论容量 |
| T = 200，平均占线程 500 ms | `200 / 0.500 = 400 rps` | 下游变慢 10 倍，线程容量降至 1/10 |

**等数据库时不一定使用 CPU，但仍可能占着平台线程。** 因此 CPU 不高、线程池却满，是完全可能的。

**补充理解：**课件 p.17 用 p50 2.1 s 联系“约 5000 个在途请求”，应作为排队量级的说明；仅凭 p50 不能严谨算出平均在途数，也不能证明它们具体排在哪个队列。

### 7.2 排队无处不在

```text
客户端
  → 连接接入 / accept backlog
  → 请求等待执行
  → 工作线程等待数据库连接
  → 数据库执行与锁等待
  → 返回结果
```

这是等待位置的概念图，不表示每个请求都必然依次进入所有队列。

| 等待位置 | 等什么 | 可见症状 |
| --- | --- | --- |
| 接入层 | 有能力接收连接 | 建连慢、连接超时 |
| 请求执行队列 | 空闲业务线程 | 请求延迟上升 |
| 数据库连接池 | 空闲连接 | 获取连接耗时增加 |
| 数据库内部 | CPU、I/O 或热点锁 | 查询 / 事务耗时上升 |

队列能吸收短暂突发，却不增加长期处理能力。高峰结束后仍慢，可能是服务还在处理已经失去价值的积压请求。

课件给出的方向是：**有界队列、超时、截止时间与背压。** 补充理解：还需要定义队列满后如何拒绝或减速，以及如何把压力反馈给上游；仅设置等待超时，并不保证下游正在执行的工作被取消。

### 7.3 非阻塞与事件循环改变什么

- `epoll` / NIO 让少量线程管理大量连接，避免每条空闲连接都占一个业务线程。
- 在事件循环中执行 50 ms 的同步计算，会推迟该循环上其他任务的处理。
- Tomcat NIO 的接入与轮询可以非阻塞，但同步 Servlet 的业务处理仍可采用一请求一线程。
- 虚拟线程或 goroutine 降低大量等待任务的线程成本，**CPU、数据库连接、热点锁的容量仍然存在**。

不要把“能挂起很多任务”理解为“能够同时完成同样多的数据库操作”。限流与并发控制仍然需要。

### 7.4 数据库连接池：更少但更稀缺的并发资源

```text
连接池容量估算：λ_pool ≈ P / D

P：可用连接数
D：每个请求平均占用的连接时间总量
```

本讲例子：10 个连接，每请求占用 8 ms：

```text
λ_pool ≈ 10 / 0.008 = 1250 请求/s
```

这个计算假设数据库能维持该耗时，且请求的连接需求符合题设。若一个请求多次访问数据库，应累计连接占用；若事务里夹着网络调用或其他等待，连接可能比 SQL 本身执行时间占用得更久。

| 做法 / 现象 | 为什么 |
| --- | --- |
| 连接池从 10 调到 100，吞吐不变 | 下游并行能力有限，等待只是移进数据库 |
| 数据库单条 SQL 不慢，请求却偶发很慢 | 可能在等待获取连接 |
| 缩短事务与持有连接的范围 | 降低每请求占用连接时间，提高复用效率 |
| 多实例各开一个连接池 | 必须把所有实例的连接总量与数据库容量一起算 |

课件以 MySQL `max_connections = 151`、HikariCP 池大小 10 说明连接有上限。这些是本讲的配置背景，不能把最大连接数当成数据库可高效并行执行的查询数。

**补充理解：**HikariCP 的“约核数 × 2”是调优起点，原讨论还涉及磁盘等因素；核数指数据库侧的资源，最终应以压测为准。[HikariCP：About Pool Sizing](https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing)

池满时通常先等待，超过 `connectionTimeout` 后可以抛出异常，因此课件的“表现是延迟，不是错误”应理解为**最初的表现**。[HikariCP 配置说明](https://github.com/brettwooldridge/HikariCP#configuration-knobs-baby)

## 8. 回答 Lecture 4：线程池是症状，行锁可能是原因（p.20）

### 8.1 读写路径要分别分析

| 路径 | 本讲瓶颈 | 线程池的角色 |
| --- | --- | --- |
| 查询课表、查询余量 | CPU 或数据库连接池 | 轻载时平均线程占用短，还远未达到 200 个 |
| 抢热门课程、扣减余量 | 对共享数据的串行竞争 | 大量请求等待下游，线程逐渐被占满 |

写路径的因果链：

```text
同一热门课程余量需要协调更新
  → 行锁竞争，提交吞吐受限
  → 已拿到数据库连接的请求等待锁，其他请求等待连接
  → 阻塞式业务线程被占满
  → 上游积压、超时、重试
  → 负载进一步放大
```

因此，“先看到线程池满”不等于“根因是线程不够”。把线程池扩大到 2000，可能只是让更多请求进入等待，同时增加内存与调度成本。

### 8.2 300 TPS 与 1200 TPS 的来源

课件援引思考题 1 的写路径数据：单机约 300 TPS；串行比例约 `s = 0.25` 时，按 Amdahl 定律：

```text
S(N) = 1 / [s + (1 - s) / N]
N → ∞ 时，S_max = 1 / s = 4
理想总吞吐上限 ≈ 300 × 4 = 1200 TPS
```

**补充理解：**1200 TPS 是该案例、该串行比例下的理想渐近上限，不是数据库行锁的通用性能，也不是 4 台机器必然达到的吞吐。不能仅凭后面参数表的“数据库写 10 ms”推出 300 TPS；整个数据库调用耗时与持有热点锁的临界区时长并不等同。

课件提出 Redis 原子扣减、排队削峰和限流等方向。它们各自解决不同问题：

- **调整数据更新路径：**减少数据库热点竞争，但要处理正确性、持久化、失败补偿与一致性。
- **排队削峰：**把突发流量变成可处理的节奏，但增加等待，且必须限制积压。
- **限流：**控制进入系统的工作量，让过载可控，但需要明确拒绝或重试反馈。

Redis 中一次原子扣减，并不会自动保证 Redis 与 MySQL 之间的一整套业务事务正确。

## 9. 延迟：百分位数与扇出放大（pp.22–23）

### 9.1 p50、p95、p99 分别说什么

| 指标 | 直观含义 | 观察重点 |
| --- | --- | --- |
| 平均值 | 全部请求耗时的算术平均 | 总体平均成本，会受极慢请求影响 |
| p50 | 约 50% 请求不超过该耗时，即中位数 | 典型体验 |
| p95 | 约 95% 请求不超过该耗时 | 较慢一端的体验 |
| p99 | 约 99% 请求不超过该耗时 | 尾部体验 |

**概念校正：**课件将 p99 简称为“100 个里最慢的那个”，这个说法不精确。按 nearest-rank 方法，100 个样本升序排列后，p99 取第 99 个，最大值是第 100 个；其他分位数算法也可能插值。应记“99% 分位点”，不要记成最大值。[NIST：Percentiles](https://www.itl.nist.gov/div898/handbook/prc/section2/prc262.htm)

右偏长尾分布中，平均值常大于 p50；这不是任何分布都必然满足的关系。延迟应说明指标、统计窗口与请求范围。课件强调在 SLO 中关注尾部，但不意味着所有 SLO 必须只用 p99。

### 9.2 一次页面有多个下游调用

假设一个页面同步等待 N 个并行调用，**每个调用超过 100 ms 的概率均为 1%，且慢事件相互独立**：

```text
P(所有调用都不超过 100 ms) = 0.99^N
P(至少一个调用超过 100 ms) = 1 - 0.99^N
```

| N | 至少遇到一次慢调用的概率 | 解释 |
| --- | --- | --- |
| 1 | 1% | 单次调用的尾部 |
| 12 | 约 11.4% | 约 88.6% 的调用组能全部在阈值内完成 |
| 100 | 约 63.4% | 大多数调用组至少遇到一个慢调用 |

课件说“单服务 p99 成了页面 p89”，是把页面耗时近似为这组并行调用的最大值，并忽略其他开销后的表达。

**补充理解：**

- N 是必须同步等待的调用数，不是系统服务总数；14 个服务不等于 N 必须为 14。
- 串行调用沿关键路径相加；并行且必须全部完成的分支由最慢者决定。不能把所有服务耗时一律相加，也不能把各服务 p99 直接相加当页面 p99。
- 一般情况下应写 `1 - P(所有调用都不慢)`，只有独立时才能直接相乘。
- 课件用共享数据库说明相关慢事件。相关性对概率的影响不能笼统说“一定更低”：完全同涨同落时至少一次慢的概率可以更低，但会出现一起变慢；其他依赖关系仍需具体分析。

### 9.3 课件点名的应对方向

| 手段 | 作用 | 补充理解：代价 |
| --- | --- | --- |
| 梳理关键路径 | 减少必须同步等待的工作 | 需要明确哪些结果可以延后 |
| 超时与降级 | 限制等待，提供部分结果 | 可能牺牲功能完整性或数据新鲜度 |
| 对冲请求 | 慢到一定程度后向另一副本发起冗余请求 | 增加负载，必须考虑幂等与取消 |
| 重试预算 | 限制故障时的额外请求 | 需要截止时间、退避和总量约束 |

## 10. 运行时层级：裸机、虚拟机、容器、函数（pp.26–28）

### 10.1 不同层级把哪些工作交给谁

| 层级 | 隔离 / 管理方式 | 课件启动量级 | 主要收益 | 主要成本 |
| --- | --- | --- | --- | --- |
| 裸机 | 物理机器 | 分钟到天 | 直接控制硬件，减少虚拟化开销 | 交付慢、利用率与资源调配问题 |
| 虚拟机 | hypervisor；每台有自己的内核 | 分钟级 | 较强隔离、按需分配机器 | 内核和系统开销 |
| 容器 | namespace + cgroup；共享宿主内核 | 秒级 | 制品化交付、快速起停、较高密度 | 共享内核故障面，隔离边界不同于独立 VM |
| 函数 / FaaS | 平台管理执行环境与伸缩 | 冷启动约 100 ms 到秒级 | 可缩到零，减少实例管理工作 | 冷启动、配额限制、平台依赖 |

课件密度示例为裸机“1”、VM“十”、容器“百”、函数“按需”，用于比较资源颗粒度，不是部署容量承诺。裸机的“分钟到天”也包含资源交付语境，不能与单个进程启动时间混为一谈。

### 10.2 容器就是受到隔离和限制的进程

| 机制 | 回答的问题 | 示例 |
| --- | --- | --- |
| namespace | 它看得见什么？ | PID、网络、挂载点、主机名等视图 |
| cgroup | 这组进程能使用多少资源？ | CPU 配额、内存限制、I/O 控制 |
| 镜像 | 启动时使用什么文件系统内容？ | 上一讲的不可变制品 |

容器里的程序仍由宿主机内核调度，宿主机可以看到相应进程。

| 现象 | 解释与排查方向 |
| --- | --- |
| 平均 CPU 看起来不高，但响应周期性变慢 | 可能在短时间内用完 cgroup CPU 配额，被 throttling；检查节流统计和配额 |
| 宿主机还有内存，容器却 OOMKilled | 可能超过该 cgroup 的限制；核对容器口径的内存使用 |
| JVM 开出远超容器核数的运行时线程 | 检查 JVM 对容器资源的识别及显式配置 |

**补充理解：**fd 上限通常由 `RLIMIT_NOFILE` 等机制管理，不能把所有资源限制都归为 cgroup；镜像也不等于运行时全部文件系统，实际还可叠加可写层和挂载。

### 10.3 函数与冷启动

函数平台管理执行环境，在需要时初始化、运行与回收。冷启动使“启动时间是硬参数”更加直接地反映在请求延迟上。

课件认为，突发、低频、事件驱动的任务适合考虑函数，如发短信、图片处理、报表生成；长连接、长任务、强依赖预热的热路径则需认真评估执行时长、并发、内存与成本限制。

**补充理解：**一次调用不等于一定新建并销毁一个实例。以 AWS Lambda 为例，平台可以保留并复用执行环境，形成 warm start。无状态要求是不能把该环境中的内存或临时文件当作唯一可靠的持久状态。[AWS Lambda 执行环境生命周期](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html)

## 11. 课程实践：单机 Tomcat 的运行时画像（pp.30–33）

### 11.1 参数设定

| 项目 | 本讲设定 |
| --- | --- |
| 应用机器 | 4 核、8 GB，运行一个 Tomcat JVM；MySQL 在另一台机器 |
| Tomcat NIO | `maxThreads = 200`，`maxConnections = 8192`，`acceptCount = 100` |
| JVM | `-Xmx = 4 GB`；线程栈预留示例为 1 MB |
| 数据库连接池 | 10 个连接 |
| 查询请求 | CPU 3 ms + 等数据库 8 ms + 其余 1 ms，基线占线程约 12 ms |
| 提交请求 | CPU 5 ms + 数据库写 10 ms + 随并发变化的行锁等待 |
| 在线人数 | 开放瞬间 2000 人，每人 2～6 条 keep-alive 连接 |

以下先算**查询路径**，并按题设把 8 ms 视为每请求平均连接占用、3 ms 视为 CPU 时间。提交请求需要单独计算。

### 11.2 四个上限，再加内存预算

| 资源 | 计算 | 结果 / 含义 |
| --- | --- | --- |
| CPU | `4 / 0.003` | 约 **1333 QPS** |
| 数据库连接池 | `10 / 0.008` | **1250 QPS** |
| 工作线程 | `200 / 0.012` | 约 **16 667 QPS**，仅为基线线程容量 |
| 客户端连接 / fd | `2000 × 4` | 约 **8000 条连接**，接近 8192；还要核对 fd 限制 |
| 内存 | 课件粗估约 4 GB 堆 + 0.5 GB 堆外 | 仍要给系统、缓存、连接缓冲与波动留余量 |

```text
只比较前三项、保持题设耗时不变时：
查询吞吐理论容量 ≈ min(1333, 1250, 16667) = 1250 QPS
```

**读路径先接近的是连接池与 CPU，不能看到配置中的 200 就断定线程池最先成为瓶颈。**

补充理解：12 ms 是给定负载条件下的基线。连接池开始排队后，线程占用时长会增长；16 667 QPS 不能视作重载时仍固定不变的能力。内存中的 `-Xmx = 4 GB` 也不代表 JVM 当前已经用满 4 GB。

### 11.3 与 800 / 1200 / 1500 QPS 的现象对照

以题设平均需求估算资源利用率：

```text
CPU 利用率 ≈ λ × 0.003 / 4
连接池利用率 ≈ λ × 0.008 / 10
```

| 输入负载 | CPU 需求占比 | 连接池需求占比 | 课件引用的压测现象 |
| --- | --- | --- | --- |
| 800 QPS | 60% | 64% | p95 约 150 ms，正常 |
| 1200 QPS | 90% | 96% | p95 约 1.8 s，排队明显 |
| 1500 QPS | 112.5% | 120% | 超过理论容量，出现严重过载 |

超过 100% 表示需求超出供给，不是资源实际能长期运行在 120% 利用率。接近满载时，突发和服务时间波动会使等待显著增加，所以上限不应直接作为满足延迟目标的运行点。

**补充理解：**这些比例支持“为什么会接近瓶颈”的解释，不能仅凭它们精确推导 p95 = 1.8 s；后者是课件引用的压测结果。实际容量还受网络、GC、系统开销和负载分布等影响。

### 11.4 讨论一：连接池调到 30，接下来是谁到顶？

**课件讲评：**

```text
新的连接池理论容量 = 30 / 0.008 = 3750 QPS
CPU 容量仍约 1333 QPS
```

因此下一项是 CPU。在“不加机器”的条件下，可考虑缓存热数据、减少重复序列化、合并或减少重复查询等，目标是降低每请求的资源需求。

**补充理解：**按这组简化数字，总体理论容量只是从约 1250 提升到 1333 QPS，约增加 6.7%，不是连接池扩三倍、整机吞吐就扩三倍。缓存若只减少数据库等待而不减少应用 CPU，也未必能解除 CPU 瓶颈。

### 11.5 讨论二：写路径为什么线程池会满？加到 2000 有用吗？

**课件讲评：**2000 个提交涌向受热点行锁制约的写路径，等待时间变长。工作线程被等待占住，上游继续积压；增加线程不会消除串行化的更新瓶颈。

应区分三个目标：**减少真正的串行工作、限制同时竞争的数量、控制系统接收的总负载。** 分别考虑事务与数据路径优化、排队、限流，并验证不超选、不重复占位等业务约束。

### 11.6 讨论三：8000 条连接先碰到什么？

**课件讲评：**

1. 若进程 fd 限制仍是 1024，通常先遇到 fd 耗尽；日志和下游连接也要占用额度，不能把全部 1024 都留给客户端。
2. 提高 fd 限额后，8000 条连接已接近 `maxConnections = 8192`。每人若保持 6 条，则是 12 000 条，超过该值。
3. 空闲连接本身不代表大量 CPU 工作，因此 CPU 可能很闲，连接却已经无法继续接入。
4. Nginx 可承担客户端连接，并在合适配置下复用后端连接；它自身也需要足够的 fd、连接和内存预算。

### 11.7 讨论四：换成 Go，或打开虚拟线程，什么变了？

| 项目 | 按课堂控制变量模型，是否改变 |
| --- | --- |
| 大量并发任务的线程成本 | 显著降低，线程这一层限制放宽 |
| 内存基线、栈开销、启动与预热 | 可能改变，需要重新测量 |
| CPU 上限 | 若仍是每请求 3 ms、仍只有 4 核，就仍约 1333 QPS |
| 连接池上限 | 若仍为 10 个连接、每请求占 8 ms，就仍是 1250 QPS |
| 热点行锁 | 若业务与数据库更新方式不变，竞争仍在 |
| 客户端连接 / fd | 不会因换语言自动消失 |

**补充理解：**真实迁移可能改变 CPU 时间和数据库交互方式，因此应重新测量。课堂结论针对“只改变并发实现，其他需求不变”的比较。

## 12. 复习要点与易混淆概念（p.34）

| 容易混淆的概念 | 应怎样区分 |
| --- | --- |
| 利用率 / 饱和 | 资源在忙 / 已有工作等待资源 |
| 在线人数 / 连接数 / 在途请求数 / QPS | 用户规模 / 保持的通道 / 未完成工作 / 每秒处理量 |
| 堆 / RSS / cgroup 内存 | 对象区域上限 / 进程驻留页 / 一组进程及相关内存的计费口径 |
| 连接器 NIO / 业务非阻塞 | 接入连接的方式 / 业务代码等待时是否占用平台线程 |
| 并发 / 并行 | 同时有多项工作在推进 / 同一时刻真正执行多项工作 |
| 线程池满 / 根因在线程池 | 观察到的症状 / 需要证据证明的容量约束 |
| p99 / 最大值 / 平均值 | 分位点 / 最慢样本 / 算术平均 |
| 冷启动 / 每次调用 | 新执行环境初始化 / 可复用已有环境的一次工作 |

可按以下顺序分析一个服务：

```text
区分读写路径与负载形态
  → 量出每请求 CPU、线程占用、连接占用与内存成本
  → 列出 CPU、池、fd、内存及下游限制
  → 算出候选瓶颈，观察实际等待在哪里
  → 做一项有针对性的调整
  → 用成功吞吐、尾延迟、错误率和正确性验证
```

## 13. 思考题、课后任务与参考资料（pp.24、34–35）

### 13.1 思考题 2：「14 个服务，160 毫秒」

课件给出的场景：选课平台拆成 14 个服务，首页 p50 从 180 ms 降到 160 ms；实习生却用 `14 × 20 = 280 ms` 估算。关键是分析调用依赖、同步等待和关键路径，不能按服务总数直接相加。

五幕分别讨论：

1. 估算：响应时间由什么决定。
2. 开放日：缓存与命中率变化。
3. 提交：学生实际在等待什么。
4. 事故：尾延迟与扇出放大。
5. 评审：收益和代价。

**课件交付要求：小组完成，2026-10-15（周四）23:59 截止，10-16 讲评。** 课件指出题面位于课程仓库的 `2026/quiz/Q-2.md` 与 `Q-2.html`；本地仓库当前未包含这两个文件，因此本笔记只记录发布信息，不补造完整题面或答案。

### 13.2 课后思考

1. **给小组项目画运行时画像。**  
   记录运行时与部署方式、线程数、RSS、fd、连接数；测量每请求资源需求，按本讲表格估算谁先到顶，再用压测验证。

2. **计算首页同步下游调用的尾延迟概率。**  
   先识别真正必须等待的 N 个调用，再检查独立性假设，使用 `1 - 0.99^N`。不能从“系统有 14 个服务”直接确定 N。

3. **把 2025 实验 2 的 Go 后端换成 Java，哪些行会变化？**  
   参考思路：线程成本、RSS、启动预热可能变化；CPU 时间要实测；连接池、数据库和锁限制不会仅因语言名称变化就消失。

## 14. 复习自测

1. **CPU 不高，为什么请求仍然很慢？**  
   可能在等锁、数据库连接或 I/O，也可能平均值掩盖了局部 CPU 饱和与配额节流。

2. **`-Xmx = 4 GB`，能否把容器内存限制也设成 4 GB？**  
   不能据此判断足够；还要预算堆外、缓存和相关内核内存，并留余量。

3. **2000 人在线，每人 4 条连接，是否需要 8000 个业务线程？**  
   不需要这样对应。空闲连接占 fd；业务线程取决于请求执行模型与活跃工作量。

4. **200 个线程、平均占用 500 ms，线程容量是多少？**  
   `200 / 0.5 = 400 rps`，且只是线程层的估算。

5. **10 个数据库连接、每请求占用 8 ms，容量是多少？**  
   `10 / 0.008 = 1250 请求/s`，前提是数据库能维持该耗时。

6. **为什么不能把 p95 放进 Little's Law 代替 W？**  
   W 是与 L、λ 边界一致的平均停留时间，p95 是分位点。

7. **连接池从 10 增到 30，本讲读路径会变为 3750 QPS 吗？**  
   不会；按其余需求不变计算，CPU 约 1333 QPS 就先到顶。

8. **为什么增加线程未必缓解抢课超时？**  
   热点更新的串行约束仍在，更多线程可能只增加等待与资源消耗。

9. **虚拟线程能否提高 CPU 密集计算本身的速度？**  
   不能自动提高；它主要改善大量等待任务的并发成本。

10. **12 个独立调用各有 1% 概率超过阈值，至少一个慢的概率是多少？**  
    `1 - 0.99^12 ≈ 11.4%`。

11. **宿主机内存充足，为什么容器仍会 OOMKilled？**  
    可能已超过该 cgroup 的内存限制。

12. **本讲最重要的排障思路是什么？**  
    用资源需求与上限计算候选瓶颈，再用等待位置和运行指标验证；不要把首先出现的症状直接当成根因。
