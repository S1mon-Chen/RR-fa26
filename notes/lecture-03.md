## 1. 本讲主线

Lecture 2 讨论了非功能性需求与软件架构。本讲从前端、后端两个视角，分析同一个平台如何接收用户输入、处理业务、返回结果，并在规模增长时维持体验与一致性。

```text
用户输入
   ↓
前端：接收输入、请求数据、展示结果
   ↓ 网络通信
后端：处理命令与查询、执行业务规则
   ↓
数据：持久化、事件、查询视图
   ↓ 响应或推送
前端更新界面
```

本讲贯穿的判断标准是：**一项技术解决了什么问题，又增加了什么成本？**

| 部分 | 核心问题 | 关键词 |
| --- | --- | --- |
| 前端定位 | 前端与后端如何分工？ | 用户接口、展示与计算解耦 |
| 前端常见问题 | 如何覆盖多端、观察故障并缩短等待？ | 跨平台、可观测、响应时间、通信协议 |
| 前端趋势 | 界面如何开发、运行和验证？ | AI、渲染策略、工具链、组件与体验质量 |
| 后端定位 | 如何处理请求并适应云环境？ | 命令与查询、持久化、云原生、松耦合 |
| 后端模式 | 服务拆分后如何管理事务和查询？ | Saga、Event Sourcing、Outbox、CQRS |

## 2. 重新认识前端（pp.5–10）

### 2.1 前端的三个职责

**前端是用户与后端之间的接口（Interface）。**

1. **接收用户输入**：键盘、鼠标、触控、声音、视觉，以及 VR/AR 等空间交互。输入方式不断扩展，职责不变。
2. **向后端请求数据**：包括静态资源请求和动态数据请求。
3. **展示返回结果**：将数据组织成用户能够理解和操作的界面。

**补充理解：**静态资源通常包括脚本、样式、图片等，可由静态资源服务器、对象存储等承载，并通过 CDN 分发。动态请求则通常需要根据用户、参数和业务状态计算结果。这是对 p.7“静态资源通常都放在哪里”的参考回答。

### 2.2 解耦的核心：展示与计算分工

p.8 强调，前后端解耦的核心是**展示与计算的解耦**。前端负责交互与展示，后端承载业务处理和数据服务，从而支持多种终端复用平台能力。

**补充理解：**这是一种职责划分，不意味着前端完全不计算，也不意味着前后端没有依赖。端上仍可执行表单校验和界面状态计算；双方仍需约定接口、数据结构和错误语义。关键业务校验与权限控制不能仅依赖前端。

### 2.3 部署图与运行时视角

| 视角 | 课件结构 | 阅读重点 |
| --- | --- | --- |
| 部署图（p.9；p.38 再次出现） | 接入层、路由与负载均衡、应用层、数据层、基础设施 | 请求经过哪些组件，组件如何部署与协作 |
| 运行时分层（p.10；p.39 再次出现） | 用户层、应用层、平台服务层、云技术层、资源层 | 终端如何使用业务与平台能力，底层资源如何支撑上层 |

部署图列举 CDN、反向代理缓存、Nginx、网关、负载均衡、业务组件、消息队列、配置中心、数据库、Redis、日志平台等。监控、链路追踪和服务治理贯穿多个层次。

运行时图以选课平台为例：浏览器、App、小程序等终端使用课程浏览、选课、课表查询和智能问答；下层提供权限、事务、搜索、消息等能力，最终由计算、存储、网络和 GPU 等资源支撑。

## 3. 前端常见问题（pp.12–19）

### 3.1 跨平台：复用与原生能力的取舍（pp.12–13）

同一产品可能需要覆盖 Android、iOS、鸿蒙、不同浏览器、桌面系统以及 XR 等新终端。平台语言、UI 框架、系统能力、屏幕与输入方式、审核发布机制都可能不同。

| 路线 | 课件举例 | 关注点 |
| --- | --- | --- |
| Web 优先 | 响应式布局、PWA | 跨设备使用和布局适配 |
| 跨平台框架 | Flutter、React Native | 共享实现与平台能力之间的取舍 |
| 容器方案 | 小程序、混合应用 WebView | 在宿主提供的能力与约束内运行 |
| 业务能力复用 | 业务逻辑下沉后端 | 减少各端重复实现业务规则 |

**核心权衡：开发与维护成本 ↔ 性能与原生能力。** 复用代码并不意味着可以省略各平台的适配与验证。

### 3.2 前端可观测：如何看到用户设备上的故障（pp.14–15）

前端运行环境不受开发者完全控制，设备、系统、浏览器和网络差异使线上问题难以复现。

| 环节 | 课件内容 | 要解决的问题 |
| --- | --- | --- |
| 采集 | Crash log、调试埋点、行为埋点、性能数据 | 发生了什么，用户经历了什么 |
| 组织 | 统一 SDK，按错误、性能、行为分类 | 避免采集方式随业务无序膨胀 |
| 传输 | 采样、本地缓存、打包、压缩、批量上报 | 控制流量、电量和运行开销 |
| 关闭页面时上报 | `sendBeacon` 作为兜底 | 减少页面退出导致的数据丢失 |
| 定位与隐私 | 数据脱敏，关联版本号 | 保护用户数据并定位具体版本的问题 |

**补充理解：**兜底上报不能理解为所有崩溃或断网场景都保证送达。可观测方案本身也有开销，需要平衡数据价值与采集成本。

### 3.3 响应时间：先拆解，再优化（pp.16–17）

课件用以下简化模型分析请求耗时：

```text
响应时间 ≈ 建立连接的时间 + 传输数据的时间 + 后端处理的时间
```

| 耗时来源 | 问题原因 | 课件对策 |
| --- | --- | --- |
| 建立连接 | 连接与握手开销 | 连接复用、HTTP/2、HTTP/3 |
| 传输数据 | 内容大、距离远、带宽受限 | 压缩、缓存、按需加载、CDN 与边缘节点 |
| 后端处理 | 计算、排队和资源竞争 | 缓存、异步处理、水平扩展 |

用户规模增大后，服务端排队和带宽限制都可能导致响应时间增长。应先通过浏览器 Network 面板等工具拆解耗时，再选择优化措施。

**补充理解：**该模型便于分析，并非完整的页面体验模型；页面还可能有脚本执行、布局与绘制等开销。课件将业务处理时间归入动态请求，但静态资源请求也可能经过服务器或缓存节点处理。

### 3.4 通信协议为何演进（pp.18–19）

| 技术 | 课件强调的能力 | 对应问题 |
| --- | --- | --- |
| HTTP/2 | 多路复用、HPACK 头部压缩 | 多请求的排队和重复头部开销 |
| HTTP/3 / QUIC | 基于 UDP，支持连接迁移 | TCP 连接上的丢包阻塞、移动网络切换 |
| SSE | 服务端向客户端持续发送事件 | 通知和流式结果 |
| WebSocket | 双向实时通信 | 双方都需持续发送数据 |

p.18 说明，HTTP/2 Server Push 已被 Chrome 移除，并提及 103 Early Hints。复习时应区分：**HTTP/2 Server Push 与 SSE、WebSocket 的业务消息推送不是同一个机制。**

**补充理解：**p.19 对 HTTP/1.1 的描述是教学简化，重点是其缺少 HTTP/2 式的多路复用；不能据此理解成浏览器总共只能发一个请求。协议选型要结合数据方向、实时性与基础设施支持。

## 4. 前端发展趋势：三个主题、八个话题（pp.21–29）

### 4.1 AI 辅助开发与 AI 应用交互（pp.22–23）

**AI 辅助开发的流程：**

```text
明确页面目标、接口契约与验收条件
    → AI 生成或修改组件、补充测试
    → 在真实浏览器验证交互、异常与可访问性
    → 开发者审查业务规则、权限和维护成本
    → 交付
```

验证失败时，将失败证据反馈给 AI，继续修改。开发者仍需读懂代码、提出约束并用测试验证结果。

**AI 产品界面以智能选课助手为例：**输入偏好 → 逐步展示建议与依据 → 用课程卡片呈现结构化结果 → 确认后提交选课。

界面需要区分等待、生成、执行与失败，提供取消、重试和恢复能力。写操作执行前应展示范围并确认；鉴权、参数校验与密钥管理保留在服务端。课件提出以流式传输配合预定义组件，控制内容与操作边界。

### 4.2 浏览器与服务端协同渲染（p.24）

| 策略 | 生成界面的主要时机与位置 | 课件适用场景 | 权衡 |
| --- | --- | --- | --- |
| SSG：静态生成 | 发布前，在构建时生成 HTML | 文档、课程介绍等稳定内容 | 更新时机、缓存失效 |
| SSR：服务端渲染 | 请求到达时，由服务端或边缘节点生成 HTML | 需要首屏内容的动态页面 | 服务端延迟、运行成本 |
| CSR：客户端渲染 | 浏览器运行脚本生成界面 | 管理后台、复杂编辑器 | 脚本体积、浏览器执行成本 |

同一应用可组合不同策略。**RSC（React Server Components）按组件划分执行位置，可与 SSR、SSG 配合**，不能简单看作与这三者互斥的第四选项。

渲染决策也包含缓存策略与用户数据隔离：不同用户的数据不能因错误共享缓存而混在一起。

### 4.3 浏览器原生能力（p.25）

- **现代 CSS**：容器查询让组件按容器空间适配；`:has()` 表达条件样式，减少部分额外脚本。
- **Baseline**：结合特性支持状态和真实用户设备确定采用范围，并保留旧环境的可用体验。
- **WebAssembly / WebGPU**：扩展计算、图形与部分端侧 AI 能力；检测目标环境支持情况，并提供回退。

采用依据是设备覆盖、下载成本与真实运行效果。

### 4.4 微前端与 API 的选型边界（p.26）

| 设计维度 | 课件给课程项目的基础选择 | 何时进一步评估 |
| --- | --- | --- |
| 应用拆分 | 单一应用内按业务模块组织 | 多团队需独立交付时考虑微前端，关注共享依赖和故障隔离 |
| 接口契约 | REST + OpenAPI，明确数据结构与错误响应 | 多端需灵活聚合时考虑 GraphQL，关注查询成本、N+1 和缓存 |
| 页面数据聚合 | BFF 可按页面组织后端数据 | 可与 REST 或 GraphQL 配合 |

**补充理解：**BFF 即 Backend for Frontend，面向特定前端提供适配或聚合接口。组件化、微前端、接口协议与 BFF 解决的是不同层面的问题。

### 4.5 编译优化与工具链（p.27）

课件以 React Compiler 1.0、Vite 8 + Rolldown 为例：前者通过自动记忆化减少重复计算，后者采用 Rust 打包器统一相关打包实现。

关注点是：升级后检查插件兼容、构建结果、构建耗时，并通过回归测试和真实交互测量验证效果。基础能力仍包括 TypeScript、模块化、自动化测试与性能测量。

### 4.6 设计系统与组件工程（p.28）

可复用组件需要共同定义：

| 资产 | 内容 |
| --- | --- |
| 设计令牌 Design Tokens | 颜色、间距、字体等规则 |
| 组件契约 | 输入、事件与状态 |
| 组件文档 | 示例和使用限制 |
| 版本策略 | 升级与兼容规则 |

“选课按钮”不只有外观，还包括默认、禁用、提交中与失败状态。交互测试验证提交和错误恢复，视觉回归发现样式变化，键盘与读屏检查验证可访问性。课件还以 DTCG 设计令牌规范说明工具之间共享设计资产的方向。

### 4.7 体验质量与线上可观测（p.29）

| 指标 | 含义 | 课件给出的良好阈值 |
| --- | --- | --- |
| LCP：Largest Contentful Paint | 最大内容绘制，反映加载体验 | ≤ 2.5 秒 |
| INP：Interaction to Next Paint | 交互到下一次绘制，反映交互响应 | ≤ 200 毫秒 |
| CLS：Cumulative Layout Shift | 累积布局偏移，反映视觉稳定性 | ≤ 0.1 |

阈值按**真实用户访问的第 75 百分位**评估，移动端和桌面端分开统计。不能用一次本地测试或所有请求的平均值代替这一口径。

上线后关联版本、错误和接口请求定位问题，用灰度发布验证修复并准备回滚。自动化测试、可访问性与依赖安全共同构成交付基线。

## 5. 重新认识后端（pp.34–39）

### 5.1 后端的职责

后端接收请求，按业务逻辑处理数据，完成必要的持久化，并返回结果。

| 请求类型 | 作用 | 例子（补充理解） |
| --- | --- | --- |
| 命令 Command | 改变业务状态，典型操作为增、删、改 | 选课、退课、扣减名额 |
| 查询 Query | 读取数据，不改变所查询的业务状态 | 查询课表、查询余量 |

查询又分为：可以直接通过查询语言完成的简单查询，以及需要专门数据处理程序的复杂查询。

持久化可以使用文件系统或数据库。课件提示“数据库不仅可以用作持久化”；**补充理解：**它也可承担索引查询、聚合与约束检查等工作。

### 5.2 Pull 与 Push：如何返回或通知结果（p.37）

| 方式 | 工作机制 | 适用场景 | 主要代价 |
| --- | --- | --- | --- |
| 短轮询 | 客户端定时请求 | 实时性要求低 | 空请求多，延迟受轮询间隔影响 |
| 长轮询 | 服务端挂起请求，有数据才响应 | 兼容老旧环境的通知 | 长时间占用连接，并发管理压力 |
| SSE | 在 HTTP 长连接上持续发送事件 | 通知、行情、AI 流式输出 | 推送方向为服务端到客户端 |
| WebSocket | 建立全双工连接 | 聊天、协同编辑、在线游戏 | 连接状态、负载均衡和扩容更复杂 |
| Webhook | 事件发生时回调接收方 URL | 支付结果、CI 通知等系统集成 | 接收端可达性、验签、重试 |

**补充理解：**SSE 和 WebSocket 的连接仍由客户端建立；“主动推送”指连接建立后服务端不必等客户端每次询问才发送新数据。Webhook 通常是系统之间的回调接口。

## 6. 云原生与可扩展性（pp.40–42）

### 6.1 从技术清单转向工程实践

课件对 CNCF 云原生定义 v1.0 与 v1.1 的比较强调：

- 视角从云原生“技术”转向云原生“实践”，从应用扩展到工作负载。
- 在公有云、私有云、混合云中，以可编程、可重复的方式满足规模化需求。
- 核心仍是松耦合与自动化，同时强调互操作、安全、弹性、可管理、可持续和可观测。
- 技术包括容器、服务网格、微服务、不可变基础设施、声明式 API，以及多租户、Serverless 等；清单并非穷尽。

对后端而言，重点是**可扩展、松耦合与性价比**，并关注安全及资源效率。

### 6.2 Amdahl 定律：为什么加机器的收益递减（p.42）

设必须串行执行的比例为 `s`，处理器数量为 `N`，理想加速比为：

```text
S(N) = 1 / [s + (1 - s) / N]

当 N → ∞ 且 s > 0 时，S(N) → 1 / s
```

| 串行比例 s | 理论加速上限 |
| --- | --- |
| 5% | 20 倍 |
| 50% | 2 倍 |

**结论：只增加资源，无法突破串行部分形成的上限。** 减少共享、串行环节和耦合，才可能改善可扩展性及性价比。

**补充理解：**这是固定工作量下的理想模型，尚未计入通信和协调开销，不能直接当作真实分布式服务的扩容预测公式。

## 7. 复杂系统的排障方法论（p.44）

课件针对多层复杂系统提出：

```text
遇到问题
  → 向下游询问是否能够解决
  → 若不能，判断本层能否解决
      → 能：优化，或增加资源
      → 不能：通知上游，由上游调整
```

**补充理解：**“上下游”是相对调用关系。例如应用访问数据库时，数据库是下游；前端调用应用接口时，前端是上游。应结合链路追踪与各层指标识别瓶颈，判断问题能在哪一层有效解决。

参考思路：选课接口慢 → 分辨网络、应用与数据库耗时 → 判断下游查询或资源是否可改进 → 再评估本层缓存、并发控制和扩容 → 必要时由上游调整请求频率与交互方式。

## 8. 后端框架与运行效率（pp.46–47）

课件列举 Spring Boot + Spring Cloud、Quarkus、Micronaut、Dropwizard 和 Vert.x，没有要求所有项目采用同一个框架。

p.47 用 Quarkus 官方图比较内存占用与“启动 + 首次响应”时间：

| 测试项 | Quarkus 原生镜像 | Quarkus JVM | 图中的传统云原生技术栈 |
| --- | --- | --- | --- |
| REST：RSS 内存 | 12 MB | 73 MB | 136 MB |
| REST + CRUD：RSS 内存 | 28 MB | 145 MB | 209 MB |
| REST：启动 + 首次响应 | 0.016 秒 | 0.943 秒 | 4.3 秒 |
| REST + CRUD：启动 + 首次响应 | 0.042 秒 | 2.033 秒 | 9.5 秒 |

以上为**课件图中单核机器测试示例**，不是通用性能保证。它说明启动速度和内存占用会影响部署密度及弹性场景的成本；不能据此推断所有业务的稳态吞吐表现。

## 9. Saga：跨服务事务（pp.48–53）

### 9.1 为什么需要 Saga

服务各自管理数据后，一次业务操作可能跨越多个本地事务。p.48 列出 2PC、3PC、TCC 等方案，再引入 Saga；p.49 展示把跨服务事务拆成由消息或事件串联的本地事务。

**Saga = 一串本地事务 + 失败时的补偿操作。**

课件采用异步消息方式，关注最终一致性，而非让整个业务过程像单个数据库事务一样瞬间提交。

**补充理解：**补偿是显式业务操作，不是数据库自动回滚；Saga 也不自动提供跨服务隔离。已提交的中间状态可能被其他操作看到，需要结合业务规则处理并发。[参考：Saga 模式](https://microservices.io/patterns/data/saga.html)。

### 9.2 两种协调方式

核心区别：**谁决定下一步做什么？**

| 维度 | Choreography：协同式 | Orchestration：编排式 |
| --- | --- | --- |
| 决策位置 | 各服务订阅事件并自行响应 | 协调者按状态机发出命令 |
| 流程组织 | 分散在事件链中 | 集中定义和跟踪 |
| 失败处理 | 服务响应失败事件并执行补偿 | 协调者触发相应补偿 |
| 主要困难 | 事件链增长后难以理解和排查 | 协调者的可用性、性能与依赖关系 |
| 课件选型建议 | 服务少、流程简单 | 服务多、流程复杂、需要集中监控 |

**p.50 协同式示例：**订单服务创建订单并发出事件 → 客户服务尝试预留信用额度 → 发布成功或超额事件 → 订单服务据此处理订单。

**p.51 编排式示例：**创建订单 Saga → 协调者发出预留额度命令 → 客户服务处理并回复 → 协调者决定订单后续状态。

这里的“编排”是业务流程编排，不是 Kubernetes 的容器编排。同一系统可混用两种协调方式。

### 9.3 共同工程要求

课件强调可靠消息、失败处理与补偿。**补充理解：**服务之间没有直接调用，也仍然依赖事件契约；所谓松耦合不等于没有耦合。协调者的风险也需要通过具体实现评估。

## 10. Event Sourcing 与 Transactional Outbox（pp.54–55）

### 10.1 双写问题

课件提出：**不使用 2PC 时，如何可靠地、原子性地更新数据库并发送消息，同时保证消息时序？**

```text
先更新数据库，再发消息：中间崩溃 → 数据已变，消息没发
先发消息，再提交数据库：提交失败 → 消息已发，数据没变
```

课件列出 Event Sourcing 与 Transactional Outbox 两条路线。

### 10.2 Event Sourcing：以事件记录状态演变

p.55 从“订单表保存当前状态”切换到“保存订单事件序列”，例如创建、批准、发货。

| 术语 | 含义（补充理解） |
| --- | --- |
| Event Store | 持久保存业务事件，事件序列构成状态依据 |
| Event Broker | 将事件分发给订阅者 |
| Replay | 按序重放事件，重建状态或视图 |

**补充理解：**状态变化本身以追加事件的方式持久化，从而减少“状态更新”和“事件记录”分离带来的双写问题。事件对外分发仍需可靠机制；只使用消息队列不等于事件溯源。[参考：Event Sourcing 模式](https://microservices.io/patterns/data/event-sourcing.html)。

### 10.3 Transactional Outbox：把发送意图与数据一起提交

课件列出该模式但未展开，以下为**补充理解**：

```text
一个本地数据库事务
  ├─ 更新业务数据
  └─ 写入 Outbox 待发送消息
         ↓ 事务提交后
消息转发器读取 Outbox → 发送到消息系统 → 消费者处理
```

原子提交的是业务数据与待发送消息记录，消息实际发送发生在之后。转发过程可能重复发送，因此消费者需要幂等处理；消息顺序也需要明确保证。[参考：Transactional Outbox 模式](https://microservices.io/patterns/data/transactional-outbox.html)。

| 对比 | Event Sourcing | Transactional Outbox |
| --- | --- | --- |
| 保存状态的方式 | 以业务事件历史为依据 | 通常保留当前状态表，额外记录待发消息 |
| 主要改变 | 业务状态的建模与存储方式 | 数据更新与消息发送的衔接方式 |
| 额外成本（补充理解） | 事件演进、重放、视图维护 | 转发器、消息积压和去重 |

## 11. CQRS：跨服务查询（p.56）

**CQRS = Command Query Responsibility Segregation，命令查询职责分离。**

课件场景是：多个服务分别保存数据，但用户需要一个跨服务的查询结果。

p.56 中，订单、厨房、配送、账务服务发布事件，订单历史服务消费这些事件，维护专门的订单历史查询数据库。

```text
多个业务服务 → 业务事件 → 事件处理器 → 查询视图
                                          ↑
                                      用户查询
```

**补充理解：**读模型可以提前聚合查询所需数据，减少查询时跨多个服务取数；代价是视图更新和一致性管理。异步更新意味着查询结果可能暂时落后于写入。CQRS 与事件溯源可以配合，但并不互为前提。[参考：CQRS 模式](https://microservices.io/patterns/data/cqrs.html)。

### 三类模式不要混淆

| 模式 | 首先回答的问题 |
| --- | --- |
| Saga | 一次业务跨多个服务时，如何推进流程并处理失败？ |
| Event Sourcing / Outbox | 如何持久记录状态变化或发送意图，支撑可靠事件发布？ |
| CQRS | 如何分离写入与读取职责，并组织查询模型？ |

它们可组合使用，但各自解决的问题不同。

## 12. 后端趋势（p.57）

| 方向 | 课件举例 | 与本讲的联系 |
| --- | --- | --- |
| 更轻的运行时 | 虚拟线程、GraalVM 原生镜像 | 并发能力、启动时间和内存成本 |
| Serverless 与按需伸缩 | 按用量计费、自动扩缩 | 云原生与资源效率 |
| 持久化执行 | Temporal 等工作流引擎保存执行状态 | Saga 编排与失败恢复 |
| 可观测标准化 | OpenTelemetry | 统一追踪、指标与日志采集 |
| 面向 AI 的后端 | RAG、Agent、工具调用、MCP | 支撑 AI 产品的交互与执行 |

**补充理解：**表中技术不意味着采用后同时获得所有收益。例如虚拟线程与原生镜像的作用不同；本节重点是辨认问题、成本与适用条件。

## 13. 课程实践：选课平台（p.58）

### 13.1 课件场景

选课高峰、名额有限，选课成功后需要通知学生。

课件示意选课服务 → 名额服务 → 通知服务 → 课表查询视图；名额不足时，执行补偿并取消选课记录。

| 需求 | 对应设计 |
| --- | --- |
| 选课、退课 | 命令，执行业务事务并校验名额 |
| 课表、余量展示 | 查询，使用读模型，可结合缓存 |
| 跨服务执行 | Saga 串联本地事务，处理失败补偿 |
| 高峰流量 | 水平扩展、消息队列削峰 |
| 慢请求定位 | 逐层排查，结合链路追踪 |

### 13.2 参考思路：把前后端串起来

以下是根据本讲概念整理的解释性流程，不是课件指定的唯一实现：

1. 前端提交选课命令，并展示“处理中”。
2. 后端校验请求并创建待确认记录，可靠地记录后续事件。
3. 名额服务在本地事务中检查并扣减名额；失败时通过 Saga 触发选课记录的补偿。
4. 成功状态通过事件更新查询视图，并触发通知。
5. 前端通过查询或推送获知最终结果，更新课表与按钮状态。

**补充理解：**缓存或读模型中的余量用于展示，最终是否能选上仍由命令处理路径校验。异步处理时，“请求已受理”不能直接显示成“选课成功”；这正是前端状态设计与后端一致性设计的衔接点。

课件没有给出本讲独立作业的提交格式、截止时间或强制技术清单。

## 14. 复习自测

1. **前端的三个职责是什么？**  
   接收输入、请求数据、展示结果；核心分工是展示与计算解耦。

2. **跨平台开发的主要取舍是什么？**  
   开发与维护成本，以及性能和原生能力；还要验证各端体验与兼容性。

3. **前端可观测为什么需要采样、缓存和批量上报？**  
   用户设备与网络差异大，采集也消耗资源；需要兼顾定位价值、数据送达与开销。

4. **请求响应时间可以先拆成哪三部分？**  
   建立连接、传输数据、后端处理；页面整体体验还包含浏览器执行和渲染。

5. **SSE、WebSocket、Webhook 如何区分？**  
   SSE 适合服务端单向流式推送；WebSocket 支持双向实时通信；Webhook 是事件触发的系统间回调。

6. **SSG、SSR、CSR 的关键差异是什么？**  
   分别在构建时、请求时和浏览器运行时生成界面；取舍包括更新、首屏、服务端成本和脚本成本。

7. **体验质量的三个指标及课件阈值是什么？**  
   LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1；按真实用户访问 p75、移动与桌面分别评估。

8. **命令和查询如何区分？**  
   命令改变业务状态，查询读取业务数据；选课是命令，查看课表是查询。

9. **为什么加机器不一定有效？**  
   串行环节限制加速比，还存在通信与协调开销；需减少瓶颈和耦合。

10. **Saga 两种协调方式的本质区别是什么？**  
    协同式由服务根据事件自行决定下一步；编排式由协调者按状态机推进。

11. **为什么 Saga 补偿不是数据库回滚？**  
    之前的本地事务已经提交，补偿是新的业务操作，需要显式设计。

12. **Outbox 原子提交的到底是什么？**  
    同一个本地事务中的业务数据与待发送消息记录；实际消息发送由后续转发器完成。

13. **为什么采用 CQRS 后仍可能读到旧数据？**  
    读模型可能通过异步事件更新，写入完成与查询视图更新之间存在延迟。

14. **选课平台中三个模式如何配合？**  
    Saga 组织跨服务流程与补偿；事件溯源或 Outbox 支撑可靠事件；CQRS 组织课表等查询视图。

15. **如何判断是否采用一种新技术？**  
    先明确要解决的问题，再评估收益、运行与治理成本，并通过测量和验证作决定。
