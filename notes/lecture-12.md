## 1. 本讲主线：从管资源到管运行中的应用（pp.3、29）

[Lecture 11](/Users/xlchen/RR-fa26/notes/lecture-11.md) 完成弹性方案，模块 6 回答资源怎样分、放在哪儿、何时增减。本讲继续追问：**系统坏了或慢了，应当换硬件、加资源，还是修改软件？谁来处理，收益和代价是什么？**

两个引例贯穿全讲：

- **可靠性问题：**4 台应用服务器加 Nginx，一学期发生磁盘写满、内核 panic、两次 OOM、网卡故障，均被冗余吸收；一次健康检查参数修改，却造成 3 分钟全站 502。“机器出问题”是否就等于“硬件坏了”？
- **性能问题：**MySQL 写路径受 fsync 限制，简化上限约 250 TPS，而持续需求为 300 TPS。应当换更快的盘、调组提交，还是把名额扣减移到 Redis？

判断一个方案时，需要同时回答：

| 问题 | 要交代的内容 |
| --- | --- |
| 问题在哪里？ | 故障证据、饱和资源、用户受到的影响 |
| 由谁解决？ | 基础设施运维、应用运维、开发或云平台的责任 |
| 能改善多少？ | 性能上限、容量余量、故障后的剩余能力 |
| 何时能用？ | 交付、开发、验证、上线和回退所需时间 |
| 总共花多少？ | 一次性人力、持续资源费用、后续维护成本 |
| 带来什么新问题？ | 新瓶颈、复制与一致性、相关故障、额外观测需求 |

## 2. 运维的两类对象与云上分工（pp.5–6）

### 2.1 基础设施运维与应用运维

| 维度 | 基础设施运维 | 应用运维 |
| --- | --- | --- |
| 对象 | 机房、服务器、网络、存储、操作系统、虚拟化与容器平台 | 运行中的应用实例、版本、配置、依赖、数据 |
| 生命周期尺度 | 通常以年计：采购、上架、运行、维修、下线 | 变化更频繁，可能每天多次发布 |
| 典型工作 | 容量交付、巡检、固件与内核补丁、硬件维修 | 发布、配置、伸缩、值班、事故处置 |
| 主要指标 | SMART、内存纠错计数、温度、USE 资源指标 | SLO、RED、业务指标 |
| 变更方式 | 计划维护窗口、逐台进行 | 持续变更、分批放量 |
| 本案例 | 云主机、云盘、弹性公网 IP、网络 | Nginx 配置、Tomcat 版本与配置、MySQL 数据与参数 |

这里区分的是**管理对象与责任**，不是把团队机械分成两个部门。DevOps 下开发、平台与 SRE 可以共同承担这些工作，但底层容量交付与应用行为管理仍是不同的问题。

### 2.2 上云以后，应用仍需管理三个接口

课件以 ECS 的责任共担为例：云平台负责物理服务器、网络与存储等基础设施；租户负责实例内部的操作系统、应用、数据保护与访问控制。具体边界随所购买的服务变化，不能把 ECS 的边界直接套到托管数据库等服务。

| 接口 | 平台提供或通知什么 | 应用侧需要做什么 |
| --- | --- | --- |
| 计划事件 | 重部署、重启、本地盘换盘、系统维护等 | 检查影响，先摘流与排空，安排低谷窗口，确认数据恢复路径 |
| 容量提前量 | 物理机交付可能以周计；云主机通常更快，L-11 按加节点约 4 min 估算 | 提前申请与预热，把交付时间计入控制环 |
| 可靠性承诺 | 某些云盘由平台提供冗余与持久性；本地盘、单副本产品的边界不同 | 明确哪些数据必须自行复制、备份、恢复 |

**上云改变了硬件由谁维护，没有消除应用与基础设施之间的协调。**课件建议开放日前后不安排可自主选择时间的维护；这不代表租户可以阻止所有平台事件或真实故障。

## 3. 硬件不只会停，还会慢、会算错（p.8）

| 故障形态 | 含义与例子 | 简单存活检查的局限 | 需要补充的观测 |
| --- | --- | --- | --- |
| 停止，fail-stop | 宕机、内核 panic、网卡断开，无法继续服务 | 通常能通过连接失败或超时发现，但有检测延迟 | 存活探测、系统日志、平台事件 |
| 变慢，fail-slow | 盘、SSD、CPU、内存、网络仍工作，但部分操作明显变慢 | 探测可能仍在超时内成功，或未经过受影响路径 | 分实例延迟、错误与重传、端到端探测 |
| 静默出错，silent corruption | 内存位翻转、CPU 计算结果错误却未报错 | 返回成功不能证明结果正确 | 校验和、业务不变量、独立重复计算等 |

课件引用的 *Fail-Slow at Scale* 收集了 12 家机构的 101 起事件，表明多类硬件都可能出现性能故障，且影响会沿依赖链传播。[原始研究介绍](https://www.usenix.org/publications/login/summer2018/gunawi)

**灰色故障（gray failure）的核心是“差异可观测性”：组件内部的检测认为正常，使用它的应用已经感受到异常。**它描述的是观测之间的差异，不等于所有故障都是硬件问题，也不只是“速度慢”的同义词。[Huang 等：Gray Failure](https://www.microsoft.com/en-us/research/wp-content/uploads/2017/06/paper-1.pdf)

课件的“健康检查看不见变慢和算错”针对的是只检查存活、覆盖有限的探测。带业务语义、延迟阈值或结果校验的检查可以发现一部分问题，但不能因一个 `/health` 返回 200 就认为用户体验正常。

## 4. 规模怎样把小概率故障变成日常（p.9）

### 4.1 硬盘故障频率的估算

Backblaze 的 2025 年报告给出全年 AFR（年化故障率）为 **1.36%**，年度分析覆盖 **344,196 块盘**；2024 年对应 AFR 为 1.55%。这是特定盘群的统计，不能视为任意型号、盘龄与环境的保证。[Backblaze 2025 年报告](https://www.backblaze.com/blog/backblaze-drive-stats-for-2025/)

按课件把盘群规模视为固定、用同一故障率近似：

```text
每年预期故障次数 ≈ 盘数 N × 年化故障率 r
盘群平均事件间隔 ≈ 1 / (N × r) 年
每天预期故障次数 ≈ N × r / 365
```

| 盘数 | 预期故障频率 | 课件的直观表述 |
| --- | --- | --- |
| 10 | `10 × 0.0136 = 0.136 次/年` | 约 7.4 年遇到一次 |
| 1000 | `13.6 次/年`；`365 / 13.6 ≈ 26.8 天/次` | 约 27 天一次 |
| 344,000 | `344000 × 0.0136 / 365 ≈ 12.8 次/天` | 每天约 13 块 |

这里算的是**整个盘群的平均事件频率**，不是单盘寿命，也不是预言哪天会坏盘。课件的“每天约 13 块”是恒定规模近似，不等于报告实际全年故障数除以 365；真实盘数会随时间变化，AFR 按运行时间年化。

### 4.2 内存与 CPU 也有错误

- 课件引用 2009 年 DRAM 研究：样本中每年超过 8% 的 DIMM 出现错误。按同一比例估算，1000 条内存中每年受影响的数量为 80 条以上量级；**“出现错误”不等于“整条报废”，也不等于已产生不可纠正的数据损坏。**这是研究样本与时期的结果。[DRAM Errors in the Wild](https://research.google/pubs/dram-errors-in-the-wild-a-large-scale-field-study/)
- CPU 也可能静默算错。课件列举 Google 与 Meta 在大规模机器群中发现异常 CPU 的研究，用于说明“进程没崩溃”不能证明计算正确，不应据此给任意 CPU 型号套一个通用故障率。

规模扩大后，靠人逐次发现、逐台人工恢复难以持续，需要软件自动检测、隔离、切换和补建。

## 5. 硬件自身的防护及其边界（p.10）

| 防护 | 主要作用 | 覆盖不了什么 | 代价 |
| --- | --- | --- | --- |
| ECC 内存 | 检测、纠正其编码能力范围内的位错误，并提供计数 | 超出纠错能力的错误、CPU 逻辑算错等 | 平台支持与硬件成本 |
| 有冗余的 RAID | 在特定盘故障数内继续保留数据 | 误删、软件写错、超出冗余能力的故障、部分控制器或共因故障 | 容量开销、重建时的负载和性能下降 |
| 双电源、UPS | 抵御部分电源或供电中断 | 共用上游电源故障、超过续航的停电、更大故障域失效 | 设备、机房与维护投入 |
| 带掉电保护的写缓存 | 在可靠兑现持久化语义的前提下，更快确认写入 | 保护部件自身失效或实现缺陷 | 设备成本、电池或电容等维护 |

**补充理解：**不能笼统说“RAID 能坏一块盘”。RAID 0 没有冗余；RAID 5 通常可容忍一块盘失效，RAID 6 可容忍两块。重建期间能否再承受故障，要看剩余冗余，不能对所有级别一概而论。

这些机制提高了局部可靠性，但不替代跨故障域设计、应用校验或备份。尤其是**副本与 RAID 会把错误写入一起保存下来，备份承担的是另一种恢复需求**。

## 6. 可靠性的两条路线与冗余的新问题（pp.12、14–15）

### 6.1 提高单机可靠性，或让系统吸收单机故障

| 比较 | 高可靠硬件 | 普通硬件加软件冗余 |
| --- | --- | --- |
| 主要思路 | 提高单机 MTTF，减少故障 | 接受部件会坏，快速隔离与恢复服务 |
| 例子 | 高可靠服务器、双控存储阵列、RAID | 多实例、健康检查、复制与自动切换 |
| 收益 | 许多场景下应用改动少 | 容量易扩展，一台故障可以不导致全站停服 |
| 代价 | 单机昂贵，规格有上限，仍可能故障 | 复制、一致性、切换、观测与运维更复杂 |

课件引用 GFS 的设计出发点：大规模系统应把部件故障当作日常条件，故障来源既包括硬件，也包括应用缺陷、操作系统缺陷和人为失误。

回顾 L-08 的简化可用性模型：

```text
A = MTTF / (MTTF + MTTR)

MTTF：平均正常运行至故障的时间
MTTR：与该可用性口径一致的平均恢复时间
```

用户关心服务恢复，而不一定要等坏机器修好。本例在约 3 s 内摘除故障实例，让流量转给幸存实例；修机器可以随后完成。**服务恢复时间、机器修复时间、冗余补齐时间是三个不同的时间。**

这个收益要求故障后还有足够容量、状态与依赖可用；摘流也不能撤销检测前已经失败的请求。

### 6.2 多副本为什么会一起坏

| 原因 | 典型问题 |
| --- | --- |
| 共享判定者 | 同一套错误健康检查把所有后端都摘除 |
| 共享依赖 | 所有应用副本同时依赖一个失效的数据库或网络 |
| 同一次变更 | 错误版本、配置或证书同时推到所有实例 |
| 共同故障域 | 同一宿主机、机架、可用区的故障同时影响多个副本 |
| 冗余机制自身缺陷 | 切换脚本出错、虚拟 IP 漂移异常、脑裂 |

只有在故障独立、任意一个存活副本就足够服务等条件下，才能使用：

```text
n 个同可用性副本的并联可用性 = 1 − (1 − p)^n
```

容量需要至少多个副本时，应像 L-10 一样按“剩余容量是否足够”计算；共同变更或共享依赖导致的故障，也不能当成独立故障相乘。

### 6.3 硬件故障与变更故障需要不同对策

| 维度 | 部件故障 | 变更引起的故障 |
| --- | --- | --- |
| 暴露机会 | 随机器、磁盘数量和运行时间增长 | 随变更次数、变更范围增长 |
| 统计特点 | 可用群体故障率估计数量，具体单次仍不确定 | 每次改动不同，难直接用固定概率概括 |
| 相关性 | 有些可以近似独立，也可能受共同环境影响 | 同一改动常常作用于多个副本 |
| 主要对策 | 冗余、故障域分散、检测与替换 | 分批放量、门禁、快速检测、安全回退 |

Google SRE 第一版第 1 章报告，约 70% 的中断来自运行中系统的变更，并建议渐进发布、及时发现问题和安全回退。**这是该书陈述的经验，不是所有组织或本课堂六个事件的统计比例。**[Google SRE：Change Management](https://sre.google/sre-book/introduction/#change-management)

## 7. 云盘的可靠性与 fsync 延迟（p.13）

### 7.1 快慢之外，还要看谁承担数据恢复

下表保留课件所述产品与时期的口径；产品状态、区域和承诺需以对应服务文档为准。

| 存储 | 课件的延迟量级 | 课件所述冗余与持久性 | 应用需要关注什么 |
| --- | --- | --- | --- |
| 通用型 SSD 云盘 | 4K 单队列写约 1 ms；案例 fsync 约 2 ms | 三副本，持久性 99.9999999% | 数据库自身的备份、误操作恢复与可用性仍需设计 |
| 极速型 SSD 云盘 | 单次写亚毫秒级；H1 按 fsync 0.5 ms 设定 | 三副本或纠删码 EC，持久性 99.9999999% | 更快的盘也要验证实际业务性能 |
| 极速单副本云盘 | 亚毫秒级 | 课件标为公测、单副本、无冗余、不承诺持久性，并注明禁止用于核心生产业务 | 不能假设平台能恢复丢失的数据 |
| 本地 NVMe | 本讲按 fsync 0.1 ms 设定 | 数据与宿主机、本地盘绑定 | 主机或本地盘异常、重部署可能丢数据，应用需复制与恢复机制 |

**持久性不等于可用性。**数据长期不丢失，不代表任何时刻都能及时访问；存储多副本也不防止应用把错误数据合法写入。

平台性能表会区分 IOPS、吞吐量、单次 I/O 时延，并列出实例规格、负载、网络与块大小等影响因素。这些标称值不能直接当成事务吞吐或 fsync 的保证。[华为云：云硬盘类型及性能介绍](https://support.huaweicloud.com/productdesc-evs/zh-cn_topic_0014580744.html)

### 7.2 为什么单次写 1 ms，fsync 却可能约 2 ms

```text
应用请求持久化
  → 操作系统、文件系统与存储协议处理
  → 经网络访问存储集群
  → 完成满足持久性要求的写入与确认
  → fsync 返回
```

一次同步可能涉及数据、日志和其他底层操作，云存储确认还涉及网络与冗余路径。因此 `fsync` 时间不等于宣传表中的一次 4K 写时延。

需要区分两个层次：

- **事务层：**本案例按每个事务两次同步估算，例如 redo 与 binlog。
- **存储层：**每次同步内部又可能涉及多个 I/O；并非所有文件系统都固定为“两次写”。

课件的 2 ms 是案例参数，不能仅凭“1 ms 单次写”严格推导出所有系统的 fsync 都为 2 ms。改成本地盘减少了远程路径，同时把更多可靠性工作交给了应用。

## 8. 性能与容量：把硬件解、软件解放进同一张表（pp.17–19）

### 8.1 出口带宽：升配与 gzip

沿用 L-07：出口约 154 Mbps，上限 200 Mbps，利用率约 77%，高于 70% 的规划线。

| 维度 | 带宽升到 400 Mbps | 启用 gzip |
| --- | --- | --- |
| 改善机制 | 增加供给，带宽上限翻倍 | 减少需求，示例响应从 8 KB 压到 1.6 KB |
| 改善后利用率 | `154 / 400 = 38.5%` | `154 / 5 ≈ 30.8 Mbps`，约占 200 Mbps 的 15.4% |
| 上限 | 该资源可购买的规格上限 | 内容可压缩程度；已压缩图片等收益有限 |
| 见效时间 | 课件按分钟级调整估计 | 约数小时，包含配置与验证 |
| 一次性投入 | 课件简化记为 0 | 约 0.5 人日 |
| 月增量费用 | `(400 − 200) × 80 = 16000 元` | 课件记为 0，前提是现有 CPU 能吸收压缩成本 |
| 可撤回性 | 降配 | 关闭 gzip |
| 新约束 | 更高持续费用，其他瓶颈仍存在 | Nginx CPU 开销增加，需要同时看 TLS 与压缩负载 |
| 主要处理方 | 基础设施运维 | 应用运维 |

价格仅为题设，不能用作云平台报价。这里 gzip 的经济性更好；这不代表所有问题都应该先写软件，写路径案例会得到不同结论。

### 8.2 每个方案都有另一侧的前提

| 方案 | 解决什么 | 仍要补什么 |
| --- | --- | --- |
| 本地盘、单副本存储 | 降低部分 I/O 时延与成本 | 复制、故障切换、备份、恢复演练 |
| 更大的机器 | 增加单机资源 | 规格变更计划，确认应用能使用新增资源 |
| 更快的网络或磁盘 | 缓解当前资源瓶颈 | 重算 CPU、锁、内存等下一项约束 |
| 组提交、批量写 | 将同步成本分摊给多个事务 | 足够并发，且能接受聚合等待时间 |
| 缓存、Redis | 减少数据库热点访问 | 内存、数据一致性、失败补偿与恢复 |
| gzip | 用 CPU 换带宽 | CPU 余量、适合压缩的内容 |

### 8.3 成本要按同一目标与时间范围比较

```text
资源增量成本 ≈ 台数 × 单台月增量费用 × 月数

软件方案成本 ≈ 开发与验证人日 × 人日单价
             + 新增资源费用 + 后续维护成本

简单回本时间 = 一次性投入 / 每月净节省
```

课件的“硬件按月付、软件一次付”强调成本结构差异，不表示软件以后无需维护。只有优化确实减少了购买量或避免了扩容，CPU 用量下降才会变成账单收益。

小平台可能受冗余数量和故障域限制，省不下一整台机器；大平台同一个优化能作用于许多节点，节省会累积。另一方面，硬件有规格上限，软件也可能受串行部分限制，不能无限靠加机器提升吞吐。

## 9. 技术路线：专用硬件、软件定义与硬件卸载（p.21）

| 阶段 | 主要收益 | 代价或下一步动机 |
| --- | --- | --- |
| 专用硬件 | 专门设备提供高性能 | 成本高、交付与扩展粒度较粗 |
| 通用硬件加软件定义 | 可编程、按需创建、便于自动化 | 网络、存储与虚拟化功能占用主机资源 |
| 将部分功能卸载到专用硬件 | 用专用卡处理网络、存储等路径，释放主机资源 | 需要新的硬件与配套软件架构 |

课件列举的演进包括：F5 等负载均衡设备到 LVS、Nginx 与云负载均衡；存储阵列到分布式存储与云盘；传统网络设备到 SDN、安全组，再将部分处理卸载到智能网卡或专用卡。

AWS 对 Nitro 的介绍回顾：早期架构中，虚拟化和网络、存储、监控管理最多曾占用约 30% 的实例资源；Nitro 将部分功能交给专用硬件与软件。**30% 是该历史架构的描述，不能当作所有虚拟机当前的固定开销。**[W. Vogels：Reinventing virtualization with the AWS Nitro System](https://www.allthingsdistributed.com/2020/09/reinventing-virtualization-with-nitro.html)

课件还以华为云擎天架构举例说明计算、存储、网络与安全的卸载。卸载没有取消软件定义：资源仍能通过接口编排，这也是下一讲“以代码定义环境”的基础。

## 11. 讨论一：六个事件，哪些真是硬件故障（p.25）

| 事件 | 课件归因 | 应查证据 | 主要处理方 | 本例是否被冗余吸收 |
| --- | --- | --- | --- | --- |
| 磁盘写满 | 软件或操作：日志未轮转、容量管理缺失 | `df`、日志目录大小与增长、轮转和告警配置 | 应用运维处理日志，基础设施运维协助容量观测 | 是 |
| 内核 panic | **待查**：可能是内核或驱动缺陷，也可能是硬件错误 | kdump 转储、控制台日志、调用栈、MCE 与 EDAC 记录 | 基础设施运维，必要时云平台协查 | 是 |
| OOM 两次 | 课件按内存泄漏或堆配置不当归为软件问题 | 内核 oom-killer 记录、RSS 趋势、堆与容器限额 | 应用运维 | 是，共两次 |
| 网卡故障 | 题设确认为硬件 | 链路日志、`ethtool` 错误计数，结合平台诊断 | 基础设施运维，云上通常由平台处理 | 是 |
| 全站 502，持续 3 min | 健康检查参数变更错误 | 配置差异、变更时间线、后端摘除记录 | 应用运维 | 否 |

**课件讲评：确定是硬件的只有网卡故障这 1 次；panic 不能仅凭名称归因。**OOM 是内存不足时的处置现象，也不能在实际排障中未经检查就断定一定是内存泄漏。

前五次每次只影响一台机器，健康检查约 3 s 后摘除；最后一次错误判定同时作用于所有副本，破坏了“故障独立”的前提。

本题要分清三件事：**故障发生在哪个部件、根因是什么、由谁负责处理。**磁盘所在机器出了问题，不意味着磁盘介质损坏；软件引起的内核问题，也可能首先由基础设施团队排查。

## 12. 讨论二：四种写路径方案的容量与成本（pp.23、26）

### 12.1 先明确串行 fsync 模型

设每事务需要 `m = 2` 次同步，每次耗时 `t` 秒，没有组提交且同步成本串行：

```text
磁盘侧写上限 Q ≈ 1 / (m × t)
按 70% 规划的持续能力 = 0.7 × Q

本题通过条件：300 ≤ 0.7 × Q，且 600 ≤ Q
```

| 方案 | fsync 设定 | 磁盘侧上限 Q | 70% 规划线 | 持续 300 TPS | 短峰 600 TPS |
| --- | --- | --- | --- | --- | --- |
| 现状：通用型 SSD | 2 ms | `1 / (2 × 0.002) = 250` | 175 TPS | 不满足 | 不满足 |
| H1：极速型 SSD | 0.5 ms | `1 / (2 × 0.0005) = 1000` | 700 TPS | 满足 | 满足 |
| H2：本地 NVMe 加主从 | 0.1 ms | `1 / (2 × 0.0001) = 5000` | 3500 TPS | 磁盘模型满足 | 磁盘模型满足 |

3000 IOPS 是特定 I/O 条件下的盘规格，不表示 3000 次事务提交，也不能绕过同步等待直接推导 TPS。

**H2 的 5000 TPS 只是 fsync 这一项的理论上限，不是 4 核 MySQL 的整机承诺。**复制确认、CPU、热点锁、网络等均未计入。若沿用 L-07 的每次提交消耗 2 ms MySQL CPU，5000 TPS 单写入就需要 `5000 × 0.002 = 10 核`，已超过题设的 4 核。

“主从”也不自动代表每次提交都等待从库：异步、半同步或其他同步协议有不同语义。课件提示复制确认会增加等待，是在强调**更高数据保护目标会带来额外路径**；实际确认点和故障丢失窗口必须另行定义。

### 12.2 S1：组提交需要合并多少事务

把 `k` 笔事务合成一组，在同一简化模型中共享两次 2 ms 同步：

```text
组提交磁盘侧上限 ≈ k / (2 × 0.002) = 250k TPS
持续规划线 ≈ 0.7 × 250k = 175k TPS

持续 300 TPS：175k ≥ 300 → k ≥ 1.714… → 至少 2
短峰 600 TPS：250k ≥ 600 → k ≥ 2.4    → 至少 3
```

| 平均有效合并数的理想化取值 | 上限 | 70% 规划线 | 对本题的意义 |
| --- | --- | --- | --- |
| 1 | 250 TPS | 175 TPS | 等同未获得组提交收益 |
| 2 | 500 TPS | 350 TPS | 持续需求满足，600 TPS 短峰仍超过上限 |
| 3 | 750 TPS | 525 TPS | 满足本题的持续与短峰两种判断口径 |
| 4 | 1000 TPS | 700 TPS | 连 600 TPS 也落在 70% 规划线内 |

**k 取决于同时进入提交阶段的事务，不能当作调一个参数就能保证的固定批量。**参数增加等待可能聚集更多事务，也会增加单笔事务延迟；锁竞争与低并发可能使收益达不到预期。上面的吞吐简式还未单独计入凑批等待，因此是理想化估算。

MySQL 的 `binlog_group_commit_sync_delay` 控制同步前等待时间，`binlog_group_commit_sync_no_delay_count` 可在达到事务数后提前结束该等待。官方说明延迟可能减少 fsync 次数，也可能增加事务时延甚至竞争，需要调优验证。[MySQL 8.4：组提交参数](https://dev.mysql.com/doc/refman/8.4/en/replication-options-binary-log.html#sysvar_binlog_group_commit_sync_delay)

组提交可以在持久化完成后才确认成功；它与关闭同步、先返回成功再刷盘不同，不能通过放宽已确认选课记录的持久性来冒充同等效果。

### 12.3 S2：名额扣减移到 Redis

课件把 S2 的机制概括为：热点扣减不再同步等待 MySQL 的 fsync，并在讲评中标为能满足 300 / 600 TPS。

**可推出的是关键路径变了，不能仅凭“用了 Redis”计算新的 TPS 上限。**实际需验证 Redis 的执行与网络能力、原子扣减、重复请求幂等、持久化及故障恢复，以及 Redis 与 MySQL 之间的对账和落库失败补偿。异步落库也仍需能长期消化流入的数据。

### 12.4 第一年的增量成本

课件统一按“新增月费 × 12 + 人日 × 2000”计算，没有纳入原系统基线费用、后续维护与事故成本。

| 方案 | 月增量 | 人日 | 题设见效时间 | 第一年计算 | 第一年增量 |
| --- | --- | --- | --- | --- | --- |
| H1：换极速型 SSD | 130 元 | 0.5 | 约 1 天 | `130 × 12 + 0.5 × 2000` | **2560 元** |
| H2：本地 NVMe 两台主从 | 1500 元 | 5 | 1～2 周 | `1500 × 12 + 5 × 2000` | **28000 元** |
| S1：调组提交 | 0 元 | 2 | 约 1 周 | `0 × 12 + 2 × 2000` | **4000 元** |
| S2：Redis 扣减 | 300 元 | 15 | 3～4 周 | `300 × 12 + 15 × 2000` | **33600 元** |

S1 没有新增月费，但第一年比 H1 多花 `4000 − 2560 = 1440 元`。若两者始终满足相同目标、忽略维护差异，S1 相比 H1 多投入 3000 元人力、每月少付 130 元，约 `3000 / 130 ≈ 23.1 个月` 后累计成本持平；这只是条件化的成本比较，不是长期必须采用 S1 的结论。

### 12.5 两周内与长期怎么选

**课件讲评：两周内选 H1，必要时加 S1。**H1 在模型中同时满足持续与短峰需求，第一年增量最低，且交付时间短；S1 的实际批量与延迟需要实验确认。H2 接近时间期限，运维复杂度更高；S2 按 3～4 周的工期赶不上。

长期在热点与规模增加后考虑 S2；H2 在所需吞吐远超 H1 能力、且团队能承担复制与恢复工作时再评估。两者都需要重做完整资源账。

课件 p.28 还要求开放日前一周冻结变更。因此不能把“两周后开放”理解为“可以开发两周，到当天上线”：应把交付、压测、切换、观察和回退准备安排在冻结前。H1 的时间余量也更充分。

## 13. 讨论三：CPU 降 30%，能省多少机器（p.27）

### 13.1 小平台：先算容量，再加故障冗余

优化需要 10 人日，即 `10 × 2000 = 20000 元`。假定相同业务负载的应用 CPU 总需求降低 30%：

```text
优化后 CPU 需求 = 8.7 × (1 − 30%) = 6.09 核
每台 Tomcat 的规划能力 = 4 × 70% = 2.8 核

优化前只满足正常运行：⌈8.7 / 2.8⌉ = 4 台
优化后只满足正常运行：⌈6.09 / 2.8⌉ = 3 台
```

若要求坏一台后仍满足同一规划线，且每台是独立故障单元：

```text
优化前：需要 4 台工作容量 + 1 台冗余 = 5 台
优化后：需要 3 台工作容量 + 1 台冗余 = 4 台
```

| 方案 | 总台数 | 坏一台后的规划能力 | 是否覆盖需求 |
| --- | --- | --- | --- |
| 优化前的现状 | 4 | `3 × 2.8 = 8.4 核` | 小于 8.7 核，不满足 |
| 不优化，增加一台 | 5 | `4 × 2.8 = 11.2 核` | 满足 8.7 核 |
| 优化后，仍保留四台 | 4 | `3 × 2.8 = 8.4 核` | 满足 6.09 核 |
| 优化后，只留三台 | 3 | `2 × 2.8 = 5.6 核` | 小于 6.09 核，不满足 |

**课件说“一台也省不下”，指从当前 4 台出发，同时满足坏一台仍够用的目标。**相对当前账单没有减少机器，得到的是故障后的容量余量；若比较两种同样具备单机故障容忍能力的方案，则优化避免购买第 5 台。

```text
增加第 5 台：每月 500 元
优化：一次性 20000 元
忽略维护等差异，持平时间 = 20000 / 500 = 40 个月
```

不能把四台优化前后简单说成“可用性完全相同”，也不能把省 30% CPU 直接写成省 30% 服务器费用。

### 13.2 大平台：相同优化可以摊到大量节点

按题设 400 个节点、CPU 是唯一决定节点数的瓶颈，并假设优化可覆盖全部负载、腾出的节点可实际释放：

```text
可减少节点 ≈ 400 × 30% = 120 个
剩余节点 ≈ 280 个
每月节省 = 120 × 1000 = 120000 元
回本时间 = 20000 / 120000 = 1/6 月
按每月 30 天折算，约 5 天
```

这是假定优化完成并推广之后的节省回收期，不包含前面的开发与上线历时。若受内存、故障域、最低副本数或无法退订的资源约束，实际节省会更少。

## 14. 讨论四：一台半坏怎样改变全站 p99（pp.23、27）

### 14.1 先算受影响请求比例

假设 4 台均匀分流，其中一台的 8% 请求额外等待 200 ms 以上：

```text
全站受影响比例 s = 故障实例流量占比 w × 该实例慢请求比例 q
                 = 1/4 × 8% = 2%
```

这些请求的总耗时超过 200 ms，而它们占全部请求的 2%，超过最慢 1% 的尾部范围，所以**全站 p99 超过 200 ms**，高于正常 100 ms 的两倍。

不能写成 `100 + 200 = 300 ms` 的精确 p99：原来的 100 ms 是一个分位数，不是每条慢请求的固定基线，题设没有提供完整延迟分布。也不能对各实例的 p99 求平均来获得全站 p99。

### 14.2 4% 与 8% 的界线是什么意思

在 n 台等流量实例中，一台受影响时：

```text
s = q / n

若希望这类慢请求占全站不到 1%：
q / n < 1% → q < n × 1%
```

| 实例数 | 一台慢实例的流量占比 | 这类慢请求占全站不到 1% 的条件 |
| --- | --- | --- |
| 4 | 25% | 该实例慢请求比例低于 4% |
| 8 | 12.5% | 该实例慢请求比例低于 8% |

**课件把它简称为“不影响全站 p99”的界线，应理解为这类慢请求是否足以单独占据最慢 1%。**即使慢请求不足 1%，整体 p99 的数值仍可能变化；恰好 1% 时还受样本、分位数定义和其他延迟分布影响。不能把稀释占比当成消除故障。

### 14.3 为什么健康检查全过，用户仍受影响

探测每 3 s 执行一次，只覆盖少量请求与某条路径；即使遇到重传，也可能在超时阈值内成功。探测“成功”与真实业务的尾延迟是不同信号。

更有用的证据包括：按实例拆分的请求量、错误率与延迟分布；从用户侧发起的端到端探测；网络重传与接口错误计数。观测应保留实例维度，否则全站聚合指标可能难以指出具体异常实例。

### 14.4 先控制用户影响，再修复底层原因

| 手段 | 做什么 | 课件时间量级 | 边界 |
| --- | --- | --- | --- |
| 软件绕开 | 摘除或降低异常实例权重，限制同时摘除的比例 | 分钟级 | 需要可靠的判定与剩余容量，避免误摘引发级联故障 |
| 平台修复 | 提供证据，安排重部署、迁移或维修 | 小时级 | 平台可能未检测到租户看到的灰色故障，需主动沟通 |

这些时间是课堂估计，不是平台 SLA。绕开与维修可以配合：软件先缩短用户受影响时间，平台处理根因，恢复后验证再逐步接回流量。

**容量检查不能省略：**若同时处于题设 8.7 核的开放日负载，直接摘掉 4 台中的一台，只剩 `3 × 4 × 0.7 = 8.4 核` 规划能力，不足以覆盖需求。应先补容量或降载；若已完成上一题的 30% CPU 优化，则 6.09 核需求可以由剩余三台承担。

## 15. 选课平台的参考处理方案（p.28）

| 问题 | 开放日前 | 长期方向 | 主要处理方 |
| --- | --- | --- | --- |
| 写路径 fsync | 优先采用 H1，验证 300 TPS 持续与 600 TPS 短峰 | 热点与规模上升后评估 Redis 扣减，重新核算一致性与资源 | 基础设施运维配合开发、应用运维 |
| 出口带宽 | gzip 加 CDN，核对 CPU 与缓存行为 | 随内容和流量变化持续核算 | 应用运维 |
| 实例停止服务 | 多实例加健康检查，确认故障后容量 | 自动恢复、分散故障域 | 应用运维 |
| 实例半坏 | 补充分实例指标，准备有容量约束的摘流方案 | 按实际请求延迟与错误发现离群实例 | 应用运维配合平台 |
| 硬件故障与计划维护 | 可安排的维护放在低谷期，提前排空与确认数据保护 | 重点跟进平台未承诺持久性的存储 | 平台处理硬件，应用运维管理接口 |
| 变更故障 | 开放日前一周冻结，提前完成验证和回退准备 | 分批、门禁、检测与回退；下一讲展开 | 应用运维 |

## 16. 公式速查与易混淆概念

| 要算什么 | 公式或方法 | 关键前提 |
| --- | --- | --- |
| 盘群故障频率 | `N × r` 次/年 | 固定规模与同一 AFR 的近似 |
| 盘群平均事件间隔 | `1 / (N × r)` 年 | 平均频率，不是单盘寿命或故障日期 |
| 可用性 | `MTTF / (MTTF + MTTR)` | 两个时间需采用同一服务口径 |
| 简单并联可用性 | `1 − (1 − p)^n` | 故障独立，任一个副本存活就足够 |
| 串行同步写上限 | `Q ≈ 1 / (m × t)` | 无组提交，忽略其他瓶颈；t 用秒 |
| 理想组提交能力 | `Q ≈ k / (m × t)` | 能实际形成批量；还需计入等待与竞争 |
| 第一年增量成本 | `12 × 月增量费用 + 人日 × 人日单价` | 统一成本范围，不自动包含后续维护 |
| 简单回本时间 | `一次性投入 / 每月净节省` | 节省可兑现；不含开发历时 |
| 正常运行所需实例数 | `⌈总需求 / 单实例规划能力⌉` | 负载能分摊，实例等能力 |
| 容忍单实例故障的数量 | `⌈总需求 / 单实例规划能力⌉ + 1` | 一次故障只损失一个实例 |
| 全站某类慢请求占比 | `Σ(实例流量占比 × 实例内该类慢请求比例)` | 使用请求占比加权，不平均分位数 |

| 易混淆项 | 区别 |
| --- | --- |
| 机器故障 / 硬件损坏 | 描述故障发生位置 / 判断根因，需要证据 |
| fail-slow / 灰色故障 | 性能退化的故障形态 / 内外观测存在差异 |
| 存活 / 可用 / 正确 | 进程能响应 / 服务达到目标 / 结果符合语义 |
| 资源余量 / 可减少台数 | 资源需求下降 / 满足所有约束后能释放的整台机器 |
| 磁盘上限 / 系统上限 | 单项资源的模型能力 / 所有必要路径共同决定的能力 |
| 副本 / 备份 | 常用于持续服务与故障切换 / 用于恢复历史正确状态 |
| 持久性 / 可用性 | 数据不丢 / 需要时能访问并达到服务目标 |
| 硬件修复 / 服务恢复 | 部件恢复正常 / 用户请求重新得到服务，时间可以不同 |
| 软件无新增月费 / 软件零成本 | 不加资源费用 / 仍需人力、验证和维护 |

## 17. 复习自测

1. **发生内核 panic，可以直接归因于硬件吗？**

   不可以。应查看转储、调用栈与硬件错误记录，区分软件缺陷和硬件异常。

2. **1000 块盘、AFR 1.36%，为什么约 27 天遇到一次故障？**

   每年预期 13.6 次，`365 / 13.6 ≈ 26.8 天`，这是盘群平均频率。

3. **多了机器为什么可能提高服务可用性？**

   虽然部件故障机会增多，冗余和快速摘流能减少故障对服务的影响；前提是幸存容量、依赖和状态仍可用。

4. **四个应用副本为什么没挡住健康检查配置错误？**

   共享的错误判定同时作用于全部副本，是相关故障。

5. **两次 2 ms fsync 为什么只得到 250 TPS？**

   串行无组提交模型中，每事务同步时间为 4 ms，倒数为 250 TPS。

6. **H1 的持续规划能力和第一年费用是多少？**

   `0.7 × 1000 = 700 TPS`；`130 × 12 + 0.5 × 2000 = 2560 元`。

7. **组提交 k = 2 能扛住本题全部流量吗？**

   持续规划线 350 TPS 满足 300，但上限 500 TPS 小于 600 的短峰，需要理想化 k 至少为 3，并实测确认。

8. **换本地 NVMe 后是否一定有 5000 TPS？**

   不一定。那是只算 fsync 的上限，CPU、复制与热点锁等会进一步限制性能。

9. **CPU 降 30% 后，小平台为什么仍需四台？**

   6.09 核需求至少要三台提供规划能力，再留一台承受故障。

10. **400 节点平台为什么约 5 天回本？**

    题设允许释放 120 节点，每月省 12 万元；2 万元投入约为 1/6 个月。这不含开发时间。

11. **四台中一台有 8% 请求多等 200 ms，全站受影响多少？**

    均匀分流时为 2%，足以使 p99 超过 200 ms；不能由此算出精确的 300 ms。

12. **发现慢实例后可以直接摘掉吗？**

    先检查剩余容量和摘除比例。本题原始负载下三台规划能力只有 8.4 核，小于 8.7 核，需要补容量或降载。
