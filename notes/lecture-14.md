## 2. 一条选课提交的一生（p.6）

### 2.1 表结构与事务边界

课件的逻辑表结构如下，省略列类型与完整建表约束：

```text
course(
  id PRIMARY KEY, name, capacity, remain, open_at, ...
)

enrollment(
  id BIGINT 自增 PRIMARY KEY,
  student_id, course_id, created_at,
  UNIQUE KEY uk_stu_course(student_id, course_id),
  KEY idx_course(course_id)
)
```

事务示意：

```sql
BEGIN;

INSERT INTO enrollment (student_id, course_id, created_at)
VALUES (?, ?, NOW());

UPDATE course
SET remain = remain - 1
WHERE id = ? AND remain > 0;

-- 应用检查 UPDATE 的影响行数：
-- 1 行：COMMIT；0 行：ROLLBACK，不能保留刚才插入的选课记录。
-- 任一步出现错误，也进入相应的回滚与错误处理分支。
```

两个不变量分别由不同机制保护：

- **不超卖：**带 `remain > 0` 的原子扣减，并检查影响行数。
- **不重复选课：**`UNIQUE(student_id, course_id)`；选课记录与扣减在同一事务内成功或失败。

这里按“一个学生对一门课只有一条有效记录”的简化业务建模。若需要保留多学期或退选历史，唯一键和幂等规则要随业务调整。

### 2.2 沿执行路径定位问题

```mermaid
flowchart LR
    A[连接池取连接] --> B[解析 SQL 与选择执行计划]
    B --> C[沿索引定位记录]
    C --> D[获取锁与检查条件]
    D --> E[生成 undo 和 redo<br/>修改 buffer pool 中的页]
    E --> F[协调 redo 与 binlog 提交]
    F --> G[释放事务锁并返回]
    F -.复制流水线.-> H[从库接收日志并回放]
```

图是理解路径的简化；复制可以与主库提交过程交叠，半同步模式还会在返回成功前等待从库确认。

| 症状                       | 优先检查的环节                           |
| -------------------------- | ---------------------------------------- |
| 拿不到连接                 | 池是否耗尽；连接是否被慢事务或锁等待占用 |
| 扫描大量记录               | 索引、过滤条件、执行计划                 |
| CPU 不高但写请求排队       | 热点行锁、持锁时间、存储同步等待         |
| 提交成功，随后查询却看不到 | 是否读到延迟的从库或旧缓存               |
| 超时后重试出现重复         | 数据库唯一约束、幂等结果与事务边界       |

## 3. 索引：减少找行的工作，也会增加维护成本（pp.7–8）

### 3.1 为什么是 B+ 树

InnoDB 按页组织数据，课件采用默认 **16 KiB** 页大小。非叶子页容纳大量键与子页引用，扇出大、树较矮；叶子按键有序连接，便于范围扫描。

| 结构           | 与本讲需求的关系                                           |
| -------------- | ---------------------------------------------------------- |
| 哈希           | 适合等值访问，不天然提供键的有序范围与排序                 |
| 二叉树、红黑树 | 扇出只有 2；直接照搬为磁盘结构，层数和页访问可能更多       |
| B 树           | 非叶子也存记录，可能减少扇出；范围遍历组织方式不同         |
| B+ 树          | 内部页主要用于导航，数据集中在叶子，适合分页存储和范围扫描 |

**树高不等于每次查询的磁盘读取次数。**上层页若已缓存，访问这些层不需要实际磁盘 I/O。

### 3.2 聚簇索引、二级索引、回表与覆盖

在本讲显式主键的表中，聚簇索引叶子保存完整行；二级索引记录包含索引列和主键值。

```text
二级索引查到主键 → 按主键访问聚簇索引 → 取得其余列
                   这一步称为“回表”
```

如果查询所需列已经全部位于所用索引中，就是覆盖索引访问，例如：

```sql
SELECT course_id
FROM enrollment
WHERE student_id = ?;
```

`(student_id, course_id)` 可以覆盖这条查询。`EXPLAIN` 的 `Extra` 中常见 `Using index`。

主键选择也影响二级索引：主键越长，每个二级索引携带的主键越大。自增键通常有较好的插入局部性；随机键可能增加页分裂、碎片和缓存压力。这里描述的是访问模式的代价，不能据此断言所有 UUID 方案都不可用。

### 3.3 联合索引与最左前缀

`(student_id, course_id)` 先按学生排序，同一学生内再按课程排序。

| 查询条件                           | 在本案例中的设计                               |
| ---------------------------------- | ---------------------------------------------- |
| `student_id = ?`                   | 利用联合索引的最左前缀                         |
| `student_id = ? AND course_id = ?` | 利用完整联合键定位                             |
| 只有 `course_id = ?`               | 另建 `idx_course(course_id)`，支持查询课程名单 |

**补充理解：**“不满足最左前缀就绝对不用该索引”过于绝对。它通常不能直接做相应的前缀定位，但可能全索引扫描，满足条件时 MySQL 还可能选择 Skip Scan；是否采用以执行计划为准。[MySQL：Skip Scan](https://dev.mysql.com/doc/refman/8.4/en/range-optimization.html#range-access-skip-scan)

### 3.4 常见的索引访问问题

| 写法或数据分布                     | 问题                                                   | 调整方向                                                        |
| ---------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------- |
| `YEAR(created_at) = 2026`          | 普通 `created_at` 索引不能直接按原值范围定位这个表达式 | 改为 `created_at >= '2026-01-01' AND created_at < '2027-01-01'` |
| 字符串 `student_id` 与数字常量比较 | 隐式转换可能妨碍索引查找，并产生意外比较结果           | 绑定与列一致的参数类型                                          |
| `name LIKE '%数据%'`               | 没有固定左前缀，普通 B+ 树难以直接定位                 | 按搜索语义评估全文索引或搜索引擎                                |
| `status = 1` 命中九成记录          | 大量回表可能比全表扫描更贵                             | 按实际过滤条件设计联合索引，检查成本                            |

上述函数例子针对普通列索引；匹配表达式的函数索引或生成列索引需要另行讨论。增加索引也会增加空间与写入维护成本。

### 3.5 EXPLAIN 与深分页

| 字段    | 应读出什么                                                 |
| ------- | ---------------------------------------------------------- |
| `type`  | 访问方式；课件列出 `const`、`ref`、`range`、`index`、`ALL` |
| `key`   | 实际选用的索引                                             |
| `rows`  | 优化器估计检查的行数，不是实测返回行数                     |
| `Extra` | 是否覆盖、额外排序、临时表等执行信息                       |

`type=index` 可能是全索引扫描；`Using filesort` 表示需要额外排序，不等于必然写磁盘。不能脱离扫描规模，仅按 `type` 排名判断整个查询快慢。[MySQL：EXPLAIN 输出](https://dev.mysql.com/doc/refman/8.4/en/explain-output.html)

`LIMIT 100000, 20` 需要越过前面大量记录。连续翻页可以采用游标式分页：

```sql
SELECT id, course_id, created_at
FROM enrollment
WHERE student_id = ? AND id > ?
ORDER BY id
LIMIT 20;
```

这是按 `id` 递增分页的示例，第二个参数为上一页末尾 ID；应另行评估支持该过滤与排序的索引，如 `(student_id, id)`。它不直接支持任意跳到第几页；若按非唯一字段排序，还需要唯一的次级排序键。

## 4. 一张表能放多少行：先算树高与工作集（p.9）

### 4.1 “两千万行”来自什么假设

三层树指 **根页 → 一层内部页 → 叶子页**。若内部页扇出为 `F`，每叶子页放 `L` 行：

```text
三层树可容纳行数 ≈ F² × L
```

| 模型                                    | 内部页扇出 F | 每叶子页行数 L | 三层估计容量                              |
| --------------------------------------- | ------------ | -------------- | ----------------------------------------- |
| 每项 8 B 主键 + 6 B 指针，行宽约 1 KiB  | 1170         | 16             | `1170² × 16 ≈ 2190 万行`                  |
| 每项约 17 B、填充约 15/16，行宽约 1 KiB | 900          | 15             | `900² × 15 ≈ 1215 万行`                   |
| 选课记录行宽约 50 B                     | 900          | 300            | `900² × 300 ≈ 2.43 亿行`，课件取约 2.5 亿 |

这些是估算，不是 InnoDB 的固定行数阈值。页头、记录头、隐藏列、变长字段、填充率与碎片都会改变结果。

### 4.2 选课平台十年的数据量

```text
每年记录 = 20,000 人 × 8 条/学期 × 2 学期 = 320,000 行
十年记录 = 3,200,000 行

叶子页约 = ⌈3,200,000 / 300⌉ = 10,667 页
上一层约 = ⌈10,667 / 900⌉ = 12 页
根页加上一层 = 1 + 12 = 13 页
```

上面 13 页很容易常驻 buffer pool；在该理想化模型中，按主键定位一个普通行，至多还需要读一次叶子页。若涉及溢出页、旧版本链或其他索引，不能沿用“一次 I/O”概括全部工作。

课件按行宽粗估聚簇数据约 **160 MB**，加二级索引约 **230 MB**，远小于此前设定的 **6 GB buffer pool**。这是容量量级，不是数据库文件实测大小。即使按 5 万人算，十年约 800 万行，在模型中仍可保持三层。

**决策依据是树高、热数据工作集、查询与写入负载，以及维护需求；不是到了某个行数就必须分表。**

## 5. 防超卖与幂等：事务不自动替你补上正确条件（p.10）

### 5.1 四种扣减写法

| 写法                                                            | 是否正确           | 原因与代价                                                         |
| --------------------------------------------------------------- | ------------------ | ------------------------------------------------------------------ |
| 普通 `SELECT remain`，应用算出新值，再 `UPDATE SET remain=新值` | 不保证正确         | 两个事务可能都读到 1，再分别写 0，却各插入一条选课记录             |
| `UPDATE ... SET remain=remain-1 WHERE id=? AND remain>0`        | 按本题事务边界可行 | 在锁保护下依据当前记录判断与扣减，检查影响行数                     |
| `SELECT ... FOR UPDATE`，判断后再更新                           | 可行               | 先锁住目标记录，通常增加一次往返并延长持锁时间                     |
| `UPDATE ... WHERE id=? AND version=?`                           | 正确实现时可行     | 更新时同时递增版本，失败后重新读取与判断；热门行冲突会带来重试成本 |

错误写法的并发过程：

```text
初始 remain = 1
A：普通 SELECT 得到 1
B：普通 SELECT 得到 1
A：插入 A 的选课记录，把 remain 写成 0，提交
B：插入 B 的选课记录，把 remain 也写成 0，提交
结果：余量没有负数，但同一个名额被分配了两次
```

因此，“最终 `remain >= 0`”本身不足以证明没有超卖。

**资料核对：**课件将乐观锁概括为“不等锁”，应理解为不在业务读取阶段预先持有悲观锁。InnoDB 执行带版本条件的 `UPDATE` 时仍要加锁，仍可能等待；“乐观”描述冲突检测策略，不表示数据库更新无锁。[MySQL：SQL 语句设置的锁](https://dev.mysql.com/doc/refman/8.4/en/innodb-locks-set.html)

### 5.2 幂等由约束与结果处理一起完成

“先查有没有，再插入”仍有并发窗口；唯一约束让数据库拒绝同一学生重复选同一门课。

接口超时后，第一次事务可能已经提交。重试遇到本业务唯一键冲突时，应回滚当前尝试，确认已有有效选课记录，再返回与既有结果一致的“已选上”。不能把任意 `Duplicate entry`、锁超时或数据库错误都转换为成功。

**防超卖、去重、原子提交分别解决不同问题，必须配合。**

## 6. 热点行吞吐：上限由持锁时间决定（p.11）

### 6.1 把热点行看成单服务台

所有提交都更新同一课程的余量行，更新过程需要串行通过该行的锁。沿用 [Lecture 06](/Users/xlchen/RR-fa26/notes/lecture-06.md) 的排队模型：

```text
服务时间 S = 拿到热点行锁后，到提交并释放该锁的时间
单行处理能力 μ ≈ 1 / S
利用率 ρ = 到达率 λ × S
```

等待别人释放锁的时间是排队时间，不应再加进单次服务时间计算 `μ`。这个上限也不是满足尾延迟目标的安全运行线。

课件设定应用与数据库 RTT 为 0.2 ms，语句耗时 0.1 ms，单次 fsync 为 0.5 ms：

| 写法或部署                          | 持锁时间 | 单行每秒至多 | 到达率 200/s 时的 ρ |
| ----------------------------------- | -------- | ------------ | ------------------- |
| A：先 INSERT，最后 UPDATE 余量      | 1.3 ms   | 769          | 0.26                |
| B：先 UPDATE 余量，再 INSERT        | 1.6 ms   | 625          | 0.32                |
| C：先 FOR UPDATE，再 UPDATE、INSERT | 1.9 ms   | 526          | 0.38                |
| A，但使用 fsync 2 ms 的通用型 SSD   | 4.3 ms   | 233          | 0.86                |
| A，但应用与数据库 RTT 为 30 ms      | 约 31 ms | 约 32        | 6.2                 |

复现课件的简化计时：

```text
A ≈ 0.1 ms 语句 + 0.2 ms 往返 + 2 × 0.5 ms fsync = 1.3 ms
B ≈ A + (0.1 + 0.2) ms = 1.6 ms
C ≈ B + (0.1 + 0.2) ms = 1.9 ms

通用型 SSD：0.1 + 0.2 + 2 × 2 = 4.3 ms
异地：0.1 + 30 + 2 × 0.5 = 31.1 ms，课件取约 31 ms
```

这些数值忽略调度、锁交接、其他竞争与额外日志开销；先插入再扣减也意味着失败时要回滚插入。实际事务若有其他锁依赖，仍要统一加锁顺序并处理死锁。

### 6.2 为什么约 0.7 s 就耗尽连接

按课件近似 `μ = 1000/31 ≈ 32.26/s`，假设 200/s 持续到达、每个在途事务占一条连接：

```text
积压增长率 ≈ 200 − 32.26 = 167.74 个/s
连接总数 = 6 × 20 = 120
占满时间 ≈ 120 / 167.74 ≈ 0.715 s
```

这是忽略原有占用和入口控制的流体近似。连接池耗尽后，排队会转移到应用端或触发超时；继续增加 Tomcat 不能提高同一热点行的处理能力。

### 6.3 组提交为什么不能直接消除同一行的串行化

不同记录的事务可以并发推进到提交阶段，共享刷盘开销，提高整库吞吐。争用同一行时，下一个事务要先等前一个释放锁，不能简单把这一行的多个扣减都当作同时进入提交组。

当前题设只算两次 0.5 ms fsync，未计组提交收益的整库基线为：

```text
Q ≈ 1 / (2 × 0.0005 s) = 1000 TPS
```

这是课件模型中的存储基线，既不是“所有 MySQL 的上限”，也不是“有组提交后仍固定 1000 TPS”。

### 6.4 热点优化与各自的新问题

| 手段                                         | 解决什么               | 需要补上的条件                                     |
| -------------------------------------------- | ---------------------- | -------------------------------------------------- |
| 热点更新尽量靠近提交，事务内不做外部网络调用 | 缩短持锁时间           | 保持完整事务语义和一致的锁顺序                     |
| 售罄后快速拒绝                               | 减少无意义的数据库争用 | 退选、补名额时能清除标记；最终分配仍由权威数据决定 |
| 入口排队、限流                               | 控制在途事务与连接占用 | 明确超时、公平性、拒绝与重试规则                   |
| 将名额拆成 4 个独立配额行                    | 分散单行锁竞争         | 总配额不能增加；需要分配、调拨；其他瓶颈仍存在     |
| Redis 扣减后异步落库                         | 改变关键写路径         | 持久性、重复消息、补偿、对账与故障恢复             |

按题设，4 行理论锁能力约 `4 × 769 = 3076/s`，随后可能受上述约 1000 TPS 的存储基线限制。实际能否达到，取决于事务能否真正分散以及提交方式。

课件还提出：极端热点下，死锁检测本身可能昂贵，可评估关闭检测并依赖锁等待超时。但不能把它当作默认优化；**锁等待超时默认只回滚当前语句，不一定回滚整个事务**，应用必须处理完整事务失败。[MySQL：超时回滚行为](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html#sysvar_innodb_rollback_on_timeout)

## 7. 隔离级别、MVCC 与锁的范围（p.12）

### 7.1 隔离级别讨论的是哪些读现象

- **脏读：**读到其他事务未提交的数据。
- **不可重复读：**同一事务再次读同一记录，其值已被其他提交改变。
- **幻读：**重复按同一条件查询时，满足条件的记录集合发生变化。

| 隔离级别                     | 脏读 | 不可重复读 | 幻读：课件按 SQL 标准归纳  |
| ---------------------------- | ---- | ---------- | -------------------------- |
| READ UNCOMMITTED             | 可能 | 可能       | 可能                       |
| READ COMMITTED               | 避免 | 可能       | 可能                       |
| REPEATABLE READ，InnoDB 默认 | 避免 | 避免       | 标准允许，具体看实现与读法 |
| SERIALIZABLE                 | 避免 | 避免       | 避免                       |

标准中的最低保证与 InnoDB 的具体实现要分开，不能只背“RR 有幻读”或“RR 完全解决幻读”。

### 7.2 快照读如何找版本

行记录携带事务信息和回滚指针，undo 提供构造旧版本所需的信息；读视图决定哪些版本可见。

```text
最新版本                          旧版本                     更旧版本
remain=1，事务110，未提交  →  remain=2，事务105，已提交  →  remain=3，事务100，已提交
```

课件中的普通查询读到 2，前提是它的读视图允许看到事务 105。若快照更早，也可能读到 3；不能只凭“已经提交”就判断对所有事务可见。

| 场景               | 普通一致性读的快照                       |
| ------------------ | ---------------------------------------- |
| READ COMMITTED     | 每次一致性读创建新的读视图               |
| REPEATABLE READ    | 通常使用事务内第一次一致性读建立的读视图 |
| 同一事务自己的修改 | 自己可见，不能当作被旧快照屏蔽           |

普通一致性读不通过给数据行加锁来排斥写入，但不等于没有元数据锁等其他机制。[MySQL：一致性非锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)

### 7.3 快照读与当前读不能混为一谈

普通 `SELECT` 在这里按快照读；`UPDATE`、`DELETE`、`SELECT ... FOR UPDATE` 涉及当前记录和锁。上例继续更新时，需要等待事务 110 结束，再依据可更新的当前状态处理。

RR 事务中的快照查询可能看不到别人刚提交的记录，但之后的 `UPDATE` 可以影响那些记录；自己的修改随后又对自己可见。因此，**“查询展示的余量”不能代替“扣减时的权威判断”。**[MySQL：快照与 DML 的区别](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)

### 7.4 索引还决定锁住多大范围

| 访问方式                             | 本讲需要掌握的锁范围                         |
| ------------------------------------ | -------------------------------------------- |
| 完整唯一键等值，找到已有记录         | 通常只需记录锁，不需锁前面的间隙             |
| RR 下的范围加锁访问                  | 可能使用 next-key lock，即记录锁加相邻间隙锁 |
| 缺少合适索引，扫描全表的更新或加锁读 | 可能锁住大量乃至全部记录，严重影响并发       |

“唯一等值只锁一条”需要找到已有记录等前提；未命中、只使用联合唯一键的一部分、外键与重复键检查可能有不同锁行为。全表扫描产生大量记录锁也不等于自动升级成一把表锁。[MySQL：InnoDB 锁](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html)

长事务既可能长时间占锁，也可能使旧读视图需要的 undo 无法清理。优化事务不能只看一条 SQL 的执行耗时。

## 8. 提交与崩溃：三种日志和内部两阶段提交（p.13）

### 8.1 三种日志各有职责

| 日志     | 所属层       | 主要作用                       | 代价或限制                   |
| -------- | ------------ | ------------------------------ | ---------------------------- |
| redo log | InnoDB       | 崩溃恢复时重做修改，支持持久性 | 需要按持久性配置同步日志     |
| undo log | InnoDB       | 回滚修改，并支持 MVCC 旧版本   | 长事务或旧读视图使清理推迟   |
| binlog   | MySQL Server | 复制与结合备份做按时间点恢复   | 增加日志写入、同步与保留成本 |

**WAL 的准确理解：**相关日志先持久化，再允许对应脏数据页写入磁盘；并不是“必须先 fsync，才能修改内存中的 buffer pool 页”。提交也不要求把本事务涉及的全部数据页当场刷盘。[MySQL：redo log 实现说明](https://dev.mysql.com/doc/dev/mysql-server/8.4.11/PAGE_INNODB_REDO_LOG.html)

### 8.2 为什么 redo 与 binlog 需要协调

课件简化流程：

```text
InnoDB prepare：持久化准备状态
  → 写入并同步 binlog 中的事务
  → InnoDB commit：完成提交，释放事务锁
```

如果两边决定不一致，可能出现“主库恢复后有这次修改，但复制或从 binlog 恢复时没有”，或者反过来。对于崩溃时处于 prepared 状态的事务，恢复时需要依据 binlog 中是否有完整的事务提交记录等信息决定提交或回滚。

这里是 **MySQL Server 与存储引擎之间的内部提交协调**，不能直接当成跨多个业务数据库的完整分布式事务方案。

### 8.3 “双 1”、组提交与约 1 秒丢失窗口

```text
innodb_flush_log_at_trx_commit = 1
sync_binlog = 1
```

课件用两次 fsync 表示 redo 与 binlog 的持久化开销。组提交可以使多个事务共享同步操作，不能把“两次”当成每个事务独占两个物理刷盘调用的普遍定律。

| redo 配置 | 课件中的主要区别                                                               |
| --------- | ------------------------------------------------------------------------------ |
| `=1`      | 提交按要求写出并同步 redo                                                      |
| `=2`      | 提交写到操作系统缓存，通常周期性同步；操作系统崩溃或掉电可能丢尚未持久化的事务 |
| `=0`      | 写出与同步都主要周期性进行，mysqld 进程崩溃也有丢失风险                        |

**资料核对：**课件“最多丢约 1 秒”是默认周期下的粗略量级，官方文档明确周期性刷盘不保证精确每秒发生；调度和配置会改变丢失窗口。`=2` 在只有进程退出、操作系统缓存完好的简化情形下通常比 `=0` 更安全，但不能概括为任何故障下都不丢。[MySQL：redo 刷盘配置](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html#sysvar_innodb_flush_log_at_trx_commit)

ACID 的对应关系可记为：**原子性靠回滚机制，持久性靠可靠的日志与存储，隔离性靠锁和 MVCC，一致性还要有正确的业务约束与事务逻辑。**

## 9. 离开单机：复制、读写分离、分片与缓存（p.14）

### 9.1 从库收到日志，不等于已经回放

```text
主库 binlog → 从库接收并写 relay log → 从库回放修改
```

| 模式       | 主库等什么                                   | 主要边界                                     |
| ---------- | -------------------------------------------- | -------------------------------------------- |
| 异步复制   | 不等待从库确认                               | 切换到落后从库时，可能缺少主库已经提交的事务 |
| 半同步复制 | 等所需数量的从库收到并记录日志，默认至少一个 | 不等于完成回放；超时可退回异步               |

因此，半同步不能自动保证“刚提交，再从任意从库读就能看到”。[MySQL：半同步复制](https://dev.mysql.com/doc/refman/8.4/en/replication-semisync.html)

课件说“半同步多持锁一个往返”，对应默认 `AFTER_SYNC` 等待点：同步 binlog 后等待确认，再提交存储引擎。配置为 `AFTER_COMMIT` 时，确认等待发生在引擎提交之后，不能照搬同一持锁推导。[MySQL：半同步等待点](https://dev.mysql.com/doc/refman/8.4/en/replication-options-source.html#sysvar_rpl_semi_sync_source_wait_point)

### 9.2 读己之写

大事务、较弱的从库资源或回放并行度不足，都可能导致“已经选上，但我的课表没有”。

| 方案                           | 代价与边界                             |
| ------------------------------ | -------------------------------------- |
| 关键页面或写后本会话读主库     | 增加主库读压力                         |
| 写后一段时间读主库             | 简单，但固定时间不能严格保证复制已追上 |
| 等从库应用到指定事务位置后再读 | 增加等待、超时处理与路由复杂度         |

### 9.3 分片键由访问模式决定

| 分片方式           | 查我的课表       | 查一门课的名单   | 新成本                         |
| ------------------ | ---------------- | ---------------- | ------------------------------ |
| 按 `student_id`    | 一个分片         | 多个分片         | 跨分片聚合                     |
| 按 `course_id`     | 多个分片         | 一个分片         | 同一热门课仍可能集中在一个分片 |
| 两份分别组织的数据 | 各自可走一个分片 | 各自可走一个分片 | 双写或异步同步、对账与一致性   |

还要考虑全局 ID、跨分片事务、扩容搬迁和故障恢复。按当前案例的数据量，不能仅凭“以后会变大”就判断必须分片；**分片可以分摊总量，不自动解决单一热点。**

### 9.4 缓存与数据库的一致性

“先更新数据库、再删除缓存”仍有短暂窗口：并发读可能把旧值重新填回缓存，删除本身也可能失败。

课件列出延迟再删、订阅 binlog 失效、TTL 兜底等方式。它们需要重试与失败处理，不能天然变成严格一致。**浏览页面可以显示稍旧的余量，最终选课结果由权威扣减事务决定。**

## 10. 六道面试判错题（pp.15–16）

| 原说法                                          | 应怎样回答                                                                 |
| ----------------------------------------------- | -------------------------------------------------------------------------- |
| “可重复读已经完全解决幻读。”                    | 区分快照读、加锁读及混用场景；RR 不是所有业务操作都自动串行化。            |
| “给 status 建了索引，查询就一定走。”            | 优化器按成本选计划；命中比例、回表量、表达式和联合键顺序都会影响选择。     |
| “在事务里先 SELECT 余量再 UPDATE，就不会超卖。” | 普通快照读不提前锁住余量；应做带条件的原子更新，或正确使用 FOR UPDATE。    |
| “半同步复制，读从库一定能看到刚提交的数据。”    | 确认收到日志不等于回放完成，超时还可能退回异步。                           |
| “redo 刷盘设为 2 更快，而且不会丢数据。”        | 可能减少同步等待，但持久性下降；故障类型和实际刷盘周期决定风险。           |
| “单表超过 2000 万行就必须分库分表。”            | 该数来自特定行宽、扇出与三层树估算，应检查当前工作集、访问负载和维护需求。 |

这些题共同考察的是：**结论成立需要哪些条件，条件变化后结论是否还成立。**

## 11. 从机房到宇宙：先算传播下限（pp.18–19）

传播往返的简化公式：

```text
RTT_min ≈ 2 × 路径距离 / 信号传播速度
真空光速约 300,000 km/s；光纤中约 200,000 km/s
```

| 场景                        | 课件距离或设定                 | 往返时间量级  |
| --------------------------- | ------------------------------ | ------------- |
| 机房内                      | 本题设定                       | 0.2 ms        |
| 异地校区                    | 本题设定                       | 30 ms         |
| 地球对跖点                  | 沿地表约 20,000 km，按光纤速度 | 至少约 200 ms |
| 地月                        | 平均约 384,000 km              | 2.56 s        |
| 地火                        | 约 0.55～4 亿 km，随位置变化   | 约 6～45 min  |
| 旅行者 1 号位于一光日距离时 | 光走 24 h 的距离               | 约 48 h       |
| 地球与比邻星附近固定端点    | 约 4.24 光年                   | 约 8.48 年    |

这些不是完整业务响应时间：实际还包括路由、中继、排队、握手、处理与等待通信窗口。地月和地火距离也不是固定常数。

尺度每放大一级，都重新问四个问题：**往返多久？链路一直都在吗？钟怎么对？坏了谁来修？**

带宽决定单位时间能传多少数据，传播延迟决定最早何时收到；提高带宽不能突破光速下限。课件还指出，真空激光链路的传播速度高于光纤，长距离低轨卫星路线有可能更快，但需要计入真实路径和中继；静止轨道卫星往返则仅传播就约 0.48 s。

## 12. 地球：把跨地域往返放在正确的位置（p.20）

### 12.1 应用靠近用户，不一定让事务更快

| 部署                              | 远端请求经历什么                                | 热点行的结果                 |
| --------------------------------- | ----------------------------------------------- | ---------------------------- |
| Tomcat 在新校区，数据库留在原机房 | 事务中的 3～4 次往返都跨地域，约增加 90～120 ms | 持锁约 31 ms，约 32 次/s     |
| Tomcat 与数据库都在原机房         | 用户到应用跨地域一次，内部事务仍为本地往返      | 持锁仍约 1.3 ms，约 769 次/s |

**总响应时间和持锁时间是两本账。**事务开始前的查询、插入或连接等待也影响用户响应，但只有拿到热点锁后的等待会延长该热点的串行服务时间。

“跨地域放在用户与应用之间”是当前交互式数据库事务模型的结论。存储过程、减少语句往返或更换数据架构会改变路径，分析时仍应逐段数清等待。

### 12.2 分区时如何继续服务

| 方案                             | 正常时             | 断网时                                       | 代价                                     |
| -------------------------------- | ------------------ | -------------------------------------------- | ---------------------------------------- |
| 单主库集中扣减                   | 远端多一次请求往返 | 远端不能完成写入；主库机房失效会影响两地     | 简单，但集中依赖                         |
| 名额预先按校区拆分，各地本地扣减 | 本地事务           | 各地在自己的配额内继续                       | 余量不能任意共享，需要调拨规则           |
| 多数派复制，确认后提交           | 写入等待复制确认   | 能形成多数派的一侧可继续，另一侧停止相关写入 | 延迟、部署与故障域成本                   |
| 两地独立写同一份完整名额         | 本地快速返回       | 两地都可继续写                               | 若没有额外约束，可能各卖出“最后一个名额” |

课件将多数派方案按至少一次 30 ms 跨站确认、单行约 32/s 估算。这不是所有 Raft/Paxos 系统的通用吞吐上限；批处理、流水线与状态机实现会改变吞吐模型。

课件的“至少三个地点”对应典型三故障域部署、希望承受一个站点故障的方案；协议本身并不规定地点数量，关键是失去某个故障域后能否保留多数派。

### 12.3 CAP 与 PACELC 要讲清口径

- **CAP：**发生网络分区时，不能同时保证所有相关操作具有线性一致性，并让每个未故障节点收到的操作都持续得到服务。这里的可用性是理论定义，不等同于课程前面按比例统计的可用性 SLO。[Gilbert 与 Lynch：CAP 论文](https://groups.csail.mit.edu/tds/papers/Gilbert/Brewer6.pdf)
- **PACELC：**分区时讨论可用性与一致性；没有分区时，复制系统仍面临延迟与一致性的取舍。[Abadi：PACELC 论文](https://www.cs.umd.edu/~abadi/papers/abadi-pacelc.pdf)

课程中的业务选择：**名额分配优先保护不超卖，课程浏览可以接受旧数据。**预分配配额则改变了需要跨站协调的操作范围，让部分安全操作能够在本地完成。

## 13. 地球上的时钟：开放时间与事件顺序由谁决定（p.21）

### 13.1 20 ppm 漂移为何足以破坏选课公平性

假设一个 Tomcat 三天未同步，持续快 20 ppm：

```text
漂移 = 20 × 10⁻⁶ × 3 × 24 × 3600 = 5.184 s
该实例承接速率 = 200 / 6 ≈ 33.33 次/s
提前放入的尝试 ≈ 5.184 × 33.33 = 172.8 次
```

在“提前期间也有相同尝试速率”的假设下，约 173 次，已经超过 120 个名额。未必每次都成功，但足以说明数秒误差会改变分配结果。

靠配置中心推送“开放”开关也不保证同时生效：前讲的配置传播设定为 30 s。

把判定放到同一权威位置，例如：

```sql
UPDATE course
SET remain = remain - 1
WHERE id = ?
  AND remain > 0
  AND open_at <= NOW();
```

这样由主库的时间执行开放判断；需统一 `open_at` 与数据库会话的时间语义。它统一了裁决来源，仍需维护该时钟的准确性；影响 0 行也可能是未开放、已满或目标不存在，返回语义要区分。

课件建议关注 `node_timex_offset_seconds`、`node_timex_sync_status`。NTP 的精度受网络与配置影响，课件中的局域网亚毫秒、广域网数十毫秒是量级参考，不是任何环境下的保证。

### 13.2 墙钟、单调时钟与逻辑时钟

| 需要什么                       | 使用什么                                    | 边界                                                 |
| ------------------------------ | ------------------------------------------- | ---------------------------------------------------- |
| 记录某个日历时刻、判断开放时间 | 有统一语义的墙钟；常以 UTC 存储，展示时转换 | 可能被校正，跨机器有偏差                             |
| 计算耗时与超时                 | 单调时钟                                    | 用于本机时间间隔，不能直接拿来比较不同机器的绝对时刻 |
| 定义业务操作先后               | 权威服务的受控顺序，或有明确语义的提交序列  | 不等于各客户端点击时间                               |
| 表达因果顺序                   | Lamport 等逻辑时钟                          | 不表达真实经历了多少秒                               |

如果事件 A 因果上先于 B，Lamport 时间戳满足 `L(A) < L(B)`；反向不成立。可以结合节点标识给并发事件规定确定顺序，但这不是发现它们的绝对物理先后。[Lamport：Time, Clocks and the Ordering of Events](https://www.microsoft.com/en-us/research/publication/time-clocks-ordering-events-distributed-system/)

**补充理解：**数据库自增 ID 提供分配序列，不保证事务按 ID 顺序提交，也不保证无空洞。不能直接用它证明“谁先点击”或“谁先提交”。

课件列出常见雪花 ID 布局：41 位毫秒时间、10 位机器号、12 位序号；实现应处理时钟回拨和机器号冲突。它是一个常见布局，不是所有实现都固定如此。

Spanner 的 TrueTime 用带不确定性界限的时间接口，并结合提交等待提供排序保证；课件引用的 1～7 ms 来自其论文背景，不应当作所有环境的固定精度。[Spanner 原始论文](https://research.google/pubs/spanner-googles-globally-distributed-database/)

## 14. 地月：秒级往返会改变协议参数和业务规则（pp.22–23）

### 14.1 握手、窗口、超时都要重算

按地月距离 384,000 km：

```text
单程 ≈ 384,000 / 300,000 = 1.28 s
往返 ≈ 2.56 s
```

| 项目                                  | 按题设计算                     | 含义                                          |
| ------------------------------------- | ------------------------------ | --------------------------------------------- |
| 新建 TCP、TLS 1.3，再完成一次请求响应 | `3 × 2.56 = 7.68 s`            | 普通完整握手、无恢复或 0-RTT 等优化的简化模型 |
| 复用已有连接的一次请求响应            | 至少约 2.56 s                  | 省去了握手，仍不能消除传播时间                |
| 100 Mbps 链路的带宽时延积             | `100 × 10⁶ × 2.56 / 8 = 32 MB` | 要充分利用带宽，需要容纳相应量级的在途数据    |
| 约 64 KiB 窗口下的吞吐上限            | `64 / 2.56 ≈ 25 KiB/s`         | 没有窗口缩放等机制时，小窗口限制吞吐          |

实际吞吐还取决于拥塞窗口、丢包、协议与接收端能力。探针超时、心跳和重试也要区分本地与远程依赖；将 1 s 超时原样用于一次地月交互，会把正常传播误判为失败。

### 14.2 中继解决可达性，不能消除传播下限

月球背面不能直接看到地球，需要中继。课件以“鹊桥”和“鹊桥二号”为例：多一跳解决遮挡，也增加延迟、调度与故障依赖。

月球表面时钟相对地球表面存在约 **每天快 56 μs** 的效应；需要明确参考系与时间尺度，而不能只把“时区改一下”。[NIST：月球上的时间](https://www.nist.gov/news-events/news/2024/08/what-time-it-moon)

```text
一年累积差 ≈ 56 μs × 365 = 20.44 ms
一天的等效单程测距误差 ≈ c × 56 μs ≈ 16.8 km
10 m 对应的光行时间 ≈ 10 / (3 × 10⁸) s ≈ 33 ns
```

这里的 16.8 km 是按 `距离误差 = c × 时间误差` 的等效量级，不是完整定位系统的实际误差预算。课件还记录了协调月球时方案的规划，用来强调时间基准也需要基础设施与协议。

### 14.3 月球分校还能“先到先得”吗

科幻设定：地球 20,000 人、月球 300 人、火星 60 人，共抢 120 个名额。

按 200 次/s 且前 120 次都有效，理想售罄时间约：

```text
120 / 200 = 0.6 s
```

月球同一时刻发出的请求，单程就要约 1.28 s。按服务器收到的先后分配，无法提供与距离无关的点击公平性。

如果月球应用跨地月调用地球数据库，并把一次地月往返放进持锁窗口：

```text
课件粗取持锁 ≈ 2.57 s
单行能力 ≈ 1 / 2.57 ≈ 0.39 次/s
120 次成功扣减 ≈ 120 × 2.57 ≈ 308 s ≈ 5.1 min
```

不要把它与“整个事务在地球执行，月球只发业务请求”混淆：后者内部锁仍可很短，但用户等待和按到达顺序分配的不公平仍在。

### 14.4 比较三种业务方案

| 方案                       | 优点                                       | 代价                                     |
| -------------------------- | ------------------------------------------ | ---------------------------------------- |
| 跨地月远程扣减同一行       | 共享一个权威余量                           | 持锁包含长往返时吞吐极低，远端还晚到     |
| 各地预分配配额，本地扣减   | 本地事务，各自可继续工作                   | 配额取整、保底、回收与调拨规则复杂       |
| 本地收志愿，截止后统一抽签 | 距离不直接决定抢占顺序，避免实时争抢热点行 | 等待结果；需要统一规则并为远端传输留时间 |

按人数比例分配：

```text
总人数 = 20,000 + 300 + 60 = 20,360
地球：120 × 20,000 / 20,360 ≈ 117.88
月球：120 × 300 / 20,360 ≈ 1.77
火星：120 × 60 / 20,360 ≈ 0.35
```

名额是整数，火星可能分不到；向下取整还会剩余名额。因此必须制定保底与余数分配方式，不能让四舍五入算法替代公平性规则。

课件的抽签方案为本地收集 30 min 志愿，截止后送到地球并返回结果。火星单程约 3～22 min，需要提前截止，或让全局抽签等待最远端数据到齐，并处理链路中断。

**当延迟超过业务竞争窗口，改变业务规则可以同时改善公平性与技术瓶颈。**抽签把实时争抢转为截止后的批处理，但仍需正确的总名额与去重约束。

## 15. 太阳系：从持续连接转向按窗口通信和本地自治（pp.24–25）

### 15.1 传播延迟之外，还有等待窗口

地火往返约 6～45 min；课件还给出约每 26 个月一次日凌、前后约两周暂停发送指令的任务安排量级。实际暂停范围由任务计划决定。

典型路径：

```text
火星车生成数据
  → 等轨道器经过，上传并存储
  → 等轨道器与地球可通信
  → 深空站接收
  → 地面团队处理
```

NASA 深空网的戈德斯通、马德里、堪培拉站在经度上分散，帮助覆盖地球自转带来的可见性变化；有站点可见不等于天线资源永远可供当前任务使用。

DTN 的 Bundle Protocol v7 采用存储转发思路，容忍间歇连通，不要求端到端路径在同一时刻全部可用。代价包括中间存储、有效期、队列管理与更长的交付时间。[RFC 9171：Bundle Protocol v7](https://www.rfc-editor.org/rfc/rfc9171.html)

**通信链路成为按时段分配的资源。**不仅要估计数据量，还要估计下一次能发的时刻、窗口持续多久，以及积压能否清空。

### 15.2 人不能逐步参与快速控制环

地面问“哪里坏了”，即使立即回复，也要等一个往返，再叠加窗口等待。控制方式因此变为：

- 提前下发计划与期望状态，由本地控制环执行。
- 本地完成避障、健康检查与必要的故障恢复。
- 无法自行处理时进入安全模式，保留通信和等待地面处置的能力。

课件以每天约一个火星日上传计划为例。一个火星日约 24 h 40 min，说明人的值班节奏也要适应系统所在环境。

### 15.3 火星探路者：优先级反转与远程修复

课件把 1997 年故障抽象成三种任务：低优先级任务持有互斥量，高优先级任务等待该锁，中优先级任务不断抢占低优先级任务，导致锁迟迟不能释放，高优先级工作错过期限并触发复位。

**优先级继承**让持锁者临时继承等待者的高优先级，使其有机会尽快完成临界区并释放锁。它解决调度依赖问题，不等同于解除死锁，也不表示可以忽略临界区长度。

**资料核对：**课件写“通过 VxWorks 的 C 解释器上传小程序修改参数”。飞行软件负责人 Glenn Reeves 的当事人记录明确说，实际没有通过 VxWorks shell 修改，而是使用带校验的专用差分补丁机制；调试能力也是有意保留。团队先在地面复现、分析并测试，再修改相关全局配置以启用优先级继承。[Reeves：What Really Happened on Mars?](https://retis.santannapisa.it/~giorgio/mars/reeves.html)

本课的运维结论仍成立：**可观测性、地面复现环境与远程修复能力要在发射前设计好，修复通道也需要认证与校验。**

## 16. 火星分校的一次升级：把回退决定写进系统（p.26）

科幻任务：在下一次日凌前，把火星分校选课系统从 v2.0 升级到 v2.1。

| L-13 的做法              | 火星场景中的调整                                    | 原因                             |
| ------------------------ | --------------------------------------------------- | -------------------------------- |
| 金丝雀、异常时回退       | 保留 A/B 两套可启动版本；新版本失败时本地自动回旧版 | 救援不能等待地面交互             |
| 值班人员看判据、决定继续 | 将健康判据、停止条件和回退动作写入计划              | 人的反馈慢于故障发展             |
| 观察 5 min～2 h          | 按火星日和通信轮次安排观察                          | 一轮反馈可能还要等待窗口         |
| staging 验证             | 地面同构环境验证正常、失败与恢复路径                | 现场无法随时介入                 |
| 配置快速推送             | 升级包分块、校验、支持续传并按窗口传送              | 链路会中断，传输不能从头反复开始 |
| 开放日前冻结             | 日凌前留足冻结与恢复时间，课件举例为前两周          | 长时间失联时主要依赖自治         |

**补充理解：** A/B 分区主要保护代码和启动路径；若新版本已不兼容地修改数据库或持久状态，仅切回旧程序并不保证恢复。升级计划仍要设计数据兼容、迁移和恢复验证。

## 17. 系统活得比技术久：旅行者与地面系统的到期问题（p.27）

### 17.1 一光日距离意味着两天才有一次反馈

截至本讲日期，NASA 预计旅行者 1 号于 **2026-11-18** 距地球一光日，约 259 亿 km；此处是预计里程碑，不能写成已经发生。到该距离时，信号单程约 24 h，往返约 48 h。[NASA：旅行者任务状态](https://science.nasa.gov/mission/voyager/where-are-voyager-1-and-voyager-2-now/)

课件以科学数据下行约 160 bit/s 估算：

```text
160 bit/s × 86,400 s / 8 = 1,728,000 B ≈ 1.73 MB/天
```

这是全天连续发送、不扣协议开销的理想值。遥测带宽很低时，能留下什么诊断信息本身就是设计问题。

2023 年末，飞行数据子系统的一部分存储失效，使数据无法正常解读。工程师将受影响代码分散放到剩余可用内存，并调整相关引用；2024-04-18 发送首批修改，随后确认恢复工程数据。当时单程通信约 22.5 h，不能按本地调试方式快速试错。[NASA/JPL：2024 年旅行者修复记录](https://www.jpl.nasa.gov/news/nasas-voyager-1-resumes-sending-engineering-updates-to-earth/)

运行几十年的系统依赖硬件与能源余量、可修复设计，以及后继工程师仍能理解的文档。

### 17.2 地面系统也有必须提前处理的期限

| 项目                    | 课件提示与核对                                         | 对系统的影响                                 |
| ----------------------- | ------------------------------------------------------ | -------------------------------------------- |
| MySQL 8.4 `TIMESTAMP`   | 整秒上限为 `2038-01-19 03:14:07 UTC`                   | 提前排未来活动时就可能越界，无需等到当天     |
| 公共信任 TLS 服务器证书 | 已公布规则安排于 2029-03-15 起将最长有效期缩短至 47 天 | 续期、部署和失败恢复需要自动化               |
| MySQL 8.0 生命周期      | 2026 年 4 月进入 EOL / Sustaining Support 阶段         | 要区分支持类别、版本升级计划与托管服务商政策 |

`DATETIME` 的范围比 `TIMESTAMP` 大，但没有相同的自动时区转换行为；更换字段类型也需要同时检查接口与业务语义。[MySQL：日期时间类型](https://dev.mysql.com/doc/refman/8.4/en/datetime.html)

47 天规则针对其范围内的公共信任 TLS 服务器证书，不能泛化为所有私有证书、代码签名或其他证书。按长期平均覆盖计算，`365/47 ≈ 7.8` 个有效期/年，实际通常要提前续期。[CA/B Forum：TLS 基线要求](https://cabforum.org/working-groups/server/baseline-requirements/requirements/)

“MySQL 8.0 结束支持”需要限定含义：官方公告写明自 2026-04-21 起转入 Oracle Sustaining Support，不能理解为任何形式的支持服务全部消失。[MySQL：生命周期公告](https://www.mysql.com/support/eol-notice.html)

## 18. 星际：共享协议与格式，不能依赖及时救援（p.28）

### 18.1 比邻星探测器的时间推演

科幻设定：目标距离 4.24 光年，探测器以 `v=0.2c` 匀速飞行，忽略加减速、目标运动与引力影响。

```text
地球参考系的飞行时间 t = 4.24 / 0.2 = 21.2 年
洛伦兹因子 γ = 1 / √(1 − 0.2²) ≈ 1.0206
船上经历的固有时间 τ = t / γ ≈ 20.7717 年
两者差 ≈ 0.4283 年 ≈ 156 天

到达信号传回地球还需约 4.24 年
地球获知到达的时间 ≈ 发射后 25.44 年
```

“相差 156 天”比较的是上述参考系飞行时间与航行路径上的固有时间，不是两个任意远端墙钟可以直接相减的普遍公式。

### 18.2 没有独立于参考系的全局同时

狭义相对论中，空间分离且无因果先后关系的事件，其“同时”与先后可能随参考系改变；因果关系则受光锥约束。可以约定坐标时间，但不能把它当成宇宙中唯一的绝对现在。

课件用超光速通信的科幻设定作对照；已知物理中的量子纠缠不能用于可控的超光速信息传输。工程上应给时间戳注明时间尺度、参考系或时钟来源。

### 18.3 自治的能力与成本

课件列出的原则：冗余与三取二表决、安全模式与降级、本地控制环、经过认证的有限更新，以及格式与单位自描述。

成本是质量、功耗、复杂度、验证工作与维护接口带来的攻击面。三取二也需要故障相对独立；共同软件缺陷可以同时影响多个副本。

**补充理解：**课件“没有回滚”“星际单向”强调无法依靠及时地面救援，并非物理上只能单向通信，或软件绝对不能预置本地回退。能否回退仍由存储、启动和状态兼容设计决定。

### 18.4 接收者不能追问时，协议必须解释自己

课件以阿雷西博信息的 `1679 = 23 × 73` 位布局、旅行者金唱片用氢原子跃迁作为时间单位线索，说明格式不能完全依赖发送者脑中的约定。

反例是火星气候探测者的单位不一致：一端按磅力·秒输出，另一端按牛顿·秒使用。软件接口不仅要约定字段名称，还要约定单位、坐标系、时间基准、编码、版本与异常值语义。

## 19. 全讲归纳与公式速查（pp.29、31）

### 19.1 尺度改变后，哪些东西还能共享

| 尺度       | 往返量级         | 链路特征               | 主要共享对象               | 运维方式                   |
| ---------- | ---------------- | ---------------------- | -------------------------- | -------------------------- |
| 机房       | 0.2 ms，本题设定 | 通常稳定，仍会故障     | 同一个数据库与近实时状态   | 人与自动恢复共同参与       |
| 地球跨地域 | 30～200 ms       | 可能分区               | 复制的数据，需要一致性取舍 | 远程值班，明确故障域与切换 |
| 地月       | 约 2.6 s         | 遮挡与中继             | 配额、规则、本地状态       | 本地处理加远程协助         |
| 太阳系     | 6～45 min        | 通信窗口、日凌影响     | 规则与批量交换的数据       | 预先下发计划，本地自治     |
| 星际       | 年级             | 交互难以进入及时控制环 | 长期可理解的协议与格式     | 主要依赖自主恢复与降级     |

教学主线可记为：**共享数据库 → 共享数据 → 共享规则 → 共享协议与格式。**这是一种设计取向，不是说更大尺度禁止任何数据复制。

### 19.2 公式与适用条件

| 要算什么             | 公式                                    | 关键条件                                 |
| -------------------- | --------------------------------------- | ---------------------------------------- |
| 三层 B+ 树容量       | `F² × L`                                | F 为内部页扇出，L 为叶子行数；理想化填充 |
| 数据增长             | `人数 × 每学期记录 × 每年学期数 × 年数` | 保留策略与业务模型固定                   |
| 单热点行能力         | `μ ≈ 1/S`                               | S 是持锁服务时间，不是含排队的响应时间   |
| 热点利用率           | `ρ = λS`                                | 对同一串行资源，单位一致                 |
| 连接耗尽时间         | `可用连接数 / (λ−μ)`                    | λ>μ、持续到达、每事务占一连接的近似      |
| 无组提交的同步写基线 | `1/(m × fsync时间)`                     | 只计 m 次串行同步，忽略其他瓶颈          |
| 传播往返下限         | `2d/v`                                  | d 为单程路径长度，v 为传播速度           |
| 带宽时延积           | `带宽 × RTT`                            | 带宽用 bit/s 得 bit，换 byte 要除以 8    |
| 窗口约束下的吞吐     | `窗口 / RTT`                            | 另受拥塞、丢包与处理能力限制             |
| 时钟漂移             | `ppm × 10⁻⁶ × 经过时间`                 | 固定速率、期间未校正的近似               |
| 单程测距的等效误差   | `c × 时间误差`                          | 不等于完整定位误差模型                   |
| 匀速航行固有时间     | `τ = t√(1−v²/c²)`                       | 指定参考系，忽略加减速和引力             |

### 19.3 最容易混淆的概念

| 概念对                         | 区别                                            |
| ------------------------------ | ----------------------------------------------- |
| 建了索引 / 使用索引 / 高效访问 | 存在结构 / 优化器选择 / 实际减少足够多的工作    |
| 事务 / 正确业务逻辑            | 提供原子性与隔离机制 / 仍需正确条件和约束       |
| 快照读 / 当前读                | 按读视图取可见版本 / 依据当前记录并处理锁冲突   |
| 乐观并发控制 / 无锁更新        | 用版本检测冲突 / 数据库 UPDATE 仍可能加锁和等待 |
| 日志已收到 / 日志已回放        | 复制传输完成 / 该修改已能被相应查询看见         |
| 行锁上限 / 整库吞吐上限        | 单热点串行能力 / 所有资源与并发路径共同约束     |
| RTT / 带宽                     | 等一次反馈多久 / 每秒能传多少                   |
| 墙钟 / 单调时钟 / 逻辑时钟     | 日历时间 / 本地时间间隔 / 因果排序              |
| 自动重启 / 自治                | 一种恢复动作 / 在失联时依据计划完成判断与处置   |

## 20. 复习自测

1. **先 INSERT 再扣减，余量不足时为什么必须回滚？**

   否则会留下没有占到名额的选课记录，破坏记录与余量的一致性。

2. **最终余量始终为 0，能证明没有超卖吗？**

   不能。两个事务可以根据旧读数都写入 0，却各保留一条选课记录。

3. **为什么同一课每秒约 769 次，不是两次 fsync 算出的 1000 次？**

   热点锁服务时间还包含语句和往返，约 1.3 ms；1000 TPS 只是只算刷盘的基线。

4. **应用移到异地后，为何加连接池也救不了热点？**

   持锁增加到约 31 ms，单行处理能力约 32/s；更多连接主要增加等待者。

5. **320 万行为什么不意味着需要分表？**

   本例约三层树，上层只有约 13 页，整体数据与索引也可能远小于 buffer pool。

6. **RR 事务里普通查询看不到一行，UPDATE 能改到吗？**

   可能。普通一致性读和 DML 不使用完全相同的可见性规则，自己的修改随后可见。

7. **乐观锁是否能避免数据库行锁等待？**

   不能保证。条件 UPDATE 仍需要数据库锁；乐观锁主要通过版本判断是否发生业务冲突。

8. **半同步确认后为什么“我的课表”仍可能没有新记录？**

   从库可能只接收了日志，还未完成回放，或者查询去了另一个落后副本。

9. **一个 20 ppm 的时钟三天能快多少？**

   `20 × 10⁻⁶ × 259,200 = 5.184 s`；在本题平均分流下可提前放入约 173 次尝试。

10. **地月已有 100 Mbps 带宽，为什么 64 KiB 窗口仍只有约 25 KiB/s？**

    吞吐受到 `窗口/RTT` 限制；该带宽与 RTT 的乘积约为 32 MB，需要足够大的在途容量。

11. **把月球请求放到地球服务器执行，就解决公平性了吗？**

    它能避免数据库事务跨地月持锁，但按到达时间抢名额时，月球仍晚约 1.28 s。

12. **志愿加抽签为什么还改变了数据库瓶颈？**

    分配从实时争抢同一行变成截止后的批处理；仍需去重和保证名额总量。

13. **火星升级为什么不能只设计“出问题通知值班”？**

    通知和反馈需要分钟到更久，必须预置本地判据、安全模式与自动恢复路径。

14. **主键更大的选课记录一定提交得更晚吗？**

    不一定。自增 ID 的分配先后不等于事务提交先后，更不等于用户点击先后。

15. **比邻星探测器 21.2 年到达，为什么地球约 25.44 年才知道？**

    抵达消息还需约 4.24 年传播；这是相对于本题地球参考系的简化结果。
