## 2. 先认识资源、负载与目标（pp.6–8）

### 2.1 可压缩资源与不可压缩资源

这里的“可压缩”指需求暂时得不到满足时，工作能通过少运行、排队等方式继续推进，不是文件压缩。

| 资源 | 课件分类 | 不足或超限时的典型后果 | 观察线索 |
| --- | --- | --- | --- |
| CPU | 可压缩 | 排队、节流，处理变慢 | 运行队列、`cpu.stat` |
| 网络带宽 | 可压缩 | 限速、排队，也可能丢包重传 | RTT、重传、队列 |
| 磁盘 IOPS | 可压缩 | I/O 排队，完成时间变长 | `await`、I/O 队列 |
| 内存 | 不可压缩 | 回收无效后分配失败或 OOM | `memory.events`、OOM 事件 |
| fd、进程数、端口 | 不可压缩 | 创建失败、报错、拒绝 | `Too many open files` 等 |
| 磁盘空间 | 不可压缩 | 写入失败，可能导致服务不可用 | 剩余空间、写入错误 |

**补充理解：**这是一种资源规划分类，不是所有故障表现的绝对划分。CPU 排队过久也会导致请求超时；内存回收、GC 或换页也会先让程序变慢。关键区别在于：**不能保证把正在使用的内存削掉一部分后，程序仍像少拿 CPU 一样正常运行。**

### 2.2 负载类型决定谁让步

| 负载 | 本讲例子 | 主要要求 | 资源紧张时的选择 |
| --- | --- | --- | --- |
| 在线无状态服务 | Tomcat | 延迟敏感，迁移成本相对低 | 优先满足在线请求的资源需求 |
| 离线批处理 | 选课结果统计 | 延迟不敏感，可中断、可重跑 | 可以放慢或终止，承担完成延迟 |
| 有状态服务 | MySQL、Redis | 数据与实例关联，迁移和恢复成本高 | 本案例倾向独占、减少争用和迁移 |

本讲批处理运行在 **8:30–10:00**，用于统计选课结果、供教务导出；它不是思考题 2 中的“离线推荐”。

“可重跑”也有成本：已完成工作可能丢失，需要检查点、幂等和重跑机制。对在线服务的保护，意味着统计结果可能晚交付，必须把这项取舍告知使用者。

### 2.3 利用率、延迟与成本相互制约

沿用 L-07 的 M/M/1 示意模型：

```text
平均响应时间 / 平均服务时间 = 1 / (1 − ρ)
ρ：模型中的利用率，要求 ρ < 1
```

| ρ | 响应时间相对服务时间的倍数 |
| --- | --- |
| 0.5 | 2 |
| 0.7 | 约 3.3 |
| 0.8 | 5 |
| 0.9 | 10 |

高利用率可以减少机器数量，却会压缩应对突发的余量；共享提高利用率，也引入邻居干扰。目标是**在 SLO 约束下提高利用率**。

本案例沿用的 SLO 是：开放日前 10 分钟，提交 p99 ≤ 1 s。70% 是教学规划线，不是普适安全阈值；上述单服务台模型描述平均值，不能直接预测多核 Tomcat 的 p99。

## 3. cgroup v2：让资源规则生效（pp.10–11）

### 3.1 namespace 与 cgroup 分别解决什么

```text
namespace：进程能看见什么
cgroup：一组进程可以使用多少资源，以及如何参与分配
```

容器仍然是宿主机上的进程。节点还有资源，不代表某个容器仍有额度。

| 控制器 | 关键文件 | 本讲含义 |
| --- | --- | --- |
| CPU | `cpu.weight` | 争用时的相对份额；普通非 idle 组默认 100，范围 1–10000 |
| CPU | `cpu.max` | CPU 时间配额，格式为 `MAX PERIOD`，单位 μs；`max 100000` 表示不设该层配额上限 |
| CPU | `cpu.stat` | CPU 用量、节流周期数、累计节流时间 |
| 内存 | `memory.high` | 超过后施加回收压力并限速；越过它本身不触发 OOM killer |
| 内存 | `memory.max` | 硬上限；达到上限且无法回收时，可能在该 cgroup 内触发 OOM |
| 内存 | `memory.events` | `high`、`max`、`oom`、`oom_kill` 等事件计数 |
| 块设备 I/O | `io.weight`、`io.max`、`io.stat` | I/O 份额、上限和统计，本讲不展开 |
| 进程 / 线程 | `pids.max` | 限制任务数量，本讲不展开 |

例如，在课件的 cgroup v2、100 ms 周期下，`CPUQuota=300%` 对应：

```text
cpu.max = 300000 100000
          300 ms  100 ms

每 100 ms 墙钟时间，这组进程合计最多消耗约 300 ms CPU 时间。
```

**补充理解：**限制有层级，子 cgroup 不能突破父级限制。排查时需要查看当前组及祖先组，不能只看容器内部显示的一层配置。[Linux：Control Group v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)

### 3.2 份额与配额不能互相替代

假设节点有 8 核，A、B 均有足够的 CPU 密集型工作，权重为 `300 : 100`：

| 场景 | A 可得到的 CPU | B 可得到的 CPU | 原因 |
| --- | --- | --- | --- |
| A、B 都持续争用，无额外上限 | 约 6 核 | 约 2 核 | 按 3:1 分配 |
| B 空闲，A 无硬配额 | 最多用满 8 核 | 0 | 空闲份额可以借用 |
| B 空闲，A 的配额为 4 核 | 平均最多约 4 核 | 0 | 硬配额仍然封顶 |

这些是理想化份额算术，前提是可运行并发足够、无其他瓶颈和上层限制。

- **份额回答“争用时谁多拿”。** 没有争用时，通常看不出权重区别。
- **配额回答“最多拿多少”。** 即使节点空闲，也可能阻止继续使用 CPU。
- 验证份额要制造争用；验证配额要制造周期内突发。只测空闲节点上的平均 CPU 不够。

## 4. CPU 节流：看周期内并发，不能只看平均值（pp.12–13）

### 4.1 配额算术

设周期为 `P` ms，CPU limit 为 `L` 核：

```text
每周期 CPU 时间额度 Q = L × P       单位：CPU-ms

若 n 个线程持续同时占用 n 个 CPU，且 n > L：
额度耗尽的墙钟时间 t_run = Q / n = L × P / n
随后被节流的时间 t_stop = P − t_run
```

若 `n ≤ L`，本简化模型不会因为这些线程的 CPU 消耗而提前耗尽配额。公式忽略调度开销、配额切片和额外突发机制，且要求有足够可用 CPU 真正并行运行。

课件取 `P = 100 ms`、`L = 3`，即每周期 300 CPU-ms：

| 同时运行的忙线程数 n | 额度耗尽前的墙钟时间 | 随后被节流时间 |
| --- | --- | --- |
| 3 | 100 ms | 0 |
| 6 | 50 ms | 50 ms |
| 12 | 25 ms | 75 ms |
| 24 | 12.5 ms | 87.5 ms |

```text
n = 12 的理想示意：
周期开始 |-- 12 个线程同时运行 25 ms --|------ 被节流 75 ms ------| 下周期
合计 CPU 时间 = 12 × 25 ms = 300 CPU-ms
```

3 核配额并不等于“只能同时使用 3 个核”。它限制一段周期中的 CPU 时间总额，短时可以用更多核，也就可能更早耗完额度。[Linux：CFS Bandwidth Control](https://docs.kernel.org/scheduler/sched-bwc.html)

**本案例的边界：**实践部分每个节点只有 8 核，因此 12 个线程不能同时各占一核。课件 p.27 引用的“25 ms 运行、75 ms 停顿”应作为 p.12 的理想示例理解，不能直接当作该 8 核节点的实测时间线。即使单个容器短时独占全部 8 核，耗完 300 CPU-ms 也至少需要 `300 / 8 = 37.5 ms`；存在其他负载时还会变化。

### 4.2 为什么平均 CPU 低于 limit 仍会被节流

监控上的平均值可能跨越数秒或数分钟，配额却按更短周期生效。某些周期早早耗尽额度，另一些周期又没有工作，长期平均仍可能低于上限。

请求在节流期间不能获得 CPU，等待进入响应时间；如果跨越多个周期或叠加其他排队，尾延迟会继续累积。**一次停顿几十毫秒，既不等于 p99 只增加几十毫秒，也不能单独证明 p99 一定超过 1 s。**

### 4.3 三个节流计数怎样读

| 计数 | 表示什么 | 不能解释成什么 |
| --- | --- | --- |
| `nr_periods` | 配额控制统计的周期数 | 请求数 |
| `nr_throttled` | 发生过节流的周期数 | 失败请求数 |
| `throttled_usec` | 累计节流时长；多 CPU 运行队列可分别累计 | 单个请求等待时间或简单墙钟占比 |

分析一个观测窗口时，应取计数增量：

```text
节流周期比例 = Δnr_throttled / Δnr_periods
```

课件的 **38%** 表示该窗口约 38% 的周期发生过节流，不表示 38% 的 CPU 时间不可用，也不表示 38% 的请求超时。分母为 0 时不能直接计算；累计计数重置也要处理。

将节流增量与 p99、请求量、并发数放在同一时间轴，再通过调整配额或并发复测，才能判断对业务的影响程度。节流计数证明发生了节流，不自动证明所有慢请求都由它造成。

课件安排的演示是在 3 核配额下，让纯计算程序以 3、6、12 个线程各运行 4 秒，对照 `cpu.stat`。演示程序的实测结果不能替换 Tomcat 案例的 38% 设定值；课件另提示实验 3 会复现并测量节流现象。

### 4.4 三种改法及其代价

| 改法 | 本讲示例 | 代价与前提 |
| --- | --- | --- |
| 提高 CPU limit | `2.55 / 0.7 ≈ 3.64`，取 4 核 | 需要校验节点竞争、总容量及 SLO；不能保证从此没有节流 |
| 保留 request，取消 CPU 硬 limit | 允许借用空闲 CPU | 失控负载可使用更多空闲核，共享资源干扰仍存在 |
| 限制 CPU 密集型并发 | 避免过多忙线程同时消耗配额 | 排队移到执行池外，需要有界队列和超时 |

“并发不超过 limit 核数”针对真正运行的 CPU 密集型工作，不能机械地把所有 Tomcat 请求线程都限制为 3 或 4 个；I/O 等待线程、GC 线程与其他后台线程也要分别考虑。

运行时还应正确识别容器资源。课件列出：JDK 10 起支持相关容器感知，回移到 8u191；cgroup v2 支持见 JDK 15，以及 11.0.16、8u372 回移版本。部署时应核对实际发行版与补丁，不能只看到“Java 8/11”就认为支持完整。

Go 1.25 的默认 `GOMAXPROCS` 会参考 Linux cgroup CPU limit，并支持动态更新；它不按 CPU request 取值，手动设置会关闭相应自动行为。容器感知也不等于所有应用线程池都会自动获得合适配置。[Go 1.25 Release Notes](https://go.dev/doc/go1.25#runtime)

## 5. 内存：按完整峰值加余量，区分回收与 OOM（p.14）

### 5.1 堆大小不是容器总内存

课件给出一个 Tomcat 的峰值账：

| 构成 | 设定用量 |
| --- | --- |
| 堆 | 4.0 GB |
| 堆外 | 0.5 GB |
| 线程栈 | 0.2 GB |
| 元空间等 | 0.2 GB |
| 连接缓冲 | 0.2 GB |
| 合计峰值 RSS | **5.1 GB** |

```text
平时 RSS = 4.5 GB
原 memory limit = 5.0 GB
峰值需求 = 5.1 GB > 5.0 GB

建议 limit ≈ 5.1 × 1.08 = 5.508 GB，课件取约 5.5 GB
```

8% 是案例余量，不是 JVM 通用比例；`5.5 / 5.1 − 1 ≈ 7.84%`，因此课件写“约 8%”。

**补充理解：**cgroup 内存统计还包含页缓存、部分内核内存和 socket 缓冲等，不能直接把进程 RSS 当成完整计费口径。生产定额要结合 `memory.current`、`memory.stat` 和峰值来源核算，避免漏算或重复相加。[Linux：Memory controller](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory)

### 5.2 两个阀门与三种不同事件

| 情况 | 发生在哪一层 | 典型含义 |
| --- | --- | --- |
| 超过 `memory.high` | cgroup 内存控制 | 加强回收、使任务变慢；超过 high 本身不触发 OOM killer |
| 达到 `memory.max` 且无法回收 | 容器 / cgroup 内 | 即使节点有空闲，也可能在该组内 OOM |
| 节点整体内存压力 | 整个节点 | kubelet 可能驱逐 Pod；来不及处理时可能发生节点 OOM |

课件“内存没有慢一点，只有够和被杀”强调不能像 CPU 一样安全压缩必需工作集；它不是说内存不足时绝不会先出现回收或 GC 停顿。

OOM 归因需要结合 `memory.events`、容器终止原因和内核记录。**137 通常对应被 SIGKILL 终止，单凭退出码不能认定 OOM。** 同样，JVM 抛出 `OutOfMemoryError` 与内核杀进程是不同事件。

页缓存往往可回收，但不能假设所有缓存都能立即释放；也不能只凭“节点还有三成空闲”排除容器自己的硬上限。

## 6. 隔离有盲区，强度要匹配负载（p.15）

| 共享对象 | 普通 CPU / 内存配额未解决什么 | 本讲的应对方向 |
| --- | --- | --- |
| 末级缓存、内存带宽 | CPU 时间相同，执行效率仍可能因邻居变差 | 专用节点、结合拓扑安排 CPU |
| 磁盘队列、云盘额度 | 限制单组 I/O 上限，不等于保证底层服务能力 | MySQL 独占节点，观察 fsync 与 `await` |
| conntrack、PPS | 节点级共享额度仍可能耗尽 | 查连接、丢包、内核事件与规格 |
| 内核锁、页缓存争用 | 干扰发生在共享内核中 | 减少混部，定位具体争用 |

课件给出“进程 → 容器 → 虚拟机 → 裸机”的隔离强度示意，同时提醒更强隔离往往降低密度、增加成本。

**补充理解：**这不是对所有资源的严格排序；同宿主机虚拟机仍共享物理硬件，绑核也未必隔开 LLC 或内存带宽。需要确认具体隔离了什么。

本案例让 Tomcat 与可重跑批处理使用容器混部，让对 fsync 敏感的 MySQL 独占节点。这是按负载风险作出的选择，不意味着所有有状态服务都必须独占物理机。

## 7. request、limit 与 QoS（pp.17–19）

### 7.1 两个数分别管什么

| 配置 | CPU | 内存 |
| --- | --- | --- |
| request | 调度占位；运行时通常影响争用权重 | 调度占位；参与内存压力下的驱逐判断 |
| limit | 通常落实为 CPU 带宽配额，超出会节流 | 通常落实为内存硬上限，无法回收时可能 OOM |

课件用“request 管不被挤，limit 管不拖累别人”帮助记忆。

**补充理解：**request 不是独占核心，也不是延迟保证；limit 不能覆盖第 6 节的全部共享资源。调度应比较 **Σrequest 与 Node Allocatable**，后者扣除了系统等预留，不能一概用整机标称容量。CPU request 到权重的换算由运行时完成，不应把 `2600m` 直接写成 `cpu.weight = 2600`。[Kubernetes：Resource Management](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)

默认规则需带上条件：

- 只写某项资源的 limit，未写 request，且准入阶段没有应用默认 request 时，Kubernetes 会用该 limit 补齐 request。
- CPU、内存均未配置，且没有默认注入或上层约束时，才是课件所说的“既无保证也无上限”。
- 内存 request 不等于 `memory.high`；cgroup v2 下是否据此设置内存保护，还取决于运行时和启用的功能。

### 7.2 三档 QoS 怎样判定

按本讲的容器级资源配置模型：

| QoS | 判定条件 | 典型用途 / 特征 |
| --- | --- | --- |
| BestEffort | 所有容器均未设置 CPU、内存 request 和 limit | 没有这些显式资源保证和上限，压力下脆弱 |
| Burstable | 至少设置一项 CPU / 内存 request 或 limit，但不满足 Guaranteed | 可以保留保证量，同时允许突发 |
| Guaranteed | 每个容器 CPU、内存均有正的 request、limit，且各自相等 | 预留更充分，通常更不易在资源压力下被淘汰 |

**QoS 是 Pod 的属性。** 多容器 Pod 要一起判定，不能只看主容器。这里沿用课件模型，不展开 Pod 级资源配置等其他配置方式。[Kubernetes：Pod QoS](https://kubernetes.io/docs/concepts/workloads/pods/pod-qos/)

特别容易误判的例子：

```text
Tomcat：CPU request 2.6，limit 4
        内存 request = limit = 5.5 GB

QoS = Burstable
原因：CPU request ≠ limit，不能仅凭内存两者相等判为 Guaranteed。
```

### 7.3 驱逐与 OOM 不是一条固定队列

课件以 `BestEffort → Burstable → Guaranteed` 表示内存压力下的典型让步顺序，但实际需要区分：

| 路径 | 决策者 | 主要依据 |
| --- | --- | --- |
| 节点压力驱逐 | kubelet | 是否超过 request、Pod 优先级、用量相对 request 的情况 |
| 内核 OOM | Linux 内核 | OOM 评分及 `oom_score_adj` 等，且受 OOM 作用域约束 |

kubelet 不直接按 QoS 名称排序。课件列出的 OOM 调整值为 Guaranteed `−997`、BestEffort `1000`、Burstable 介于两者之间；它们影响被选择的倾向，不保证绝对不会被杀。尤其是某容器突破自身内存上限，不能期待通过杀掉其他 Pod 来解除它的上限。[Kubernetes：Node-pressure Eviction](https://kubernetes.io/docs/concepts/scheduling-eviction/node-pressure-eviction/)

因此，本讲选择“在线服务内存 request = limit；批处理小 request 加明确 limit”。批处理的低保障是可接受的业务取舍，不能据此让其资源失控。

### 7.4 取值依据：平均、峰值还是高分位

| 取值方法 | 收益 | 风险 / 成本 |
| --- | --- | --- |
| 按平均用量 | 配置较省 | 峰值争用时保障不足；若 limit 也偏低，还可能节流或 OOM |
| 按峰值 | 更能覆盖已知高峰 | 平时利用率可能低，仍需考虑未观测到的突发 |
| 按高分位加余量 | 在成本与风险之间折中 | 依赖正确的时间窗、采样和业务场景 |

课件建议开放日取峰值，平时参考高分位；CPU request 接近需求峰值，CPU limit 按峰值除以 0.7 留余量，内存按完整峰值加余量。本案例数值在第 10 节核算。

## 8. 超卖：凭什么认为大家不会同时要满（pp.20–21）

### 8.1 超卖的口径

本讲用以下关系定义按 limit 计算的超卖：

```text
Σrequest ≤ 可分配容量 < Σlimit
超卖比 = Σlimit / 可分配容量
```

limit 是单个负载允许使用的上限，**不是各负载同时可以兑现的资源承诺**。这也解释了为什么每个容器配置都合法，总需求仍可能超过节点。

### 8.2 依据一：错峰，也就是统计复用

课件的 CPU 序列为：

| 时刻 | t1 | t2 | t3 | t4 | t5 | t6 |
| --- | --- | --- | --- | --- | --- | --- |
| A 用量（核） | 1 | 2 | 4 | 2 | 1 | 1 |
| B 用量（核） | 3 | 1 | 1 | 2 | 4 | 1 |
| 合计（核） | 4 | 3 | 5 | 4 | 5 | 2 |

```text
各自峰值之和 = max(A) + max(B) = 4 + 4 = 8
同一时刻合并后的峰值 = max(A + B) = 5
差值 = 3 核
```

这说明独立峰值相加可能高估同时需求。节省成立的前提是峰值确实错开；开放日在线服务一起迎来高峰，不能沿用平时的错峰假设。

### 8.3 依据二：有一方可以让步

CPU 不够时，可以让批处理少拿 CPU、晚一些完成。课件称之为“优先级兜底”，至少要求：

1. 资源可压缩，降配不会直接破坏工作状态。
2. 被压的一方确实允许降级，且接受延迟或重跑成本。
3. 受保护负载的需求能够被容纳，Σrequest 不超过可分配容量。
4. 份额和限制配置实际生效，并在竞争场景中验证 SLO。

这里的“优先级”是业务取舍；本案例 CPU 分配主要通过 **request 对应的权重**实现，不能理解成写一个高 Pod Priority 就自动获得更多 CPU 时间。

### 8.4 为什么本讲选择内存不超卖

CPU 少分一点，批处理仍可以继续执行；必需内存不足时，却可能发生回收压力、分配失败或进程终止。JVM 堆长大后，也不能假设流量下降就立即把相应内存还给操作系统。

课件引用 JEP 346，说明 G1 有定期归还空闲内存的机制，但默认定期 GC 选项关闭；具体回收还依赖版本、GC 配置、堆下限和工作负载。**“对象被回收”与“内存归还操作系统”是两件事。** [Oracle：G1 Heap Sizing and Periodic GC](https://docs.oracle.com/en/java/javase/14/gctuning/garbage-first-g1-garbage-collector1.html)

本案例采用：

```text
Σ内存 limit ≤ 可分配内存
另为系统、运行时等留足预算
```

**补充理解：**“内存不超卖”是本讲的保守容量策略，不是说 Kubernetes 不能配置内存 limits 之和超过节点内存。系统可以允许这种配置，但必须承担并管理并发增长、驱逐和 OOM 风险；仅凭错峰想象不能证明它安全。

## 9. 请求级资源管理：还要控制放多少工作进来（p.22）

机器级配额控制“谁多拿资源”，请求级控制决定“允许多少工作进入系统”。两层需要配合。

| 方法 | 保护对象 | 必须承担的代价 |
| --- | --- | --- |
| 限流，如令牌桶 | 后端吞吐与资源容量 | 超额请求被拒绝或延后 |
| 并发上限，如池大小 | 线程、连接与在途工作数 | 等待可能移到池外 |
| 有界队列 + 超时 | 防止积压无限增长 | 队列满时拒绝，超时工作取消或丢弃 |
| 按优先级丢弃 | 过载时保住核心功能 | 本案例提交优先，查询等低优先级功能降级 |
| 舱壁 | 防止查询变慢拖住提交等其他路径 | 独立线程池 / 连接池降低共享效率 |

舱壁只隔开配置覆盖的资源；若两组池仍访问同一数据库热点或同一块盘，下游瓶颈仍然共享。

入口阈值不能只按 Tomcat CPU 算：**读请求参考应用 CPU，写请求还受 MySQL 持久化能力约束。** L-07 的“每事务两次、每次 2 ms、完全串行且无组提交”模型给出约 250 TPS 的写入上限；它不是任何 MySQL 实例的固定能力。若继续套用 70% 规划线，教学估算为 `250 × 0.7 = 175 TPS`，实际阈值需压测验证。

## 10. 课程实践：从错误配额到参考配额表（pp.24–29）

### 10.1 拓扑与负载设定

```text
Nginx（池外）
  ├─ 节点 1：8 核 / 16 GB
  │    ├─ Tomcat-1
  │    ├─ Tomcat-2
  │    └─ 选课结果统计批处理
  └─ 节点 2：8 核 / 16 GB
       ├─ Tomcat-3
       └─ Tomcat-4

MySQL：独占 4 核 / 8 GB，不计入上述节点池
```

| 参数 | 设定值 |
| --- | --- |
| 读流量 | 2400 QPS，每请求 3 ms CPU |
| 写流量 | 稳态 300 TPS，首 10 秒 600 TPS，每请求 5 ms CPU |
| Tomcat 实例数 | 4，按均匀分流估算 |
| 单 Tomcat CPU | 稳态约 2.2 核，首 10 秒 2.55 核 |
| 单 Tomcat 内存 | RSS 平时 4.5 GB，峰值 5.1 GB |
| 单 Tomcat 活跃线程峰值 | 约 12；不等于始终有 12 个线程同时占用 CPU |
| 批处理 | 平时约 1 核、1.5 GB；全速最多用 4 核 |
| 提交 SLO | 开放日前 10 分钟 p99 ≤ 1 s |

**按题设计算：**

```text
读 CPU 需求 = 2400 × 0.003 = 7.2 核
稳态写 CPU 需求 = 300 × 0.005 = 1.5 核
首 10 秒写 CPU 需求 = 600 × 0.005 = 3.0 核

稳态 Tomcat 总需求 = 7.2 + 1.5 = 8.7 核
每实例稳态需求 = 8.7 / 4 = 2.175 核 ≈ 2.2 核
每实例首 10 秒需求 = (7.2 + 3.0) / 4 = 2.55 核
```

原 4 台 `4 核 / 8 GB` 改成 2 台 `8 核 / 16 GB`，总规格仍为 16 核 / 32 GB；共享方式变了，单容器阀门和节点争用也随之改变。

### 10.2 原配额错在哪里

| 负载 | 原 CPU 配置 | 原内存配置 |
| --- | --- | --- |
| 每个 Tomcat | 只设 limit 3 核 | 只设 limit 5.0 GB |
| 批处理 | 未设置 | 未设置 |

运维的理由是“平均 CPU 2.2 核，给 3 核；平时内存 4.5 GB，给 5 GB”，漏掉了周期内突发和内存峰值。

9:00–9:05 的设定观测：节流周期比例 38%，RSS 峰值 5.1 GB，节点 1 CPU 约 67%，内存已用约 70%。这些摘要指标没有提供逐周期、逐请求的完整轨迹，不应拼成一张精确的同时刻快照。

若按 Kubernetes 的默认规则补齐 request，原 Tomcat 的 CPU、内存 request 会分别成为 3 核、5 GB；单容器 Pod 因而可能是 Guaranteed。**QoS 较高也不能修复过低的 limit。**

### 10.3 讨论一：节点 CPU 未满，为什么 p99 仍抖动

**课件讲评：配额余量偏小与周期内节流叠加。**

```text
稳态相对 3 核配额的占比 = 2.175 / 3 = 72.5%
首 10 秒相对配额的占比 = 2.55 / 3 = 85%

代入 M/M/1 示意式：
1 / (1 − 0.725) ≈ 3.6
1 / (1 − 0.85) ≈ 6.7
```

上述倍数说明逼近容量时等待可能迅速增加，不能当成 Tomcat 的实测延迟倍数。38% 节流比例说明自身 CPU 配额确实被触发；节点平均 67% 不构成“容器不会节流”的证据，也不足以排除所有瞬时邻居干扰。

参考修改为 CPU request 2.6 核，limit 4 核：

```text
request ≈ 峰值 2.55 核，向上取 2.6
limit ≥ 2.55 / 0.7 ≈ 3.64 核，取 4
```

另两种选择是取消 CPU 硬 limit 或限制 CPU 密集型并发，代价见第 4.4 节。修改后要复测节流、p99 和同节点批处理完成时间，不能只验证 CPU 百分比下降。

### 10.4 讨论二：节点内存有余量，为什么仍被杀

**课件讲评：容器需要约 5.1 GB，却只有 5.0 GB 的硬上限。** 节点其他空闲内存不能自动越过这个限制。

参考修改：内存 `request = limit ≈ 5.5 GB`，覆盖题设完整峰值并加约 8% 余量。归因时仍要核对 cgroup 内存计数和 OOM 事件，而不是只看进程 RSS 或退出码。

### 10.5 讨论三：批处理为什么选 Burstable

参考配置：

```text
CPU：request 0.5 核，limit 4 核
内存：request 0.5 GB，limit 3 GB
QoS：Burstable
```

批处理可以借用空闲资源，争用时接受变慢；内存使用超过较小 request，在本案例条件下更容易成为压力驱逐候选。它是否最先被驱逐，还取决于优先级和其他 Pod 的用量。

不用无明确上限的 BestEffort，是为了限制失控占用。若改为 CPU `request = limit = 4 核`，并满足其余 Guaranteed 条件，节点 1 的 CPU request 会变成：

```text
2 × 2.6 + 4 = 9.2 核 > 8 核，按题设放不下。
```

代价由统计任务及其使用者承担：完成时间推迟；若被终止，重跑浪费部分工作，因此需要检查点等恢复设计。

### 10.6 讨论四：12 核 limit 放在 8 核节点上是否成立

节点 1 的参考 CPU 配额：

```text
Σrequest = 2.6 + 2.6 + 0.5 = 5.7 核 ≤ 8 核
Σlimit = 4 + 4 + 4 = 12 核
超卖比 = 12 / 8 = 1.5

首 10 秒需求 = 2 × 2.55 + 4 = 9.1 核 > 8 核
```

**课件讲评：成立的依据是让批处理降速，不是错峰。** 在在线需求各为 2.55 核的理想模型中，两个 Tomcat 共用 5.1 核，剩余 `8 − 5.1 = 2.9 核` 给批处理。

这里不是直接把 8 核按 `2.6 : 2.6 : 0.5` 一次分完：如果三者始终有无限 CPU 需求，静态比例约为 `3.65 : 3.65 : 0.70` 核；本题 Tomcat 的平均需求低于其份额，未用部分才可继续让给批处理。**5.1 / 2.9 是按需求受限的平均分配推演，不是每个瞬间的保证。**

内存反例：若把批处理 limit 改为 8 GB：

```text
Σlimit = 2 × 5.5 + 8 = 19 GB > 16 GB
某时实际需求 = 2 × 5.1 + 6 = 16.2 GB > 16 GB
```

课件据此说明节点 OOM 风险。更准确地说：若这些需求不可回收、无法通过其他机制缓解，就无法同时满足；实际可能先触发 kubelet 驱逐，也可能发生内核 OOM，不能仅凭 16.2 这个数断言固定的处理顺序或受害者。

### 10.7 参考配额表与逐节点核算

**Tomcat 行为每个实例的配置，不是 4 个实例的合计。**

| 负载 | CPU request | CPU limit | 内存 request | 内存 limit | QoS / 说明 |
| --- | --- | --- | --- | --- | --- |
| Tomcat × 4 | 每个 2.6 核 | 每个 4 核 | 每个 5.5 GB | 每个 5.5 GB | Burstable，CPU 两者不相等 |
| 批处理 × 1 | 0.5 核 | 4 核 | 0.5 GB | 3 GB | Burstable，可让步 |
| MySQL | — | — | — | — | 独占 4 核 / 8 GB，不在池内 |

| 节点 | 资源 | 课件容量 | Σrequest | Σlimit | Σlimit / 容量 |
| --- | --- | --- | --- | --- | --- |
| 节点 1 | CPU | 8 核 | 5.7 核 | 12 核 | 1.5 |
| 节点 1 | 内存 | 16 GB | 11.5 GB | 14 GB | 0.875 |
| 节点 2 | CPU | 8 核 | 5.2 核 | 8 核 | 1.0 |
| 节点 2 | 内存 | 16 GB | 11 GB | 11 GB | 0.6875，约 0.69 |

**落地提醒：**课件按 8 核 / 16 GB 直接算，部署时应改用可分配量，并计入 sidecar、节点代理及其他实际负载。全池总量够，不代表每个节点都够。GB 与 GiB 也不能混用；Kubernetes 的 `G` 是十进制，`Gi` 是二进制。[Kubernetes：Resource units](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/#resource-units-in-kubernetes)

### 10.8 入口读限流怎么计算

按课件的应用层 CPU 规划模型：

```text
Tomcat CPU 规划预算 = 16 × 0.7 = 11.2 核

首 10 秒写占用 = 600 × 0.005 = 3.0 核
读阈值 = (11.2 − 3.0) / 0.003 ≈ 2733 QPS，课件取约 2730

稳态写占用 = 300 × 0.005 = 1.5 核
读阈值 = (11.2 − 1.5) / 0.003 ≈ 3233 QPS，课件取约 3230

首 10 秒读流量相对规划阈值的余量
= 1 − 2400 / 2733.33 ≈ 12.2%
```

这是 **CPU 侧的教学估算**：假定均匀分流、单请求 CPU 成本不变、批处理能让步，且其他资源没有先到顶。它没有为批处理设定独立的固定 CPU 预算；若要求整个节点池总用量都不超过 70%，还必须先扣掉批处理和系统开销，不能直接照搬 2730。

读阈值也不能解决写路径过载。题设 300 / 600 TPS 是写入需求，不是证明数据库能够稳定完成的吞吐；写入限流仍应服从数据库磁盘、锁等瓶颈。参考配额表本身不构成提交 p99 达标的证明。

## 11. 公式速查与易混淆概念

| 想计算什么 | 公式 | 前提 / 单位 |
| --- | --- | --- |
| CPU 需求 | `Σ(请求速率 × 单请求 CPU 秒数)` | 结果为核数，不使用请求墙钟耗时 |
| 每周期 CPU 额度 | `Q = L × P` | L 为核数，P 为 ms，Q 为 CPU-ms |
| 额度耗尽时间 | `t_run = L × P / n` | n > L，且 n 个线程真正持续并行运行 |
| 随后节流时间 | `t_stop = P − t_run` | 配额用完后等待下周期的简化模型 |
| 平均 CPU 用量 | `累计 CPU 时间 / 墙钟时间` | 单位统一，结果为核数 |
| 节流周期比例 | `Δnr_throttled / Δnr_periods` | 同一观测窗口，分母非零 |
| CPU limit 规划值 | `峰值需求 / 目标利用率` | 本讲取 0.7，仍需压测 |
| 内存 limit 规划值 | `完整内存峰值 × (1 + 余量比例)` | 本案例取约 8%，口径不能只看堆 |
| 超卖比 | `Σlimit / 可分配容量` | CPU、内存分别按节点计算 |
| 读限流估算 | `(CPU 预算 − 写 CPU 需求 − 其他固定预算) / 单读 CPU 秒数` | 单请求成本稳定，检查其他瓶颈 |

| 容易混淆的概念 | 区别 |
| --- | --- |
| 节点利用率 vs 容器额度消耗 | 分母和时间尺度不同，节点空闲不解除容器配额 |
| 线程数 vs 同时运行的线程数 | 等待 I/O、等锁或等调度的线程并未同时使用 CPU |
| 份额 vs 配额 | 份额决定争用比例，配额限制时间预算 |
| request vs 实际用量 | 一个是配置和调度依据，一个是观测；实际可高于 request |
| CPU limit vs 绑核 | 时间预算不指定固定核心，绑核限定可运行 CPU 集合 |
| 内存 request = limit vs Guaranteed | Guaranteed 还要求所有相关容器的 CPU 条件满足 |
| cgroup OOM vs 节点 OOM vs 驱逐 | 作用域、决策者和触发条件不同 |
| `-Xmx` vs RSS vs cgroup 内存 | 分别是堆上限、进程驻留内存、组内存统计，不能互换 |
| 额度耗尽前经过 25 ms vs 只用 25 CPU-ms | 6 线程各运行 25 ms，合计为 150 CPU-ms |
| 配额表合法 vs SLO 达标 | 合法配置只说明规则可接受，体验仍需实际验证 |

## 12. 课后思考与参考解答（p.31）

### 12.1 为小组项目编制配额表

按以下步骤完成，不仅填写一组数：

1. **列负载性质。** 哪些在线、哪些可重跑，哪些有状态；谁可以让步。
2. **收集用量。** 平均、高分位、峰值和突发持续时间，覆盖 GC、批处理和发布等场景。
3. **写出配额及依据。** CPU / 内存 request、limit、Pod QoS，并注明数据来自测量还是假设。
4. **逐节点求和。** 核对 Σrequest、Σlimit、可分配容量及超卖比。
5. **验证让步路径。** 人为制造竞争，检查在线 SLO、节流、OOM / 驱逐、批处理完成时间。

可使用以下表头：

| 组件 / Pod | 实例数与节点 | CPU request / limit | 内存 request / limit | QoS | 峰值依据 | 让步方式及代价 |
| --- | --- | --- | --- | --- | --- | --- |
| 按项目填写 | 按实际部署填写 | 注明单位 | 注明单位 | 按整个 Pod 判定 | 测量窗口或假设 | 变慢、拒绝、降级或重跑 |

如果取消某负载 CPU limit，Σlimit 不再是一个有限的封顶总量；应明确记录“无硬上限”，转而核算 request、峰值需求和争用结果，不能把缺失的 limit 当成 0。

### 12.2 limit 1.5 核、6 个线程同时忙，每周期被停多久

**按题设计算：**沿用 100 ms 周期，假设至少有 6 个可用 CPU，6 个线程从周期开始持续并行，且没有其他限制或突发额度。

```text
每周期额度 Q = 1.5 × 100 = 150 CPU-ms
额度耗尽时间 = 150 / 6 = 25 ms
随后被停时间 = 100 − 25 = 75 ms

平均 CPU 用量 = 6 × 25 / 100 = 1.5 核
```

CPU 百分比要先看分母：

| 统计口径 | 显示值 |
| --- | --- |
| 一个逻辑 CPU 的能力 = 100% | 150% |
| 容器 limit 1.5 核 = 100% | 100% |
| 8 核节点总能力 = 100% | `1.5 / 8 = 18.75%` |

所以“每周期有 75 ms 被节流”和“平均用满 1.5 核额度”并不矛盾。若物理并行度不足或线程中途等待，不能再直接套 25 / 75 ms。

### 12.3 把 `-Xmx` 从 4 GB 调到 5 GB，容器仍限制 5.5 GB

**按题设推算：**假设开放日堆实际增长到新上限，其他用量保持课件设定：

```text
堆外、栈、元空间等及连接缓冲 = 0.5 + 0.2 + 0.2 + 0.2 = 1.1 GB
新峰值需求 ≈ 5.0 + 1.1 = 6.1 GB
6.1 GB > 容器 limit 5.5 GB
```

因此容器 OOM 风险增加，不能用“5 GB 堆仍小于 5.5 GB limit”判断安全。还可能先出现回收、GC 或应用分配问题，具体表现取决于实际用量。

`-Xmx` 是堆上限，修改它不意味着进程立刻新增 1 GB 驻留内存，所以不能断言改参数瞬间必然被杀。应重新核算完整内存峰值，并同步检查节点总预算；若保留 5.5 GB 容器额度，就必须为非堆内存留出空间。以上沿用课件统一的 GB 算术，真实 JVM 参数与容器配置需先统一到字节单位。

## 13. 复习自测

1. **资源管理的“三问加一个保证”是什么？**
   给多少、放哪儿、何时变；隔离让分配规则实际生效。

2. **为什么容器 3 核 limit 不等于绑定 3 个核？**
   limit 约束周期 CPU 时间，可以短时多核并行，随后因额度耗尽而节流。

3. **节点 CPU 67%，容器平均 2.2 核且 limit 3 核，能排除节流吗？**
   不能。长窗口平均值看不到每个配额周期内的突发，应检查节流计数增量。

4. **节流周期比例 38% 是什么意思？**
   约 38% 的统计周期发生过节流，不是请求超时率，也不是墙钟停顿占比。

5. **12 个线程、3 核配额就一定运行 25 ms、停 75 ms 吗？**
   不一定。还要求 100 ms 周期、12 个线程持续同时运行且有足够 CPU；本案例 8 核节点不满足这个并行度条件。

6. **内存还有三成空闲，容器为什么会 OOM？**
   容器可能达到自己的 `memory.max`，即使整机仍有空闲也无法越过该限制。

7. **内存 request = limit = 5.5 GB，CPU request 2.6、limit 4，是什么 QoS？**
   按本讲单容器 Pod 模型是 Burstable，CPU 的 request 与 limit 不相等。

8. **CPU request 低会直接触发节流吗？**
   不会因越过 request 就触发配额节流；request 影响争用份额，CPU limit 才设时间上限。

9. **为什么批处理不用 BestEffort？**
   本讲要求可让步，但仍要有明确的资源上限，防止无约束占用。

10. **节点 1 的 CPU 超卖比为什么是 1.5？凭什么成立？**
    三个负载 limit 合计 12 核，节点 8 核；在线需求得到保障时，批处理接受少拿 CPU、晚完成。

11. **提高 Tomcat limit 能解决数据库写入瓶颈吗？**
    不能。数据库磁盘、日志同步和锁的上限需要单独核算与保护。

12. **参考配额表完成后，还必须验证什么？**
    有竞争时在线 SLO 是否达标、是否节流或 OOM、批处理能否按可接受的时限完成，以及每个节点是否有足够余量。
