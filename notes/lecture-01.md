## 1. 本讲主线

互联网产品通常具有**规模大、持续提供服务、生命周期长、迭代频繁、需求与技术复杂**等特点。这些特点使开发工作延伸到团队协作、软件架构、资源管理与运行维护。

本讲的逻辑可以概括为：

```text
产品特点：规模、服务模式、复杂度
    ↓
技术挑战：开发协作、可用性、性能、运维
    ↓
基础设施：项目管理、代码管理、CI/CD、沟通工具
    ↓
第一周实践：华为云与 CodeArts 环境准备
```

## 3. 互联网产品的特点

### 3.1 规模大：Scale（p.15）

课件从三个维度描述规模：

| 维度 | 课件列举的量级 | 关注点（补充理解） |
| --- | --- | --- |
| 用户 Users | 十亿级（Billion） | 大量用户带来的访问需求与负载变化 |
| 数据 Data | PB/天（PB/Day） | 数据持续产生，涉及存储、处理与传输 |
| 算力 Computing Power | 数十万台计算机 | 大量机器与资源的组织、管理和维护 |

这些量级用于说明大型互联网产品的规模特征，并非每个互联网产品都必须达到的门槛。

**补充理解：**用户总量不等于并发访问量；数据总量与单位时间新增数据量也不同。描述“规模”时，需要明确指标与时间范围。

### 3.2 以服务形式提供软件：SaaS（p.15）

**SaaS = Software as a Service，软件即服务。**

课件强调三个特点：

- **Continuous：持续提供服务。** 产品需要在运行期间持续满足用户需求。
- **Long Life Cycle：生命周期长。** 软件需要长期维护和演进。
- **Iterative：迭代。** 产品通过多次更新逐步完善功能和质量。

**补充理解：**持续服务与持续变更需要同时成立。例如，更新功能时仍需考虑现有用户的使用，因此发布过程和运行维护也是产品工程的一部分。

### 3.3 复杂度高：Complexity（p.16）

课件分别从需求和技术两个方面讨论复杂度，每个方面又分为横向与纵向。

| 方面 | 横向 Horizontal | 纵向 Vertical |
| --- | --- | --- |
| 需求 Requirements | 功能覆盖广（Broad Function） | 业务流程长且复杂（Long and Complex Process） |
| 技术 Techs | 架构（Architecture） | 全栈（Full Stack）、DevOps |

**补充理解：用电商产品举例。**

- 需求横向复杂：同时存在商品、搜索、购物车、订单、支付等功能。
- 需求纵向复杂：一次下单可能跨越库存检查、订单创建、支付确认与履约等环节。
- 技术横向复杂：需要组织不同组件或服务之间的关系。
- 技术纵向复杂：需要贯通前端、后端、数据、部署与运维等层面。

这里的“横向/纵向”用于分析复杂度，不应直接等同于扩容方式中的“水平扩容/垂直扩容”。

## 4. 产品特点带来的技术挑战（p.17）

| 挑战 | 课件关键词 | 如何理解（补充理解） |
| --- | --- | --- |
| 开发环境与工具 Dev Environment and Tools | 迭代开发、团队协作、沟通 | 多人需要协调需求、代码与交付进度 |
| 可用性 Availability | 持续服务、规模 | 系统需要在持续运行和大规模使用下保持可用 |
| 性能 Performance | 规模 | 用户、请求或数据增长后，仍需维持适当的响应与处理能力 |
| 运维 Operation | 自动化、智能化 | 提高重复操作效率，并增强运行管理能力 |

### 可用性与性能的区别（补充理解）

- **可用性**关注服务能否正常使用。
- **性能**关注请求处理的速度与能力，例如延迟和吞吐量。

例如，服务能够返回结果但响应很慢，主要体现性能问题；服务无法提供功能，则体现可用性问题。严重的性能下降也可能使服务实际上无法使用，两者会相互影响。

本讲提出这些挑战，尚未展开具体架构方案或性能计算公式。

## 5. 团队开发的基础设施（p.18）

| 类别 | 课件内容 | 核心作用（补充理解） |
| --- | --- | --- |
| 项目管理 Project Management | 进度 Schedule、任务 Task | 明确任务分工与时间安排 |
| 源代码管理 Source Code Management | 代码 Code、协作 Collaboration | 管理代码版本和多人协作 |
| 自动化工具 Automation Tools | CI、CD | 自动执行集成与交付相关流程 |
| 沟通 Communication | 微信等 | 协调问题、需求和决策 |

### CI/CD 术语补充

**CI（Continuous Integration，持续集成）**：频繁集成代码变更，并通过自动构建、测试等检查及时发现问题。

**CD** 常见的两种含义是：

| 术语 | 含义 | 发布到生产环境的区别 |
| --- | --- | --- |
| Continuous Delivery | 持续交付 | 保持软件可发布，生产发布可以保留人工确认 |
| Continuous Deployment | 持续部署 | 通过规定检查的变更自动部署到生产环境 |

课件只写了“CD”，未指定是哪一种。理解两者区别即可，不应据此推断实验必须自动发布到生产环境。

**DevOps 补充理解：**强调开发与运维之间的协作，通过共同流程、自动化与反馈支持软件交付和运行；它不等同于某一个工具。

## 6. 第一周任务：环境准备（p.20）

### 6.1 华为云 HuaweiCloud

课件列出的准备内容包括账号（Account）、额度（Credit）与云资源（Cloud Resources）。

| 云资源术语 | 基本含义（补充理解） |
| --- | --- |
| VPC：Virtual Private Cloud | 虚拟私有云，用于组织隔离的云上网络 |
| NAT：Network Address Translation | 网络地址转换，用于转换网络通信中的地址 |
| SNAT：Source NAT | 源地址转换；典型场景是私网主机通过转换后的源地址访问外部网络 |
| DNAT：Destination NAT | 目的地址转换；典型场景是将访问指定外部地址或端口的流量映射到内部服务 |
| Floating IP | 浮动 IP；课件未进一步展开其具体配置方式 |
| ECS：Elastic Cloud Server | 弹性云服务器，提供运行应用所需的计算环境 |
| Security Group | 安全组，用于控制相关云资源允许的入站与出站流量 |

**记忆方式：**VPC 组织网络，ECS 运行应用，NAT 处理地址转换，安全组控制允许通过的流量。

SNAT 与 DNAT 中的 S、D 分别对应 **Source（源）** 和 **Destination（目的）**。地址转换与流量放行承担不同职责，配置时需要分别理解。
