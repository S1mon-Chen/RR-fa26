## 1. 本讲主线：从零件到整机（pp.3–4）

[Lecture 3](/Users/xlchen/RR-fa26/notes/lecture-03.md) 介绍框架、Saga、Outbox、云原生等“零件”。本讲以电商系统为例，说明这些能力如何随着业务增长组合成一个系统。

案例改编自 huashiou《服务端高并发分布式架构演进之路》。复习时，每个阶段都回答三个问题：

```text
当前瓶颈是什么？ → 用什么方案缓解？ → 方案又带来什么新问题？
```

**核心结论：架构演进 = 识别当前瓶颈 + 最小改动。** 11 个阶段是案例中的演进路线，不能直接当作所有项目的升级顺序。

### 1.1 四条线索

| 线索 | 对应阶段 | 主要关注点 |
| --- | --- | --- |
| 单机到集群 | ① 应用与数据库分离；② 缓存；③ 应用横向扩展 | 减少资源争抢与重复查询，增加应用处理能力 |
| 数据层扩展 | ④ 读写分离；⑤ 分库分表；⑧ 引入多种数据系统 | 分散数据库负载，满足不同数据访问需求 |
| 流量入口 | ⑥ LVS / F5；⑦ DNS 轮询 / GSLB | 扩展入口容量与机房覆盖 |
| 应用架构 | ⑨ 拆分应用；⑩ 微服务化；⑪ 容器化、云平台与云原生 | 支持独立迭代、能力复用与部署运维 |

第三阶段之后还有前端插曲：静态资源、CDN、反向代理缓存与前后端分离。

### 1.2 11 个阶段速查

| 阶段 | 当前瓶颈 | 课件方案 | 引入的新问题 |
| --- | --- | --- | --- |
| ① | 应用与数据库争抢单机资源 | 分开部署 | 数据库并发读写成为瓶颈 |
| ② | 读多写少，数据库查询压力大 | 本地缓存 + 分布式缓存 | 一致性、穿透、击穿、雪崩 |

| ⑤ | 业务之间互相影响，大表负载增长 | 按业务分库，按时间或哈希分表 | 跨库 JOIN、分布式事务 |

| ⑩ | 多个应用需要复用业务能力 | 微服务化 | 调用链、服务治理与运维复杂 |
| ⑪ | 运维复杂，资源利用率低 | 容器化、云平台、云原生实践 | 组织能力、成本、供应商锁定 |

## 2. 系统原型：单机电商（p.5）

```text
浏览器 ── 域名解析 ──> DNS
   │
   └── 请求服务器 IP ──> 单台服务器
                           ├─ Tomcat：应用逻辑
                           └─ 数据库：数据存储
```

初始原型将应用和数据库放在同一台机器上。课件先忽略前端，提出问题：**商业模型成功、用户数不断攀升后，如何改进架构？**

需要关注三类资源：计算资源（CPU、内存）、持久化资源（磁盘 I/O）、传输资源（网络 I/O）。

**补充理解：**用户数量只是负载的间接指标；并发请求数、请求频率、读写比例、数据量与业务处理成本，才决定各组件受到多大压力。

## 3. 单机到集群：阶段一至三（pp.6–8）

### 3.1 第一阶段：应用与数据库分开部署

- **瓶颈：**Tomcat 与数据库在同一台机器上争抢 CPU、内存和 I/O 资源。
- **方案：**服务器 A 运行 Tomcat，服务器 B 运行数据库。
- **效果：**应用与数据库可以分别配置资源，减少同机争抢。
- **新问题：**用户继续增长，数据库并发读写很快成为瓶颈。

**补充理解：**分开部署不等于数据库已具备高可用或分布式能力，也会增加网络通信这一环节。它解决的是部署与资源隔离问题。

### 3.2 第二阶段：本地缓存 + 分布式缓存

课件假设电商业务**读多写少**，数据库查询先成为瓶颈，因此让热点数据优先走缓存。

| 类型 | 课件示例 | 补充理解：作用与代价 |
| --- | --- | --- |
| 本地缓存 | Caffeine | 位于应用进程中，访问开销小；不同实例各有副本，更新协调更难 |
| 分布式缓存 | Redis | 多个应用实例可共享访问；增加网络访问、缓存服务容量与可用性管理 |

**补充理解：**一种常见读取路径如下，课件未规定唯一实现：

```text
请求 → 本地缓存 → 分布式缓存 → 数据库
         命中返回     命中返回      未命中时查询并按策略回填
```

缓存减少数据库查询，但引入了以下问题：

| 问题 | 含义（补充理解） |
| --- | --- |
| 缓存一致性 | 数据库已更新，缓存仍可能保留旧值；多级缓存还需协调不同副本 |
| 缓存穿透 | 查询不存在的数据，缓存反复未命中，请求持续进入数据库 |
| 缓存击穿 | 某个热点数据失效，大量请求同时回源 |
| 缓存雪崩 | 大批缓存集中失效，或缓存服务故障，导致大量请求同时回源 |

**下一处瓶颈：**数据库读压力下降后，单机 Tomcat 可能先扛不住。

### 3.3 第三阶段：Nginx 负载均衡，横向扩展 Tomcat

```text
浏览器 → Nginx 反向代理 / 负载均衡
             ├─ Tomcat A ─┐
             ├─ Tomcat B ─┼─> Redis / 数据库
             └─ Tomcat C ─┘
```

- **瓶颈：**单台应用服务器处理能力不足。
- **方案：**增加 Tomcat 实例，由 Nginx 分配请求。
- **新问题：**请求可能落到不同实例，原本只保存在单机上的 Session 无法自然共享。
- **课件方向：**应用无状态化，或集中存储 Session。

**补充理解：**无状态化指实例不依赖自身独有的会话状态来处理后续请求，业务数据仍然需要存储。仅增加实例数，不会自动解决共享数据库的瓶颈。

**版本提示（按课件记录）：**p.8 列出 Tomcat 的 NIO / NIO2，并说明 BIO、APR 已移除。复习重点是应用处理模型与横向扩展；具体迁移需对应目标版本，不能把旧版本连接器配置直接照搬。

## 4. 前端插曲：减少到达应用服务器的请求（p.9）

| 改进 | 做法 | 作用 | 需要处理的问题 |
| --- | --- | --- | --- |
| 静态资源与动态请求分离 | Nginx 直接返回 HTML、JS、CSS、图片；Tomcat 处理动态请求 | 减少应用线程处理静态内容的负担 | 静态资源发布与版本管理 |
| CDN | 静态资源分发到靠近用户的边缘节点，大促前预热 | 降低访问延迟与骨干网流量 | 内容更新、预热与缓存失效 |
| 反向代理缓存 | Nginx 缓存热点页面或接口结果 | 缓存命中时无需访问 Tomcat | 哪些内容可缓存，何时更新 |
| 前后端分离 | SPA + API，前端独立部署、独立迭代 | 分开组织交付与职责 | 跨域、SEO、首屏体验 |

课件特别指出：

- 静态资源可在文件名中加入 hash，区分不同版本。
- 跨域部署需要考虑 CORS。
- CSR / SSR 等渲染策略会影响缓存位置；SEO 与首屏问题可联系 SSR 理解。

**补充理解：**反向代理缓存适合读多、变化慢的内容。商品详情中的介绍、库存、个人价格等字段更新频率和共享范围不同，不能不加区分地缓存整个响应。前后端分离也不意味着必须采用纯 CSR。

## 5. 数据层扩展：阶段四与五（pp.10–11）

### 5.1 第四阶段：读写分离

**瓶颈：**读与写在同一个数据库实例上互相争抢资源。

```text
写请求 → 主库 ── 复制 / 同步 ──> 从库 ← 读请求
```

**新问题：主从同步延迟与“读己之写”。**

**补充理解：**“读己之写”指用户完成写入后，后续读取能够看到自己的修改。例如选课成功后立即查询课表，如果查询落到尚未同步的从库，可能暂时看不到这门课。

可根据业务对一致性的要求设计读取路径，例如对关键的写后查询暂时读取主库；这会增加主库读压力，需要明确适用范围。

**要点：读写分离主要分担读负载，不能直接消除主库上的热点写入或行锁竞争。**

### 5.2 第五阶段：分库分表

不同业务共用一个数据库，负载与数据增长后可能互相影响。课件提出两种拆分方式：

| 手段 | 课件做法 | 补充理解：设计问题 |
| --- | --- | --- |
| 分库 | 按商品、支付等业务拆分 | 哪些数据归同一业务，如何减少跨库访问 |
| 分表 | 按时间或哈希拆分大表 | 如何选择分片键、定位数据与分散热点 |

**新问题：**跨库 JOIN、分布式事务。原来在一个数据库里完成的关联与事务，可能需要应用协调或新的查询模型。

联系 Lecture 3：

- **Saga**：把跨服务业务过程组织成多个本地事务，失败时执行相应补偿。
- **Outbox**：在同一个本地事务中提交业务数据与待发送消息记录，支撑后续可靠发布。

**补充理解：**这两个模式职责不同，Outbox 本身不等于跨库事务。分表也不自动等于负载均匀：按月分表可能仍将所有近期写入集中到当月表；单个热门课程的余量行也不会因为其他数据分表就失去写竞争。

## 6. 流量入口扩展：阶段六与七（pp.12–13）

### 6.1 第六阶段：LVS / F5 承载多台 Nginx

**瓶颈：**后端已经扩展为集群，但单机 Nginx 成为入口瓶颈。

```text
浏览器 → 虚拟 IP（VIP）
             ↓
       LVS / F5 主备
             ↓
       多台 Nginx
             ↓
       多台 Tomcat
```

课件采用 **LVS / F5 + 主备 + 虚拟 IP**，通过四层转发承载多台七层代理。

| 维度 | 四层负载均衡 | 七层负载均衡 |
| --- | --- | --- |
| 主要处理依据（补充理解） | IP、端口、连接等传输层信息 | HTTP 主机名、路径等应用层信息 |
| 本讲角色 | 入口层分流 | Nginx 反向代理与请求分配 |
| 取舍 | 转发工作相对简单，但缺少应用层语义 | 可按业务请求路由、缓存，但处理工作更多 |

**补充理解：**课件强调四层转发的性能优势，不能理解为任何硬件、配置和工作负载下都有固定性能差距。这里的 LVS / F5 指其在图中的四层接入角色；产品名称不等于只能工作在某一层。

主备和虚拟 IP 支持入口故障切换，但单个活动入口仍有容量上限，系统也仍局限于一个机房。

### 6.2 第七阶段：跨机房负载均衡

**方案：**使用 DNS 轮询 / GSLB，让同一域名对应分属不同机房的虚拟 IP。

```text
                    ┌─ VIP A → 机房 A 的入口与应用集群
域名 → DNS / GSLB ──┤
                    └─ VIP B → 机房 B 的入口与应用集群
```

**新问题：**跨机房数据同步，以及 DNS 缓存导致的切换延迟。

**补充理解：**GSLB 是 Global Server Load Balancing，即全局服务器负载均衡。简单 DNS 轮询并不自动提供完整的健康检查与故障切换能力；客户端和解析器缓存也使流量无法在修改解析后立即全部切走。图中的双机房入口不代表已经解决跨机房数据一致性或完整容灾。

## 7. 第八阶段：按数据需求引入专门系统（p.14）

随着数据成为重要资产，单靠原有关系数据库难以满足新增的检索、分析等需求。

| 类别 | 课件示例 | 理解重点 |
| --- | --- | --- |
| NoSQL | HBase、MongoDB；图中还列出 Neo4j | 根据数据模型与访问方式选择存储 |
| 搜索引擎 | Elasticsearch；图中还列出 Solr | 支持专门的检索需求 |
| 分布式文件系统 | HDFS | 存放分布式文件数据，可作为数据处理的基础 |

**新问题：多数据源一致性。** 同一业务变化可能需要更新数据库、搜索索引等多个表示，课件提到 CDC 同步。

**补充理解：**CDC 即 Change Data Capture（变更数据捕获），将源数据库的变化传递给下游。异步同步仍需处理延迟、失败、重复与顺序；搜索索引未更新时，可能暂时检索不到刚修改的数据。

本阶段的重点是**按需求选择数据系统**，并非把关系数据库全部替换掉，也不是每个项目都要引入表中的全部组件。

## 8. 应用架构演进：阶段九至十一（pp.15–17）

### 8.1 第九阶段：按业务线拆分应用

- **瓶颈：**业务代码不断堆积，一个应用难以支持业务细分与快速迭代。
- **方案：**按业务线拆分应用。课件示例为淘宝应用、天猫超市、天猫书店、天猫户外等。
- **收益：**不同业务线独立迭代。
- **新问题：**用户、订单、支付等公共模块在各应用中重复实现。

### 8.2 第十阶段：微服务化与功能复用

将用户、订单、支付等能力抽成服务，供多个业务应用使用。课件同时提及“中台化及其反思”。

| 阶段 | 拆分对象 | 首要目的 |
| --- | --- | --- |
| 第九阶段 | 按业务线组织的应用 | 独立迭代 |
| 第十阶段 | 用户、订单、支付等业务能力 | 跨应用复用 |

**新问题：**调用链复杂，需要注册发现、熔断限流、链路追踪，部署运维难度上升。

**补充理解：**将公共代码改成远程服务后，调用多了网络延迟与失败方式，服务之间还要管理契约和数据边界。对中台化的反思可以从实际复用价值与协调成本入手：共享能力如果过度集中，也可能让多个团队等待同一服务排期。本讲没有展开中台案例的具体结论。

### 8.3 第十一阶段：容器化、云平台与云原生

**瓶颈：**服务数量增多后，运维复杂、资源利用率低。

| 方向 | 课件列举 | 补充理解 |
| --- | --- | --- |
| 容器化与编排 | Docker / Kubernetes（K8s） | 组织应用运行环境，调度和管理容器实例 |
| 云平台 | IaaS / PaaS / SaaS | 分别侧重基础设施、应用平台、现成软件的服务交付 |
| 云原生实践 | 定义参见 Lecture 3 | 结合松耦合、自动化、可观测等实践管理工作负载 |

p.17 的架构图强调：**容器按需调度，节点按需扩缩。** 图中不同组件使用不同节点数量和资源配置，体现按工作负载分配资源；这些数值是案例示意，不是课程项目的部署要求。

**新问题：**运维体系与组织能力要求、成本，以及供应商锁定（vendor lock-in）。

**补充理解：**容器化、上云与云原生相互关联，但含义不同。应用打包为容器后，仍需解决健康检查、配置、发布、数据持久化和故障恢复；云平台也不会自动消除热点写入等业务瓶颈。

## 9. 数量级直觉：怎样读性能表（p.18）

以下为课件提供的**单机吞吐数量级示例**：

| 组件 | 课件数量级 | 对应阶段 |
| --- | --- | --- |
| Tomcat：简单动态请求 | 数千～数万 QPS | 一至三 |
| MySQL：读 | 数千～万级 QPS | 二、四 |
| MySQL：写 | 数百～数千 TPS | 五 |
| Redis | 十万级 QPS | 二 |
| Nginx：七层反向代理 | 数万～十万级 QPS | 三、六 |
| LVS：四层转发 | 数十万～百万级；课件未明确标注单位 | 六 |

课件提醒：数字可能随硬件与请求复杂度相差一两个数量级，并给出教学性的相对关系：

```text
Redis ≫ Nginx ≫ Tomcat ≈ MySQL 读 ≫ MySQL 写
```

**补充理解：**

- QPS 是每秒查询 / 请求数，TPS 是每秒事务数；一次事务可能包含多个操作，二者不能直接等同。
- 不同组件承担的工作不同，上表不是相同测试条件下的性能排名。
- 容量取决于请求复杂度、数据大小、缓存命中率、索引、事务、持久化策略和硬件等条件。
- 一个用户操作可能触发多次后端查询；万级在线人数不等于万级 QPS。
- 容量验证应同时观察吞吐量、延迟、错误率和资源饱和程度。不能只看“每秒完成了多少请求”。

这张表用于理解“为什么瓶颈会在组件之间转移”，具体系统仍需压测。

## 10. 课程实践：选课平台（p.19）

### 10.1 场景特点

| 维度 | 课件描述 |
| --- | --- |
| 当前架构 | 单机，或应用与数据库分离，即第一阶段 |
| 流量 | 平时很低；选课开放前 10 分钟形成类似秒杀的瞬时读写高峰 |
| 数据 | 课程余量是热点行，写冲突集中在少数热门课程 |
| 用户规模 | 全校同时在线上限可估，约万级，远小于电商 |

**关键差异：**本讲电商案例从读多写少出发；选课高峰还包含对少量课程余量的集中写入，因此瓶颈顺序可能不同。

### 10.2 讨论一：先崩的是 Tomcat 线程池还是数据库行锁？

**参考思路：先观测，不能只凭架构图判断。**

| 观察对象 | 重点证据 |
| --- | --- |
| Tomcat / 应用 | 活跃线程、请求排队、CPU、超时情况，线程在计算还是等待下游 |
| 数据库连接池 | 活跃连接、等待连接的请求数和等待时间 |
| 数据库 | 慢查询、事务耗时、行锁等待、死锁、I/O |
| 请求链路 | 时间花在入口排队、业务计算、数据库访问还是锁等待 |

压测应分别覆盖查课、分散选课、集中抢同一门课等场景。线程池占满可能是应用计算不足，也可能是大量线程等待数据库；后者仅增加 Tomcat 实例可能加重数据库竞争。

### 10.3 讨论二：缓存余量、排队削峰、限流如何选择？

| 手段 | 主要缓解什么 | 代价与边界（参考思路） |
| --- | --- | --- |
| 缓存课程信息与余量 | 减少重复读取数据库 | 余量可能短暂过时；提交时仍需做权威校验 |
| 排队削峰 | 平滑短时写入洪峰 | 增加等待；需要处理队列积压、重复请求、失败与结果查询 |
| 限流 | 将进入系统的负载限制在可承受范围内 | 部分请求被拒绝或要求稍后重试；需要清楚反馈并考虑公平性 |

**补充理解：**无论选哪种性能方案，正确性都要独立保证：不能超选，同一学生不能重复占位。常见思路是在数据库事务中使用带余量条件的更新，并配合选课记录的唯一约束，明确失败与重试语义；这只是实现思路，不是课件指定方案。

异步排队时，“已受理”与“选课成功”是不同状态。前端应等待最终结果后再确认成功。

### 10.4 讨论三：哪些阶段可能用不上？

**参考思路：**在本讲给定的用户规模和课程业务范围内，可能不需要多层 LVS 接入、复杂分库分表、HDFS，或按多条商业业务线拆分应用。是否跨机房取决于可用性目标，是否引入搜索系统取决于检索需求，不能仅根据用户量判定。

“永远用不上”难以脱离需求作绝对判断。更准确的回答是：**当前没有相应瓶颈或需求，就不必承担该方案的成本。** 容器化也可从项目早期采用，不必先经过前十个阶段。

### 10.5 讨论四：只允许改一处，改哪里？

**参考思路：**先指出观测到的瓶颈，再选择一处修改。例如：

- 重复查课占据数据库大部分负载：缓存稳定的课程信息。
- 应用 CPU 饱和而数据库尚有余量：增加应用实例并分配流量。
- 热门课程行锁等待明显：优先缩短关键事务，或限制同时进入写路径的请求。
- 瞬时流量远超稳定处理能力：在入口实施有界限流或排队。

题目没有给出压测结果，因此不能断言某一项一定最好。验证时比较修改前后的成功吞吐、尾部延迟、错误率，以及选课数据是否正确。

## 11. 本讲小结：系统设计应适可而止（p.20）

不能照搬演进顺序，原因有三：

1. **应用场景不同：**电商与选课平台的读写比例、热点和峰值形态不同。
2. **组织能力不同：**团队能否部署、监控、排障和维护新增组件，决定方案是否可行。
3. **技术起点不同：**项目可以从云和容器起步，无须重走案例中的历史顺序。

课件强调 YAGNI（You Aren't Gonna Need It）：按需演进，避免为尚不存在的需求过度设计。

**补充理解：**可以用以下流程组织一次架构决策：

```text
明确负载与质量目标
  → 采集证据，定位当前瓶颈
  → 选择能缓解瓶颈的最小改动
  → 列出一致性、可用性、运维与成本代价
  → 压测验证，决定是否继续演进
```

## 12. 课后思考与参考资料（p.21）

### 12.1 课后思考

1. **挑一个熟悉的系统，判断它处在第几阶段，写出当前瓶颈和最小改动。**  
   参考组织方式：业务与负载 → 当前架构 → 瓶颈证据 → 最小改动 → 新问题 → 验证指标。实际系统可以同时使用多个阶段的手段，不必硬贴单一阶段标签。

2. **阅读原文，找出课件省略的两步（CDN / 反向代理、ESB），说明为什么可以省略，以及什么情况下不能省。**  
   课件已在 p.9 的前端插曲中介绍 CDN 与反向代理缓存，未把它们单独编号；“省略一个阶段”不等于这些能力没有价值。ESB（Enterprise Service Bus，企业服务总线）未在本讲展开。本题仍需阅读原文，再结合其系统集成背景作答，不能仅由本课件还原原文论证。

3. **选课平台的“秒杀”高峰，用本讲哪两个阶段的手段就够了？**

## 13. 复习自测

1. **为什么第一步是应用与数据库分离？**  
   减少两者争抢单机资源，并支持独立配置资源；并不自动实现数据库高可用。

2. **缓存为什么能缓解数据库压力，又会引入哪些问题？**  
   命中时减少回源查询；需要处理一致性、穿透、击穿、雪崩。

3. **横向扩展 Tomcat 后为什么要处理 Session？**  
   后续请求可能进入不同实例，不能依赖原实例独有的会话状态。

4. **读写分离能否直接解决热门课程的行锁竞争？**  
   不能。它主要分担读负载，对同一余量行的写入仍需协调。

5. **为什么刚选完课却可能暂时查不到？**  
   若查询走从库或异步更新的读模型，数据可能尚未同步。

6. **分库分表为什么使事务和查询变复杂？**  
   原来在同一数据库内完成的事务和关联，可能需要跨库协调。

7. **LVS / F5 与 Nginx 在本讲架构中如何分工？**  
   前者承担四层接入分流，后者承担七层反向代理；各自有容量和功能边界。

8. **为什么修改 DNS 后，流量不会立刻全部切走？**  
   客户端与解析器存在缓存，跨机房切换需要考虑缓存有效期等因素。

9. **拆分应用与微服务化在本案例中的目标有何不同？**  
   前者按业务线支持独立迭代，后者抽取可被多个应用复用的业务能力。

10. **上云和容器化能否自动消除系统瓶颈？**  
    不能。它们改善资源组织与交付运维，仍需处理业务热点、数据一致性等问题。

11. **为什么不能直接按课件 QPS 数字配置生产系统？**  
    数字依赖硬件、负载与测试口径，必须在目标条件下验证吞吐、延迟与正确性。

12. **本讲最重要的架构原则是什么？**  
    依据证据识别当前瓶颈，实施最小改动，并评估新增复杂度与成本。
