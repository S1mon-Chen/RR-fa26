## 2. 资源的三问与容量规划（pp.5–6）

### 2.1 每种资源都问同样三个问题

| 问题 | 含义 | 示例 |
| --- | --- | --- |
| 上限由什么决定？ | 硬件、配额、配置及工作方式允许的最大能力 | 核数、内存大小、IOPS、fsync 延迟、带宽、连接额度 |
| 如何判断饱和？ | 是否已有工作因资源不足而等待 | CPU 运行队列、换页、磁盘队列、网络排队与丢包 |
| 如何换算？ | 把业务负载转换成同一单位的资源需求 | QPS × CPU 时间；TPS × fsync 次数；QPS × 响应字节数 |

```text
资源需求 = 单请求资源消耗 × 请求速率
规划容量 = 资源上限 × 目标利用率
需求占比 = 资源需求 ÷ 资源上限
```

多个请求类型共用资源时，应把各自的需求相加。CPU 用“核秒/秒”，网络用“字节/秒”或“位/秒”，存储用“IO 次数/秒”；**单位一致后才能比较。**

**利用率**表示资源被使用的程度；**饱和度**关注是否有工作无法立即获得资源。整机平均值、短时峰值、单个核和容器配额的统计边界不同，因此不能只看一个百分比。

**补充理解：**内存与连接数量还涉及驻留时间，不能把所有需求都直接用 QPS 乘一次分配量。内存要看工作集和存活对象；平均在途数量可用边界一致的 Little's Law：`L = λ × W`。

### 2.2 为什么不能把 100% 当作正常运行目标

课件使用 M/M/1 排队模型说明趋势：

```text
ρ = 到达速率 λ ÷ 服务速率 μ
平均服务时间 S = 1 / μ
平均响应时间 W = S / (1 - ρ)
平均排队时间 Wq = W - S = S × ρ / (1 - ρ)
```

| 利用率 ρ | 平均响应时间 W |
| --- | --- |
| 50% | 2 倍服务时间 |
| 60% | 2.5 倍 |
| 70% | 约 3.33 倍 |
| 80% | 5 倍 |
| 90% | 10 倍 |
| 95% | 20 倍 |

接近满载时，少量额外工作就会造成明显等待。因此本讲统一以 **70% 作为容量规划的教学起点**，留下 30% 余量吸收突发和波动。

**公式边界：**M/M/1 假设泊松到达、指数分布的服务时间和单服务台，并要求 `ρ < 1` 才有稳态；真实多核、多队列系统不一定符合。70% 不是数学上的突变点，也不是所有资源的通用阈值，应结合负载波动和延迟目标校验。

课件将思考题 1 的“800 QPS、p95 150 ms”“1200 QPS、p95 1.8 s”“1500 QPS、错误率 9%”放在旁边作趋势对照。**平均响应时间公式不能直接推导这些 p95 或错误率，不能把两列当作精确对应的测量。**

## 3. 延迟数量级：先判断成本在哪一层（p.7）

| 操作 | 课件给出的数量级 |
| --- | --- |
| 内存访问 | 约 100 ns |
| SSD 随机读 | 几十到一百 μs |
| 云盘一次 I/O | 0.5～2 ms |
| 机械盘寻道 | 5～10 ms |
| fsync：NVMe / 云盘 / 机械盘 | 0.1 ms / 1～3 ms / 10 ms |
| 机房内 RTT | 0.1～0.5 ms；思考题 2 取 0.2 ms |
| 同城 / 跨省 / 跨国 RTT | 1～3 ms / 20～40 ms / 100～200 ms |
| 1 Gbps 链路传输 1 MB | 约 10 ms |

复习重点是**量级差异**：一次缓存未命中可能把内存访问变成磁盘访问；一次额外的跨地域往返，可能比几毫秒代码优化更昂贵。

**补充理解：**这些是教学参照，不是设备性能承诺。“100 ns”指内存访问量级，不代表一次完整 SQL 查询只要 100 ns。采用十进制单位，1 MB 在 1 Gbps 上的理想纯传输时间为 `8 Mb / 1000 Mbps = 8 ms`；课件约 10 ms 是量级估算。

## 4. CPU：算时间预算，观察等待（pp.9、11）

### 4.1 从单请求 CPU 时间换算核数

一个可用逻辑核每秒提供约 1 秒 CPU 时间。若单请求平均消耗 `t_cpu` 秒 CPU 时间：

```text
CPU 理论 QPS 上限 ≈ 可用核数 / t_cpu
所需核数 ≈ QPS × t_cpu / 目标利用率
```

沿用上一讲的 4 核、每次查询消耗 3 ms CPU：

```text
理论上限 = 4 / 0.003 ≈ 1333 QPS
70% 规划容量 = 1333 × 0.7 ≈ 933 QPS
若要求 1200 QPS：所需核数 = 1200 × 0.003 / 0.7 ≈ 5.14 核
```

最后一个结果需要按可选规格向上配置，并验证实际吞吐。**CPU 时间不等于请求响应时间**：等数据库、锁和网络的时间，不能全部算成 CPU 消耗。

多个接口的计算方式：

```text
总 CPU 需求（核）= Σ（第 i 类请求速率 × 第 i 类请求 CPU 时间）
```

### 4.2 vCPU、steal 与容器节流

| 概念 | 本讲含义 | 判断时注意 |
| --- | --- | --- |
| vCPU | 云实例获得的逻辑处理单元，常见 x86 规格中对应硬件线程 | 不同架构和规格的定义、单核性能可能不同 |
| steal，`%st` | 虚拟 CPU 等待宿主机提供运行时间的占比 | 持续出现时要检查宿主机调度争用 |
| cgroup throttling | 一组进程用完 CPU 配额后被暂时限制运行 | 宿主机仍有空闲 CPU，也可能发生节流 |
| 单核热点 | 工作集中在一个核或串行执行路径 | 总平均值会掩盖局部饱和 |

### 4.3 典型误判

| 现象 / 误判 | 正确检查方向 |
| --- | --- |
| 4 核机器上进程 `%CPU = 100%`，认为整机满了 | 若工具按单核 100% 计数，进程最多可接近 400%；先确认口径 |
| 平均 CPU 40%～50%，认为 CPU 一定不是问题 | 分核、分时段看利用率，检查运行队列、steal 与节流 |
| 线程更多，吞吐却下降 | 检查上下文切换、串行竞争和下游等待 |
| 增加核数后没有收益 | 可能受串行部分约束，或瓶颈在磁盘、网络和锁 |

`vmstat` 的 `r` 持续超过可用核数，是 CPU 等待的线索。还应使用 `mpstat -P ALL`、性能剖析与火焰图定位具体消耗；某个指标异常并不单独证明根因。

## 5. 内存：关键是工作集能否驻留（pp.10–11）

### 5.1 三类需要核算的使用者

| 项目 | 含义 | 为什么重要 |
| --- | --- | --- |
| 进程 RSS | 当前驻留物理内存的进程页 | 堆、堆外、线程栈等都会占用 |
| 操作系统页缓存 | 内核缓存文件与日志数据 | 可减少磁盘访问，一部分可回收 |
| 数据库 buffer pool | 数据库管理的数据页、索引页等缓存 | 应与热数据规模、访问模式匹配 |

工作集是当前负载反复访问、需要留在内存里的数据。工作集无法驻留时，换页或数据库缓存未命中会把访问转移到更慢的存储。

课件给出的预算思路：

```text
实例预算 ≈ 堆需求 + 其他堆外需求 + 连接缓冲需求
连接缓冲需求 ≈ 每连接缓冲 × 连接数
主机预算 ≈ 各进程需求 + 未计入的系统 / 缓存开销 + 余量

数据库 buffer pool 的教学起点：至少覆盖热数据 × 1.2，再以命中率校验
```

**补充理解：**buffer pool 通常已经包含在数据库进程的内存占用中；连接缓冲也可能已计入堆或堆外。不要把 RSS、buffer pool、全部页缓存机械相加，否则可能重复计算。`热数据 × 1.2` 是课件的规划示例，不能替代对索引、连接、临时执行内存和系统余量的核算。

### 5.2 内存压力会先表现为延迟

观察 `available`、`vmstat` 的 `si/so`、major page fault、GC 频率与停顿，以及数据库缓存命中率。

- `used` 高，不一定代表内存不足；其中可能有可回收缓存。
- 持续 swap in/out、缺页和缓存未命中增加，可能使延迟普遍上升。
- 大量短生命周期分配可能造成 GC 压力，即使存活对象并不多。
- OOM 是严重后果之一，不能等到 OOM 才监测内存压力。

沿用上一讲的辨析：退出码 137 通常表示被 `SIGKILL` 终止，**不单独证明 OOM**；还要看内核或容器事件。没有配置 swap 时，内存压力也不会表现为 `si/so` 上升，应结合其他指标判断。

## 6. 存储：IOPS、吞吐量与持久化延迟（pp.13–16）

### 6.1 三项指标和两类访问模式

| 指标 | 单位 | 回答的问题 |
| --- | --- | --- |
| IOPS | 次/秒 | 每秒能完成多少次 I/O？ |
| 吞吐量 | MB/s | 每秒能传输多少数据？ |
| 延迟 | μs、ms | 一次操作需要等多久？ |

| 访问模式 | 典型场景 | 主要约束 |
| --- | --- | --- |
| 随机小 I/O | 数据库页读取、索引访问 | IOPS 与单次延迟 |
| 同步小写入 | 日志追加后等待 fsync | 持久化延迟、提交并发方式 |
| 顺序大 I/O | 备份、扫描、大文件传输 | 吞吐量，也受其他资源约束 |

日志可以是顺序追加，但**每次追加后都等待持久化**时，依然可能受延迟限制。不能看到“顺序写”就只检查 MB/s。

```text
课件简式：IOPS 需求 ≈ 写 TPS × 每事务 I/O 数 + 读 QPS × 未命中率
吞吐量需求 ≈ IOPS × 平均每次 I/O 大小
```

读项简式假设每次查询只有一次相关缓存访问、未命中产生一次物理读。更一般地，应按“每请求平均物理 I/O 数”核算，并计入日志、索引、后台刷页等工作。**fsync 次数不等于底层 I/O 次数。**

云盘的 IOPS、吞吐量、突发额度受规格影响；本地临时盘需要考虑实例释放或故障后的数据保留能力。本讲所列规格是题设，实际选型还要核对所用产品。

### 6.2 write() 返回与持久化完成

```text
普通缓冲写入：应用 write() → 操作系统页缓存 → 后续写回设备
显式持久化：调用 fsync() → 等待设备报告同步完成 → 返回
```

普通缓冲 `write()` 成功返回不保证数据已经持久化；成功的 `fsync()` 会等待设备报告传输完成。课件用这一差异解释“持久性要付出等待成本”。[Linux fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html)

**补充理解：**这是普通缓冲 I/O 的模型，不能概括所有打开标志与 I/O 模式。数据库的持久性还与日志配置、文件系统和存储设备兑现同步语义的能力有关。

### 6.3 为什么 2 ms 可能把写入限制到几百 TPS

按本讲的简化条件：同步操作串行完成、每次耗时相同、没有组提交；每事务需要 `k` 次 fsync，每次延迟为 `t` 秒：

```text
串行 fsync 能力 ≈ 1 / t
写 TPS 上限 ≈ 1 / (k × t)
fsync/s 需求 ≈ 写 TPS × k
```

| 课件中的 fsync 延迟 | 每事务次数 | 串行模型下的 TPS 上限 |
| --- | --- | --- |
| 云盘 2 ms | 2 | `1 / (2 × 0.002) = 250` |
| NVMe 0.1 ms（p.14） | 2 | `1 / (2 × 0.0001) = 5000` |
| NVMe 0.2 ms（p.27） | 2 | `1 / (2 × 0.0002) = 2500` |

p.14 与 p.27 使用了不同的 NVMe 延迟示例，两个结果分别对应各自参数，不能混用。实际数据库还存在组提交、日志设备布局和其他瓶颈，不能把上式当作所有 MySQL 的固定上限。

### 6.4 redo、binlog 与组提交

本讲按“redo log 一次、binlog 一次”估算每次提交的同步成本；它讨论的是需要持久化的写事务。

**组提交**允许多笔事务共享一次日志同步，降低摊到每笔事务的 fsync 次数。它与“提前返回成功、稍后再刷盘”不同：组提交可以等待该组日志持久化后再确认成功。MySQL 的 binlog 组提交机制也允许通过等待聚合更多事务，但要权衡提交延迟。[MySQL 8.4：Binary Logging Options and Variables](https://dev.mysql.com/doc/refman/8.4/en/replication-options-binary-log.html#sysvar_binlog_group_commit_sync_delay)

**课件讲评：**改为约每秒刷盘可提高吞吐，但故障时可能丢失最近的已确认提交；选课记录不能用这种方式换取性能。

**配置边界：**`innodb_flush_log_at_trx_commit=1` 在提交时写入并刷新 redo；取 2 时每次提交写入、通常定期刷新。官方明确指出每秒刷新并非严格定时，因此“最多丢 1 秒”不能当作硬保证。`sync_binlog` 按提交组控制同步频率，取 0 时依赖操作系统刷新，并不是“binlog 每秒刷一次”的定时开关。[MySQL 8.4：InnoDB 参数](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html#sysvar_innodb_flush_log_at_trx_commit)、[sync_binlog](https://dev.mysql.com/doc/refman/8.4/en/replication-options-binary-log.html#sysvar_sync_binlog)

### 6.5 数据库读写分别怎样使用存储

```text
读：查询 → buffer pool
             ├─ 命中：从内存中的页继续执行
             └─ 未命中：读取磁盘页，再继续执行

写：修改内存中的数据页，产生 redo 等日志
      ├─ 提交路径：按持久性配置完成日志同步
      └─ 后台路径：后续刷新脏数据页
```

在页访问次数不变时，命中率从 99% 降至 90%，未命中率由 1% 变为 10%，物理读需求可能增至原来的 **10 倍**。因此内存不足可以间接变成磁盘压力。

提交持久化不要求把本次修改的所有数据页立即写回，日志使数据库能够恢复尚未落盘的数据页修改。读写分离、分片可以分摊负载，但仍要分别核算每个节点的资源需求。

课件强调存储瓶颈，并不意味着数据库永远不会受 CPU、SQL 执行、锁或网络限制。

### 6.6 饱和征兆与向上游传播

| 观测项 | 含义 / 用法 |
| --- | --- |
| `await`，以及 `r_await` / `w_await` | I/O 平均完成时间，包含排队和服务时间；观察是否偏离基线 |
| `aqu-sz`，旧称 `avgqu-sz` | 设备请求的平均队列长度；与设备并行能力和延迟一起判断 |
| `%util` | 设备忙碌程度的线索；不能单独代表现代 SSD 的性能用满程度 |
| `vmstat b` | 不可中断等待任务的线索，常与 I/O 有关 |
| 数据库指标 | 提交耗时、日志等待、脏页积压、buffer pool 命中率、锁等待 |

课件使用“`aqu-sz > 1`、`%util` 接近 100”提示关注存储等待。**补充理解：**对可并行处理请求的 SSD、RAID 或云盘，队列大于 1 不必然异常；`%util = 100%` 也不单独证明已到吞吐上限，应结合延迟、队列趋势和规格。[Linux iostat(1)](https://man7.org/linux/man-pages/man1/iostat.1.html)

典型传播链可以理解为：

```text
持久化变慢 / 存储排队
  → 提交等待变长，部分事务的持锁时间延长
  → 后续事务等锁，连接占用更久
  → 应用等连接 / 等结果，工作线程被占住
  → 请求排队，尾延迟和超时增加
```

这是本讲对上一讲“线程池耗尽”的进一步解释；实际锁释放时点与提交实现有关，应核对日志等待、锁等待和上游延迟的关联，不能仅凭 CPU 低就认定磁盘是根因。

## 7. 网络：往返、字节数与连接额度分别核算（pp.18–21）

### 7.1 带宽与 RTT 是两个维度

- **带宽**决定每秒可传多少数据，大响应体尤其敏感。
- **RTT**是一次往返耗时，多次串行交互尤其敏感。
- 长连接复用可以减少重复握手，减少串行调用可以减少必须等待的往返。

```text
网络耗时粗估 ≈ 串行往返次数 × RTT + 数据量 / 可用带宽
```

增加带宽不会缩短由传播距离决定的那部分 RTT；如果原先存在拥塞排队，增加可用带宽仍可能降低实际测到的 RTT。这个简式忽略了丢包重传、拥塞控制、共享链路竞争等因素。

### 7.2 思考题 2：20 ms 用到了哪里

课件回顾 [思考题 2](/Users/xlchen/RR-fa26/questions/Q-2/Q-2.md) 的一次新建连接请求，RTT 为 5 ms，TLS 握手按 1 RTT 计算：

| 阶段 | 耗时 |
| --- | --- |
| DNS 解析 | 1 ms |
| TCP 握手 | 5 ms |
| TLS 握手 | 5 ms |
| 请求往返 | 5 ms |
| 服务端处理 | 3 ms |
| 剩余内容传输 | 1 ms |
| 合计 | 20 ms |

服务端处理仅占 `3 / 20 = 15%`。在这个例子中，省掉一次 5 ms 往返的收益，大于把服务端优化 1 ms。

机房内复用已建立的连接时，不需要为每次调用重算 TCP / TLS 握手。课件以 RTT 约 0.2 ms、单次调用网络开销约 0.5 ms 作对照，不能把这次新建连接的 20 ms 套到每个服务间调用上。TLS 往返数取决于协议版本和连接状态，课件列出的 1～2 RTT 是教学概括。

### 7.3 带宽计算：字节到位要乘 8

本讲沿用十进制估算：`1 KB = 1000 B`，`1 MB = 10^6 B`；`B` 是字节，`b` 是位。

```text
出口带宽需求（bit/s）= QPS × 平均响应大小（B）× 8
所需带宽规格 = 出口需求 / 目标利用率

1 Gbps = 125 MB/s（理想换算）
```

课件取实际可用约 100 MB/s 作为估算，真实有效吞吐取决于协议开销、包大小和链路竞争。

| 场景 | 按题设计算 |
| --- | --- |
| 2400 QPS，8 KB JSON | `2400 × 8000 × 8 = 153.6 Mbps`，约 154 Mbps |
| 按 70% 目标利用率采购 | `153.6 / 0.7 ≈ 219.4 Mbps` |
| gzip 压缩比 5:1 | 响应约 1.6 KB，带宽约 30.72 Mbps |
| 2400 次/s 都传输 200 KB 静态首页 | `480 MB/s = 3.84 Gbps` |

100 Mbps 出口无法承载未压缩 JSON 的题设流量；200 Mbps 虽高于 153.6 Mbps，也已经超过 70% 规划线。

压缩需要消耗 CPU；CDN 将可缓存静态资源的传输移到边缘。二者都要按实际命中率、压缩比和业务流量复核。这里“200 KB 首页经 CDN”指课件的静态资源场景，不能直接推成“所有带登录态的动态接口都可共享缓存”。

### 7.4 带宽够了，连接仍可能建不起来

| 资源 | 上限 / 约束 | 可能表现 |
| --- | --- | --- |
| 进程 fd 与服务连接额度 | 操作系统限制、Nginx / Tomcat 配置 | 无法继续接入新连接 |
| 临时端口 | 单源 IP 到同一目标 IP、目标端口的可用源端口范围 | 新建出站连接受限 |
| `TIME_WAIT` 状态 | 关闭后的 TCP 状态占用及端口复用条件 | 高连接周转率下出现端口压力 |
| conntrack | 连接跟踪表容量 | 新连接丢包或超时 |
| NAT / SNAT | 网关连接数、端口和吞吐等规格 | 外部接口连接失败 |
| PPS | 每秒包数上限 | 小包业务带宽不高，但包处理能力先到顶 |

课件给出的临时端口数量级约为 2.8 万～6 万，具体范围取决于系统配置。**不是整台机器所有 TCP 连接一共只能有这么多**；目的地址不同、源 IP 不同和连接复用都会影响数量。

`TIME_WAIT` 不等于应用还持有一个打开的 fd。课件的“无 EIP 实例经 NAT 出公网”指所采用的网络拓扑；实际也可能使用代理等出口方式，应沿真实访问路径检查。

两种连接估算不能混淆：

```text
面向在线用户的连接数 ≈ 在线用户数 × 每用户保持的连接数
外部调用平均活跃连接占用 ≈ 调用 QPS × 平均连接占用时间
```

第二式按一次调用独占一条连接的模型使用；长连接池中的空闲连接、连接关闭后的状态、HTTP/2 多路复用等，要另行考虑，不能直接把活跃请求数当成 NAT 表的全部占用。

### 7.5 网络饱和怎么观察

关注 `sar -n DEV` 中的收发字节与包数、`ss -tin` 中的 RTT 和重传、监听队列溢出，以及内核中的 conntrack 告警。对 NAT 还要检查云平台相应监控。

**课件强调：带宽超限未必立刻显式报错，可能先限速排队，表现为延迟上升。** 队列满时可能丢包、重传，继续恶化后也可能超时或报错；因此“带宽超限不报错”应理解为“不能依赖应用错误率首先发现问题”。重传本身也不只由带宽不足造成。

## 8. 最小实验与观察工具（p.22）

实验原则是每次主要改变一种资源的负载，比较基线与加压后的**吞吐、延迟、队列及资源指标**。以下是实验设计，不是已经完成的测试。

| 资源 | 如何施加负载 | 观察工具 | 主要判据 |
| --- | --- | --- | --- |
| CPU | 纯计算接口，逐步提高请求并发 | `mpstat -P ALL`、`vmstat`、`perf` 与火焰图 | 核心持续繁忙、运行队列增长、吞吐趋于平台 |
| 内存 / GC | 增加短生命周期对象分配，或扩大存活工作集 | `pidstat -r`、堆分析、GC 日志、`vmstat` | GC 频率与停顿、缺页 / 换页、p99 变化；两类负载分别解释 |
| 磁盘 | 课件用大块写入 + fsync；提交路径可另测固定小块同步写 | `iostat -x`、`biolatency`、提交耗时 | `await`、队列长度上升；区分吞吐限制和同步延迟限制 |
| 网络 | 大响应体 + 高并发 | `sar -n DEV`、`ss -tin` | 字节速率接近额度、RTT / 重传或队列增长 |

常用 **Linux 服务端**观察命令：

```bash
mpstat -P ALL 1
vmstat 1
free -m
pidstat -r -p <pid> 1
iostat -x -y 1
sar -n DEV 1
ss -tin
ss -ltn
netstat -s
```

`<pid>` 替换为目标进程。`iostat -y` 跳过从开机以来累计的首份报告，便于观察当前时间窗口；具体字段与命令可用性以系统版本为准。[Linux iostat(1)](https://man7.org/linux/man-pages/man1/iostat.1.html)

实验报告应对应本讲三问：**上限是什么、何时出现等待、计算需求与观察结果是否一致。** 具体接口、参数和操作步骤以本年度实验指导书为准。

## 9. 课程实践：选课平台开放日的资源账（pp.24–25）

### 9.1 题设参数

| 项目 | 课件设定 |
| --- | --- |
| 入口 | Nginx 终结 TLS，EIP 出口 200 Mbps |
| 应用 | 4 台 Tomcat，每台 4 核、8 GB |
| 数据库 | 1 台 MySQL，4 核、8 GB |
| 数据库磁盘 | 通用型云盘，3000 IOPS，fsync 约 2 ms |
| 查询负载 | 2400 QPS，均衡时每台 Tomcat 600 QPS |
| 写入负载 | 300 TPS；开放后前 10 秒需求达到 600 TPS |
| 在线连接 | 2000 人，每人 4 条连接 |
| 查询消耗 | Tomcat CPU 3 ms；本地缓存命中率 70% |
| 查询回源 | 未命中的请求访问 MySQL，每次 CPU 0.5 ms；buffer pool 命中率 99% |
| 查询响应 | 8 KB 未压缩 JSON |
| 提交消耗 | Tomcat CPU 5 ms；MySQL CPU 2 ms；2 次 fsync（redo + binlog） |
| 静态资源 | 200 KB 首页经 CDN 分发 |

p.25 另给出：Tomcat 每台 RSS 约 4.5 GB，数据库热数据 2 GB、buffer pool 6 GB，Nginx 按 10 240 条连接额度计算。

### 9.2 先算有多少查询到达数据库

```text
MySQL 查询 QPS = 2400 × (1 - 70%) = 720

按“一次查询对应一次页访问”的课件简式：
物理读 IOPS ≈ 720 × (1 - 99%) = 7.2
```

两个命中率属于不同层级：本地缓存先挡住 70% 的请求，剩余请求进入数据库后再看 buffer pool。**不能把 99% 直接用于全部 2400 QPS，也不能把两个命中率相加。**

7.2 IOPS 只是上述假设下的读项估算。完整写 IOPS 所需的每事务物理 I/O 数未给出，因此无法仅凭“2 次 fsync”算出总 IOPS；3000 IOPS 也不能直接当作 3000 fsync/s。

### 9.3 300 TPS 时的资源账

下表将课件 p.25 的“容量”列明确称为**规格 / 简化上限**，避免与“乘 70% 后的规划容量”混淆。

| 资源 | 按题设计算的需求 | 规格 / 简化上限 | 需求占比 | 饱和观测项 |
| --- | --- | --- | --- | --- |
| Tomcat 总 CPU | `2400 × 3 ms + 300 × 5 ms = 8.7 核` | 16 核 | 54.4% | 分核利用率、运行队列、steal、节流 |
| MySQL CPU | `720 × 0.5 ms + 300 × 2 ms = 0.96 核` | 4 核 | 24%，课件取整约 25% | 同上，并看执行等待 |
| Tomcat 每台内存 | RSS 约 4.5 GB | 8 GB | 56.3% | available、换页、GC |
| MySQL 内存 | 热数据 2 GB，buffer pool 6 GB | 8 GB | 不能用命中率代表内存利用率 | 命中率 99%、RSS、available、换页 |
| MySQL 同步提交 | `300 × 2 = 600 fsync/s` | `1 / 0.002 = 500 fsync/s` | 120% | 提交耗时、await、aqu-sz、日志 / 锁等待 |
| 出口带宽 | `2400 × 8 KB × 8 = 153.6 Mbps` | 200 Mbps | 76.8% | 发出字节速率、RTT、重传 |
| Nginx 客户端连接 | `2000 × 4 = 8000` | 题设 10 240 条 | 78.1% | 连接数、监听队列、fd |

**120% 表示需求超过供给，不表示磁盘能实际长期以 120% 的能力运行。** 未能处理的部分会等待、被拒绝或超时。

这张表尚未覆盖全部开销：例如 Nginx 的 TLS / 压缩 CPU、提交响应流量、系统内存，以及代理到后端的连接都需要另外核算。

Nginx 的 `worker_connections` 是每个 worker 的连接上限，包含到上游的连接，还受 fd 限制。不能把某个配置值直接当成全实例可服务的客户端连接数；此处的 10 240 仅按课堂题设使用。[Nginx：worker_connections](https://nginx.org/en/docs/ngx_core_module.html#worker_connections)

### 9.4 加上 70% 规划线，看清余量

| 资源 | 70% 规划容量 | 300 TPS 场景的判断 |
| --- | --- | --- |
| Tomcat 总 CPU | `16 × 0.7 = 11.2 核` | 需求 8.7 核，低于规划线 |
| MySQL CPU | `4 × 0.7 = 2.8 核` | 需求 0.96 核，低于规划线 |
| 串行 fsync | `500 × 0.7 = 350 次/s` | 需求 600 次/s，超过规划线与简化上限 |
| 出口带宽 | `200 × 0.7 = 140 Mbps` | 153.6 Mbps 未超规格，但超过规划线 |
| 连接额度 | `10240 × 0.7 = 7168` | 8000 未超题设额度，但余量不足 |

若每事务仍独占两次串行 fsync，则按 70% 目标规划的写入能力只有 `350 / 2 = 175 TPS`。

**首要瓶颈在同步持久化路径；带宽与连接也需要关注。** CPU 的余量不能弥补另一种资源的不足。上述 CPU 估算还假定各应用实例负载较均衡。

### 9.5 开放前 10 秒，600 TPS 的影响

| 资源 | 300 TPS | 600 TPS |
| --- | --- | --- |
| Tomcat 总 CPU | 8.7 核，54.4% | `7.2 + 3 = 10.2 核`，63.8% |
| MySQL CPU | 0.96 核，24% | `0.36 + 1.2 = 1.56 核`，39% |
| fsync 需求 | 600 次/s，上限的 120% | 1200 次/s，上限的 240% |

CPU 看起来仍有余量，但磁盘同步需求已经远超简化上限。即使突发结束，积压请求仍可能继续影响延迟；仅提高线程数会允许更多工作等待，不能提高磁盘的持久化能力。

### 9.6 课件引例的解释与数值边界

**课件讲评：**数据库磁盘饱和，`await` 从 2 ms 上升到 20 ms；提交变慢，热点行锁占用延长，应用线程池被占满，提交 p99 达到 2 s。它将此与思考题 1 的行锁串行部分 `s ≈ 0.25` 联系起来。

整理时应保留以下边界：

1. **250 TPS 与 300 TPS。** 严格按“2 次 fsync × 2 ms，完全串行、无组提交”计算，上限是 250 TPS；p.25 又写“吞吐量被限制在 300 TPS”。两者无法由当前简式同时推出。组提交、并发或测量条件可能解释差异，但课件未给出相应参数，不能替它补成已验证原因。
2. **引例百分比与峰值资源账。** 引例中的 CPU 30%、带宽 5%，与资源账中的 Tomcat CPU 54%、EIP 带宽 77% 不一致。课件没有交代是否来自不同主机、接口或时间窗口，因此分别记录，不当成同一口径的同一组观测。
3. **延迟不能仅靠资源需求精确推出。** `await = 20 ms`、`p99 = 2 s` 与串行比例是课件案例数值；资源账能支持“存在过载”的判断，不能单凭它推导这些具体结果。

本讲可带走的结论是：**逐项核算需求，并沿等待链定位瓶颈；“仪表盘没告警”只说明已有监测没捕捉到问题。**

## 10. 四个课堂讨论的参考答案（pp.26–27）

### 10.1 三项常规指标没告警，先查什么

按本案例先看数据库主机的 I/O 完成时间、队列、提交与日志等待，再核对锁等待、连接池占用和上游请求延迟。课件还要求检查 Nginx 的重传与监听队列溢出。

关键不是永远先查磁盘，而是对每种资源补齐“等待在哪里”的证据，并统一主机、接口、时间窗口与统计单位。

### 10.2 怎样缓解写路径瓶颈

| 方向 | 解决什么 | 需要承担的代价 / 前提 |
| --- | --- | --- |
| 更低延迟的云盘 / NVMe | 缩短一次持久化等待 | 成本、数据保留能力、容灾设计；还要重新压测 |
| 组提交 | 多事务分摊日志同步开销 | 受可并行提交程度限制，可能增加聚合等待 |
| 业务允许时批量提交 | 降低每个业务操作摊到的提交开销 | 事务更大，可能延长持锁时间、扩大失败范围 |
| 减少不必要的提交 | 降低持久化频率 | 必须保留业务所需的持久性和恢复能力 |
| 限流、排队削峰 | 控制进入存储路径的速率 | 增加等待或拒绝；持续需求超容量时不能无限排队 |
| Redis 处理热点余量扣减 | 减少关键路径上的数据库热点竞争 | 仍要设计持久化、幂等、一致性与失败补偿 |

课件不接受让已确认的选课记录可能丢失的优化。**把扣减移到 Redis，并不会自动消除整套业务的持久性要求。**

### 10.3 gzip 和 CDN 能省多少带宽

```text
gzip：8 KB / 5 = 1.6 KB
带宽：2400 × 1.6 KB × 8 = 30.72 Mbps ≈ 31 Mbps
200 Mbps 出口利用率：30.72 / 200 = 15.36%
余量：约 84.64%，课件取约 85%
```

原来余量约 23%，压缩后约 85%。压缩比 5:1 是题设，并非所有 JSON 都能达到；Nginx 还需要足够的压缩 CPU。

若每秒 2400 次请求都从源站取 200 KB 静态首页，需要 3.84 Gbps，远超本案例的 200 Mbps 出口，因此课件要求由 CDN 分发。真实回源流量还取决于缓存命中率和更新方式。

### 10.4 最小实验怎么设计

使用第 8 节的四组实验：固定其他条件，逐步增加目标资源的负载，同时记录吞吐、p95 / p99 和该资源的等待指标。一次只想证明一件事，例如“同步写延迟增长是否伴随提交 p99 增长”，不要只记录最终的 CPU 百分比。

## 11. 公式速查与易混淆概念（p.28）

| 想估算什么 | 公式 / 方法 | 主要前提 |
| --- | --- | --- |
| 资源需求 | `Σ(请求速率 × 单请求消耗)` | 资源和时间单位一致 |
| 规划容量 | `规格上限 × u`，本讲 `u = 0.7` | 目标利用率需按实际负载校验 |
| CPU 核数 | `Σ(QPS × CPU 秒数) / u` | 耗时取 CPU 时间；考虑分布与串行瓶颈 |
| 内存 | 工作集 + 其他必要占用 + 余量 | 统一口径，避免重复统计 |
| 存储 IOPS | `Σ(请求速率 × 每请求平均物理 I/O 数)` | 包含前台和后台 I/O |
| 存储吞吐 | `IOPS × 平均 I/O 字节数` | 注意不同请求大小与读写混合 |
| 写 TPS 简化上限 | `1 / (每次 fsync 秒数 × 每事务次数)` | 串行、无组提交的模型 |
| 出口带宽规格 | `QPS × 响应字节数 × 8 / u` | 多类响应相加，另计协议开销 |
| 网络耗时 | `串行往返次数 × RTT + 数据量 / 带宽` | 粗估，忽略排队、重传等变化 |
| 平均在途数 | `L = λW` | 稳定窗口、平均值、系统边界一致 |

| 易混淆项 | 区别 |
| --- | --- |
| 利用率 vs 饱和度 | 一个看使用程度，一个看有无工作因资源不足而等待 |
| 规格上限 vs 规划容量 | 规划容量预留了余量，不能把规格直接当成稳定运行目标 |
| CPU 时间 vs 响应时间 | 响应时间还包括排队、锁、I/O 和网络等待 |
| buffer pool 命中率 vs 内存利用率 | 一个是访问比例，一个是空间占用比例 |
| IOPS vs fsync/s vs TPS | 分别统计 I/O、同步操作和事务，不能互换 |
| write() 成功 vs 持久化完成 | 普通缓冲写成功不保证数据已持久化 |
| 组提交 vs 延后刷盘 | 共享同步成本不必降低确认成功时的持久性要求 |
| 带宽 vs RTT vs PPS | 分别是传输速率、往返耗时、每秒包数 |
| 在线用户 vs 连接 vs 在途请求 | 三者需要根据连接复用与请求行为分别估算 |

## 12. 课后思考与参考资料（pp.28–29）

### 12.1 为小组项目编制资源账

按第 9 节格式列出资源、峰值需求、规格上限、规划容量、需求占比与饱和观测项。

参考步骤：确定读写峰值及突发时长；测量单请求 CPU、内存工作集、I/O、响应大小和连接占用；逐层应用缓存命中率；比较各资源的规划容量，再用负载测试验证最先出现的等待。每个数值都应注明来自规格、测量还是假设。

### 12.2 查阅所用云盘的能力

记录 IOPS、吞吐量、适用的 I/O 大小和突发条件，再测量代表实际提交路径的 fsync 延迟。课件特别提醒：**fsync 延迟通常需要自行测量，规格表未必直接给出。**

### 12.3 迁移至 RTT 30 ms 的异地机房

题目要求沿用思考题 2 第一幕的耗时分解。**参考推算：**假设仍是新建 TCP 连接、TLS 握手占 1 RTT，DNS 仍为 1 ms，内容传输仍为 1 ms，服务端仍为 3 ms：

```text
TCP 握手 + TLS 握手 + 请求往返 = 3 × 30 = 90 ms
含 DNS 和内容传输的客户端网络侧耗时 ≈ 1 + 90 + 1 = 92 ms
完整请求耗时 ≈ 92 + 3 = 95 ms
```

原题网络侧耗时为 17 ms，因此增加约 `3 × (30 - 5) = 75 ms`。主要增加来自三次往返。

若复用已建立且仍可用的连接，并且 DNS 已缓存，只计请求 1 RTT 和内容传输，则网络侧约 31 ms、完整请求约 34 ms。这里仅替换客户端到机房的 RTT；没有假设机房内服务也跨地域，且传输时间和 DNS 不变都是简化条件。

## 13. 复习自测

1. **为什么 CPU 30%、内存还有余量，提交仍可能很慢？**  
   可能在等磁盘同步、锁、连接或网络；本讲案例重点是 fsync 等待向上游传播。

2. **4 核、每请求 3 ms CPU，理论容量和 70% 规划容量分别是多少？**  
   约 1333 QPS 和 933 QPS，其他资源可能更早到顶。

3. **buffer pool 命中率从 99% 降到 90%，磁盘读需求为什么可能增加 10 倍？**  
   未命中率从 1% 增到 10%；前提是相关页访问量和其他条件不变。

4. **3000 IOPS 的云盘，为什么不一定能承载 3000 TPS？**  
   一笔事务可能产生多次 I/O，还要等待日志持久化；IOPS 与同步提交延迟是不同约束。

5. **每事务两次串行 fsync、每次 2 ms，写入上限是多少？**  
   无组提交模型下为 250 TPS；按 70% 规划是 175 TPS。

6. **组提交是否等于降低持久性？**  
   不等于。多笔事务可以共享同步，并在同步完成后再确认成功。

7. **`%util = 100%` 是否足以证明 SSD 已饱和？**  
   不足。还要看延迟、队列趋势、实际吞吐和设备并行能力。

8. **2400 QPS、8 KB 响应需要多大带宽？200 Mbps 是否有 30% 余量？**  
   约 153.6 Mbps；余量只有约 23%，按 70% 规划需至少约 219.4 Mbps，尚未计额外开销。

9. **压缩比 5:1 后，带宽降到多少？**  
   约 30.72 Mbps；需要同时核算压缩的 CPU 成本。

10. **带宽很低时，网络还能因为什么资源饱和？**  
    PPS、fd、临时端口、服务连接额度、conntrack 或 NAT 连接额度。

11. **开放瞬间写需求翻倍，为什么只加 Tomcat 可能没用？**  
    更多实例不能提高同一个数据库持久化路径的能力，反而可能让更多请求同时竞争。

12. **这讲与下一讲的衔接是什么？**  
    先为每种资源回答上限、等待和换算，再将这些观测组织成能发现问题的指标与仪表盘。
